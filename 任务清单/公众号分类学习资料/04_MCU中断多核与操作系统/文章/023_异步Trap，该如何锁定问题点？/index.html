异步Trap，该如何锁定问题点？

开心果 Need Car · 2024-11-12T15:03:00+08:00 · 微信原文

软件Trap问题，我们并不陌生。对于Trap，有同步（Synchronous）和异步（Asynchronous）之分。Synchronous Trap，通过栈可以看出问题触发位置，问题原因一般容易锁定。但是，对于Asynchronous Trap的问题点锁定就有点让人“犯迷糊”，如果问题点并不是你开发的模块，锁定问题点就又增加了点难度。
本文，聊一下Asynchronous Trap的一些思考。
提示：基于TC3xx讨论
1、Trap分类
我们知道，TC3xx主核的每个CPU均有8个TCN（Trap Class Number），每个TCN又包含不同数量的TIN（Trap Identification Number），如下所示：

如上可以看出，大部分的Trap属于同步Trap，异步Trap均由硬件触发。
2、Asynchronous Trap排查的难点
Asynchronous Trap之所以难排查，主要是因为某些结果间接来源于之前执行的指令，但与这些指令的直接关联信息已经丢失。比如，NMI（Non-Maskable Interrupt，不可屏蔽中断），由外部事件触发异常，无法记录问题的具体细节。

为什么不能呢？答：回到异步Trap的特点：Trap发生时，某些结果间接来源于之前执行的指令，但与这些指令的直接关联信息已经丢失，所以，并不能说问题就是由FctlSftyLevel3_CyclicROM_Check()函数触发。
（三）通过DEADD、DATR寄存器确认问题？
既然是异步Trap，Stack又不可信，是不是可以通过对应Core的DEADD（Data Error Address Register）、DATR（Data Asynchronous Error Trap Register）等寄存器去进一步锁定问题呢？

DAE traps are inhibited if the DATR register is non-zero.
解释：如果DATR寄存器非零，则DAE Trap禁用。
分析了DATR寄存器，那么DEADD记录的错误地址可信吗？因为DEADD的作用是记录trap的地址信息，如果这个地址是问题源，问题也就迎刃而解了。但是，如上的解释可以看出，DATR寄存器非零时，DEADD寄存器记录的信息也就没有意义了。所以，异步Trap至此就没了更多的可用信息。
提示：同步错误可以查看DSTR（Data Synchronous Error Trap Register）。
3、如何定位异步Trap问题
目前为止，我没有更好的手段直接锁定异步Trap问题的触发源，只能上笨办法，具体排查步骤：
1、追溯软件版本，确认可用的版本，对比两者差异；
2、针对差异进行代码屏蔽，收窄问题范围，锁定问题所在函数；
3、进一步在函数内屏蔽程序或者断点，锁定问题所在位置。
