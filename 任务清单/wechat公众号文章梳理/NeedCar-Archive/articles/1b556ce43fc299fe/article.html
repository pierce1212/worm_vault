LiBST 放在 Secure Boot 前还是后更合理 —— 从安全与功能安全的系统性分析

开心果 Need Car · 2026-04-17T06:21:00+08:00 · 微信原文

在汽车电子和高安全嵌入式系统中，**功能安全（Functional Safety）与信息安全（Cyber Security）**正在快速融合。LiBST（Logic Built‑In Self Test，逻辑自检）和 Secure Boot （安全启动）分属这两个领域，但在启动阶段不可避免地发生交汇。一个经常被讨论、却容易被误用的问题是：LiBST 应该放在 Secure Boot 之前还是之后？

本文将从系统架构、功能安全逻辑以及工程实现可行性等角度，分析为什么将 LiBST 放在 Secure Boot 之前更为合理，也是当前主流且更易被接受的设计选择。

一、LiBST 与 Secure Boot 的职责边界

要讨论执行顺序，首先要明确两者的角色边界。

LiBST 是一种硬件自检机制，主要用于检测 CPU 核心和关键逻辑单元中的永久性故障，例如 stuck‑at fault等。它关注的是：硬件是否“物理上是健康的”。

Secure Boot 则是一种信息安全机制，其核心目标是：确保被执行的软件来自可信源，且在存储和加载过程中未被篡改。它关注的是：软件是否“逻辑上是可信的”。

因此，从目标层面看，两者并非并列关系，而是具有明显的前后依赖逻辑。

二、为什么 LiBST 放在 Secure Boot 之前更合理

1. Secure Boot 本身依赖硬件计算可信性

Secure Boot 的基础假设是：CPU 能够正确执行指令，密码学运算结果是可信的。然而，这一假设本身依赖于 CPU 核心和相关逻辑单元“没有硬件故障”。如果 CPU 的比较器、算术逻辑单元或控制路径存在永久性失效，那么：签名验签结果可能是错误的，“看似稳定的”哈希或 ECC/RSA 运算可能产生错误结果，这将导致Secure Boot 的“成功”本身变得不可信。

因此，从逻辑关系上讨论Secure Boot 可信性的前提条件是：执行 Secure Boot 的硬件本身是鲁棒的。而验证硬件健康状态的有效方式之一，正是 LiBST。

2. LiBST 会破坏正常执行上下文

从工程实现角度看，LiBST 并不是一段“普通代码”。它通常会切换 CPU 或逻辑到测试模式，会重配置内部信号路径，可能接管流水线或执行单元，不保证执行前后的上下文连续性。

也就是说，LiBST 的设计目标从来不是“可重入、可继续运行”。如果在 Secure Boot 执行过程中或之后运行 LiBST，就会面临以下问题：

  • Secure Boot 的执行状态是否还能被安全恢复？

  • 验签中间结果是否已经被破坏？

  • 安全状态机如何回滚？

这些问题会导致系统复杂度显著上升，也会增加功能安全和信息安全联合评审的难度。因此，更清晰、可控的设计是：

执行 LiBST → 得到结果 → 复位 → 从干净状态进入 Secure Boot

3. 更符合 ISO 26262 的系统化安全思路

在 ISO 26262 的功能安全体系中，一个核心思想是：避免在潜在故障条件下做出安全相关决策。Secure Boot 明显属于“安全相关决策”，因为它决定哪些代码可以被执行，一旦建立信任链，后续系统行为将以此为基础。如果在未确认 CPU 和关键逻辑健康状态前就执行 Secure Boot，那么一旦事后通过 LiBST 发现硬件故障，就意味着：已经在不可信硬件上建立了信任链，之前的安全决策理论上都需要被否定。

这种设计在安全分析报告（Safety Case）中很难自洽，而“LiBST 在前，Secure Boot 在后”的顺序，在逻辑上更加清晰，也更容易被功能安全评审接受。

三、推荐的工程启动时序

综合安全与功能安全要求，一个被广泛采用的启动时序是：

上电 / POR

    ↓

最小可信启动代码（BootROM / Safety ROM）

    ↓

执行 LiBST

    ↓

LiBST 结果判定

    ├─ 失败 → 进入安全状态 / 锁死 / 报错

    └─ 通过

          ↓

        系统复位

          ↓

      Secure Boot

          ↓

      正常系统启动


四、是否存在例外情况？

在少数架构中，确实存在不影响 CPU 主执行路径的“局部 LiBST”，例如针对某个独立硬件模块的在线逻辑自检。这类 LiBST 可能被安排在系统运行期，甚至在 Secure Boot 之后执行。

但需要强调的是：这类 LiBST 不用于建立启动可信根，它们属于运行期诊断（runtime diagnostics），并不改变“启动阶段 LiBST 应前置”的总体原则。

五、结论

综合系统安全逻辑、功能安全要求和工程实现可行性，将 LiBST 放在 Secure Boot 之前执行，是更合理、更稳健的设计选择。

简而言之：先确认硬件是可信的，再确认软件是合法的；先诊断，再建立信任。这种顺序不仅逻辑自洽，也符合当前汽车电子和高安全嵌入式系统的主流实践。
