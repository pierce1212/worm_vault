如何基于HexView完成自动化填充？

开心果 Need Car · 2025-03-14T06:32:00+08:00 · 微信原文

前文《为什么刷写文件（程序）需要填充（Padding）?》讨论了程序填充的原因。接前文，本文着重讨论如何基于HexView进行自动化填充。本文主要介绍如何基于Windows批处理脚本（*.bat）调用HexView完成程序的自动化填充。同时，对脚本中用到的关键命令进行解释。除此之外，延伸一些讨论。

1、批处理脚本（*.bat）

基于Windows的批处理脚本（FillHexFile.bat）内容如下所示：
@echo off
REM -----------------------------------------------REM Configuration parameters (modify as needed)REM -----------------------------------------------set HEXVIEW_PATH="D:\\APP\\HexViewer\\hexview\\HexView.exe"  set INPUT_HEX="C:\\Users\\songx\\Desktop\\FillHexFiles\\input.hex"                set OUTPUT_HEX="C:\\Users\\songx\\Desktop\\FillHexFiles\\output_filledHex.hex"       set FILL_BYTE=0xFF
REM -----------------------------------------------REM Step 1: Verify input file existenceREM -----------------------------------------------if not exist %INPUT_HEX% (    echo Error：The input file %INPUT_HEX% does not exist!    exit /b 1)
REM -----------------------------------------------REM Step 2: Execute HexView commandsREM -----------------------------------------------%HEXVIEW_PATH% %INPUT_HEX% /S /FR:0x80000000-0x800A0000 /FP:%FILL_BYTE% /XI:32 -o %OUTPUT_HEX%
REM -----------------------------------------------REM Step 3: Verify output file creationREM -----------------------------------------------if exist %OUTPUT_HEX% (    echo Success: Padded file saved to %OUTPUT_HEX%) else (    echo Error: Padding failed! Check HexView parameters/logs.    exit /b 1)
（一）脚本主要参数解释
/S：Run in silent mode，即：以静默模式运行，此选项用于抑制对GUI的任何输出。在执行了命令行选项中给出的所有命令后，HexView将被关闭。
/FR：需要填充数据的地址范围，eg：0x80000000-0x800A0000
/FP：在/FR指定的地址范围中，需要填充的值，eg：0xFF
/XI：此选项以Intel-HEX文件格式生成数据，其中，后面的数字32表示每行输出的字节数，用NotePad++打开，如下所示：

set OUTPUT_HEX="C:\\Users\\songx\\Desktop\\FillHexFiles\\output_filledHex.s19"

2、使用技巧

写脚本就是为了方便使用，所以，工程中可以在编译器编译完成后，使其自动调用批处理文件，而不是每次手动打开CMD或者PowerShell。
除了基于HexView填充以外，还可以在编译器对应的链接文件中设置，可以参考前文《如何使用链接文件设置填充值（Fill Value）》。
熟悉Python库的小伙伴提醒：可以尝试使用Python自带的库（intelhex库）进行填充。填充的方式多种多样，可以针对自身擅长的场景选择。
3、延伸讨论
有小伙伴提到：如果段之间的Gap过大，填充后的刷写时间可能会增大。这本身没有问题，确实，如果段之间的Gap太大，填充后刷写未必节省时间。但是，我们需要从工程角度思考：
1、针对特定的某个控制器，我们在设计内存布局（Memory Layout）时，会充分评估每个进程以及每个进程所需的内存资源问题。尤其MCU芯片资源，如此紧张，哪舍得浪费；
2、填充范围是可以自定义的，如果段之间的Gap过大，可以不进行填充处理。软件开发的小伙伴，使用调试器刷写，可能都不care是否填充的问题。前文针对的场景更多的侧重零碎化的内存（这一点我描述的不够具体）；
3、如果某个控制器属于软/硬一体交付，最终软件的集成在Tier1。也有些控制器，OEM自研Application程序，最终的集成会放到OEM侧。但是，不管在OEM集成还是供应商集成的最终软件，一般都需要额外处理，eg：压缩、加密、签名。针对这些场景，每个独立的小Block都操作一次，显然不是最优方案。eg：每个Block都签名一次显然不符合实际工程，如果这样，反而会带来更大的资源开销。所以，很多时候，需要将零散的内存填充成一个进程，进行一次签名即可。如此，程序验签时也不必多次验签，提示：非对称验签耗时，会对程序的实时性造成影响。
当然，我有限的知识框架，不一定覆盖所有的场景，仅供大家参考。
