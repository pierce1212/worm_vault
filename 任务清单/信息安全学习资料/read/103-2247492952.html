工程问题：RAM区未初始化，导致HSM失效

开心果 Need Car · 2023-09-08T11:28:00+08:00 · 微信原文

工程开发中，不同程序之间为了共享一些数据，会开辟一块独立的RAM区域，这块RAM区在程序跳转或者软复位的过程中不做初始化动作，以达到数据共享的目的。eg：Application （App）程序和Bootloader（Boot）程序之间，App为了告知Boot需要升级的请求，会将信息存储在某块共享RAM区，之后，程序跳转到Boot，Boot如果读取到App的升级请求信息，则对App程序进行更新，如果未读取到App请求升级的信息，则再次跳入App程序，示意如下所示：

虽然共享RAM区可以使得不同程序之间进行信息交互，但是，某些时候，如果RAM区处理不得当，反而会引入新的问题。本文分享一个工程问题：RAM区未初始化，导致的HSM（Hardware Security Module）失效问题。

1、问题描述

车辆诊断中，发现：向HSM所属的NVM区域写安全常量（Security Const）或者读取公钥（Public Key）时，Server端回复NRC22（Conditions Not Correct，条件不满足）。
遇到NRC22的否定响应，最先想到是确认车辆是否满足诊断条件，eg：车辆是否下高压、诊断电压是否满足、车速是否＜5Km/h等。然而，这些条件均没有问题，Server怎么就回了NRC22呢？

2、根因分析

既然，常规的诊断前置条件检查没有问题，则进一步的追查软件问题，注重确认最近的变更点，发现：软件新增了一些全局变量、一些变量的数据类型有变动（eg：uint8->uint32）。

新增全局变量和数据类型变动和本文的问题是怎样的一种关联呢？在搞清楚问题之前，先思考一下：新增全局变量或者数据类型变动会影响什么？答：内存区，即：全局变量数据类型扩大或者新增全局变量以后，需要消耗更多的内存区。

举例：在内存中划分一个200K的Section A区域，假设使用了80K空间，当新增全局变量和数据类型变动时，需要为这些变动量分配内存空间，进而使得内存使用空间＞80K，示意如下：

既然是内存空间有变动，又是如何影响HSM功能的呢？

（一）Boot、App内存划分分析
分析Boot和App的内存Layout发现，在App程序中，有一块与HSM共享的RAM区，此区在程序软复位或者程序进入App时，没有初始化动作，即：没有赋初始值或者清零动作。在软件没有变更之前，Boot的CSA区与App的HSM Shared RAM（App）不会重叠，因此App程序在与HSM的交互中，没有异常，即：不回复NRC22。Boot和App的内存Layout示意如下：

当App软件更新以后，即：新增全局变量和数据类型变动后，App的内存Layout发生如下变化：HSM Shared RAM（App）与Boot所用的CSA区存在部分重叠，由于CSA属于程序的栈空间，程序在Boot中的函数调用、中断、Trap均会使用此空间。当程序由Boot进入App以后，如果HSM Shared RAM（App）没有重新初始化，当App程序与HSM交互时，HSM就会获取到被Boot污染的脏数据（Dirty Data），而不是预期数据，进而使得HSM无法有效执行命令，最终导致程序回复上位机NRC22，如下所示：

3、修复措施

既然程序进入App时，未有对HSM Shared RAM（App）初始化导致的HSM功能异常，修改策略也就比较清晰：进入App程序时，重新初始化HSM Shared RAM（App）区域，避免数据被脏数据污染。在App中重新初始化HSM Shared RAM（App）方式有多种，比如：
  1. 开辟一块Flash区域，存储HSM Shared RAM（App）区的初始化值，在App的链接文件中做好映射，以便于App程序初始化时进行HSM Shared RAM（App）区的初始化；
  2. 在App程序中，给每个HSM Shared RAM（App）段中的全局变量赋初始值。
