# CAN FD 异常唤醒测试报告

## 1. 测试结论

本次测试验证了在 ECU 休眠后发送 CAN FD 报文是否会触发异常唤醒，并进一步排查了发送 CAN FD 后普通 CAN 报文无法实际发送的问题。

结论如下：

1. 原始 `0x616` 普通 CAN 唤醒脚本可稳定唤醒 ECU，说明 `0x616` 唤醒报文本身和 ECU 唤醒链路基本正常。
2. 在发送第一条 CAN FD 测试报文 `0x21` 后，10s 内未收到 ECU 的 `0x60B` 响应，判定该报文本身未触发 `0x60B` 异常唤醒。
3. 在 Vector 1610 设备/通道上，发送 CAN FD 报文后，再发送普通 CAN `0x616` 会出现 CANoe 侧有发送动作或 Tx 显示，但物理总线实际未正常发出的现象；停止并重新启动测量后恢复。
4. 在 Vector 1630 设备/通道上未复现该问题。
5. 因此，该问题判断为 CANoe/Vector 硬件通道、驱动或通道配置层问题，不是 CAPL 脚本唤醒状态机的根因。

## 2. 测试目的

测试目的包括：

- 从 `Trace.asc` 中筛选不同 CAN FD 报文 ID 及对应数据。
- 在 ECU 休眠后逐条发送 CAN FD 报文。
- 判断 CAN FD 报文是否会导致 ECU 异常唤醒，即是否收到 `0x60B`。
- 若收到 `0x60B`，记录 CAN FD 报文异常唤醒次数并停止脚本。
- 若 CAN FD 报文 10s 内未触发 `0x60B`，继续发送正常 CAN 唤醒报文 `0x616`，进入下一轮测试。
- 排查发送 CAN FD 后普通 CAN 报文无法实际发出的原因。

## 5. 当前脚本逻辑

当前 CAPL 脚本逻辑如下：

1. 发送普通 CAN 唤醒报文 `0x616`。
2. `0x616` 发送周期为 10ms。
3. `0x616` 最大发送次数为 200 次。
4. 若收到 `0x60B`，判定普通 CAN 唤醒成功。
5. 等待 `0x60B` 消失 500ms，判定 ECU 进入休眠。
6. 休眠后等待 10s。
7. 发送一条 CAN FD 测试报文。
8. CAN FD 报文发送后观察 `0x60B` 10s。
9. 若 10s 内收到 `0x60B`，判定为 CAN FD 异常唤醒，计数后立即停止脚本。
10. 若 10s 内未收到 `0x60B`，判定该 CAN FD 报文未触发异常唤醒，立即进入下一轮，重新发送普通 CAN `0x616`。
11. 所有 CAN FD 报文发送完成后，从第一条重新循环。

关键参数：

| 参数 | 当前值 | 说明 |
|---|---:|---|
| `gSendPeriodMs` | 10ms | `0x616` 发送周期 |
| `gMaxSendCount` | 200 | `0x616` 最大尝试次数 |
| `gSleepSilentTimeMs` | 500ms | `0x60B` 静默多久判定休眠 |
| `gSleepTimeoutMs` | 10000ms | 等待 `0x60B` 消失的超时时间 |
| `gNextRoundDelayMs` | 10000ms | 休眠后发送 CAN FD 前的等待时间 |
| `gCanFdObserveTimeMs` | 10000ms | CAN FD 后等待 `0x60B` 的观察时间 |
| `gTraceMsgCount` | 162 | CAN FD 测试报文数量 |

## 6. 测试现象

### 6.1 原始普通 CAN 唤醒脚本

原始脚本 `CANoe_Wakeup_0x616_0x60B_TestModule.can` 可稳定执行如下流程：

1. 周期发送 `0x616`。
2. ECU 回复 `0x60B`。
3. 等待 `0x60B` 消失，确认休眠。
4. 进入下一轮。

该结果说明 ECU 对普通 CAN `0x616` 的唤醒响应正常。

### 6.2 加入 CAN FD 测试后的现象

加入 CAN FD 测试报文后，观察到以下现象：

1. Round 1 中 `0x616` 唤醒成功。
2. ECU 休眠后发送 CAN FD 测试报文 `0x21`。
3. 10s 内未收到 `0x60B`，脚本判定 `0x21` 未触发异常唤醒。
4. 脚本进入 Round 2，继续发送普通 CAN `0x616`。
5. 在 Vector 1610 设备/通道上，Round 2 发送 `0x616` 后未收到 `0x60B`。
6. 手动测试确认：发送 CAN FD 报文后，再发送正常 CAN 报文，会出现实际未发出的现象。
7. 停止并重新启动测量后，再发送普通 CAN 报文可恢复正常。

### 6.3 错误帧观察

脚本中加入了 `on errorFrame` 诊断逻辑，测试中观察到：

- `errorFrames=0`
- 未观察到明显 CAN error frame 计数增长

因此目前没有证据表明问题是由显式 Error Frame 触发。

## 7. 问题分析

根据手动复现结果，问题并非 CAPL 脚本逻辑导致，原因如下：

1. 原始脚本不发送 CAN FD 报文时，普通 CAN `0x616` 可连续唤醒。
2. 当前脚本中 `0x616` 报文发送格式保持为普通 CAN，未设置 CAN FD 属性。
3. `0x616` 在 Trace 或 Write 窗口中可见发送动作，但物理总线实际未正常发出，需要重启测量恢复。
4. 同样操作在 Vector 1630 上无问题，在 Vector 1610 上有问题，说明问题与硬件设备、驱动或通道配置相关。

推测原因包括：

- Vector 1610 对当前 CAN FD/BRS 场景支持或驱动状态异常。
- 发送 CAN FD 报文后，CAN 控制器 Tx 状态或 Tx 队列异常。
- 通道可能进入某种未在 Trace 中显示的 Tx pending、Error Passive 或 BusOff 恢复异常状态。
- CAN FD 数据相位参数、BRS、ISO CAN FD 设置或收发器能力与被测网络不完全匹配。

## 8. 结论判定

| 项目 | 结论 |
|---|---|
| `0x616` 普通 CAN 唤醒脚本 | 正常 |
| CAN FD 报文 `0x21` 是否触发 `0x60B` | 未触发 |
| CAN FD 后普通 CAN 是否异常 | Vector 1610 上异常 |
| 错误帧是否明显增加 | 未观察到 |
| 是否为脚本主流程问题 | 否 |
| 是否与 CANoe/Vector 硬件通道相关 | 是 |
| 推荐测试设备 | Vector 1630 |

最终判定：当前异常主要由 Vector 1610 设备/通道在 CAN FD 后的发送状态异常引起，不建议继续通过修改 CAPL 状态机规避该问题。应优先使用 Vector 1630 或排查 Vector 1610 的硬件驱动和 CAN FD 通道配置。

## 9. 后续建议

建议按以下顺序继续排查：

1. 使用 Vector 1630 作为正式测试设备执行 CAN FD 异常唤醒测试。
2. 对比 Vector 1610 与 1630 的 Vector Hardware Config：
   - CAN FD 是否启用
   - 仲裁相位速率是否均为 500 kbit/s
   - 数据相位速率是否均为 2 Mbit/s
   - ISO CAN FD / non-ISO CAN FD 设置
   - BRS 支持状态
   - Transceiver 类型与模式
   - BusOff 自动恢复配置
3. 更新 Vector Driver Setup 和 Vector 1610 固件。
4. 复现问题时打开 CAN Statistics，重点观察：
   - Bus State
   - Tx Error Counter
   - Rx Error Counter
   - BusOff
   - Error Passive
   - Tx request 与实际 Tx 计数是否一致
5. 若必须使用 Vector 1610，建议在 CAN FD 报文发送后增加硬件通道复位或重启测量机制，但这属于 CANoe/硬件层恢复，不属于 CAPL 报文测试逻辑。
