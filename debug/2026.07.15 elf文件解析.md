我主要使用 Green Hills 编译器自带的工具读取 ELF，而不是自己解析二进制。

1. 用 `gdump.exe` 读取 ELF 的 DWARF 调试信息：

```
E:\ghs\comp_202114\gdump.exe `
  -N -yd -nl -nm -nf `
  C:\Users\nvtc140\Desktop\compare\1285\D_BIP_S32K3GHS.elf
```

其中可以看到：

```
DW_AT_name("Lib/Calculate/Lib_Calculate.c")
DW_AT_comp_dir("E:\svn\project\ASU\...\ECAS_RTA_S32K324GHS_EOL_FCT")
DW_AT_producer("GHS C 2021.1.4 [dual]")
```

`1285` 的全部 `1331` 个编译单元都记录为 SVN 工程路径；`1289` 记录的是：

```
E:\work\project\current_project\Code\07_EOL_FCT\...
```

2. 用 `gsize.exe` 读取 ELF 中各个可加载区的大小：

```
E:\ghs\comp_202114\gsize.exe `
  C:\Users\nvtc140\Desktop\compare\1285\D_BIP_S32K3GHS.elf
```

它会输出 `.pflash`、`.SysOsApp_code`、`.sram_data` 等区段。独立重建结果和 `1285` 完全一致，总计 `812253` 字节；`1289` 是 `812245` 字节。

3. 用 `gnm.exe` 查看 ELF 符号表：

```
E:\ghs\comp_202114\gnm.exe `
  C:\Users\nvtc140\Desktop\compare\1285\D_BIP_S32K3GHS.elf
```

它能看到函数、变量、地址、大小和符号所属区段，用于确认模型对象和工程模块是否被链接进去。

4. 我没有直接用原工程中的 ELF 做最终判定，而是重新编译源码：

```
make -f ToolCfg/make/project.mk prebuild `
  OUTPUT_DIR=../codex_verify_output `
  GENERATED_DIR=../codex_verify_generated `
  TEMP_DIR=../codex_verify_generated/tmp
```

然后构建独立 ELF 和 HEX。最后用 SRecord 比较可烧写地址和字节：

```
srec_cmp.exe 新构建.hex -Intel 1285\D_BIP_S32K3GHS.hex -Intel
```

结果：

- 新构建与 `1285`：退出码 `0`，逐地址字节完全一致
- 新构建与 `1289`：退出码 `2`，内容不同

之所以比较 HEX 而不要求重新生成的 ELF 整体哈希一致，是因为 ELF 包含编译目录、调试路径等 DWARF 信息；换一个构建目录，ELF 文件会变化，但实际烧写到 MCU 的代码和数据仍可完全一致。
