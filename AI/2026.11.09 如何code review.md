人力成本是双向的。我们不能只统计人工评审花费的时间，还要算上后续修复线上故障的成本。如果只是砍掉评审环节，导致线上 bug 暴涨，本质只是把工作量转移，并不是真正提效。他们的核心目标：<mark style="background: #FF5582A6;">大部分 PR 最多只需要 1 人参与（可以是作者本人），并且不抬升回滚率和线上事故率。</mark>团队以「单 PR 人工审批耗时、人工评论量」观测人力投入，回滚率、事故率是不可突破的红线护栏。

项目里维护两份关键文档：

- CLAUDE.md
    
    项目说明书，记录技术栈、编码规范、项目目标，AI 每一次评审都会读取
    
- REVIEW.md
    
    由代码负责人定义模块评审重点，约束无意义抠细节、明确忽略目录.

Claude 不再只输出代码，而是输出可验证结果：执行测试、构建项目、比对 UI 截图；再由独立子 Agent，带着全新上下文审查代码差异。




# AI 评审：
可能会出现无限循环，需要建立收敛机制

✅ 限制评审轮次，三轮之后要求作者重新评估实现方案；

✅ 多轮评审后，只对比新增代码差异，不再全量重审；

✅ 一次性列出同类全部问题，而不是一次只报一行；

✅ 不再重复上报已经识别过的问题；

✅ 夜间批量跑 AI 评审，提前挖掘存量历史 bug。

# 人的作用
方向判断：这件事到底要不要做，产品愿景、方案取舍；外部提交的变更，一律人工复核；

🔹 高危代码审计：计费支付、自动更新器、CI 流程、安装器等核心高危模块；

🔹 架构评审：决定后续团队共同遵循的底层设计；

🔹 核验证据：复核测试结果、截图、验证材料；

🔹 责任兜底：无论代码是人手写还是 AI 生成，上线变更一定有对应的责任人。

# 无需读取 PR diff 熟悉代码库
不需要任何人掌握整个代码库的完整心智模型，按需查询就足够。逐行阅读琐碎小改动，学习价值其实很低。团队日常在公开 Slack 频道协作，所有人都可以同步看到开发进展，随时参与讨论。


# You land it, you own it

- 鼓励小粒度变更，方便调试、回滚；
    
- 特性开关、灰度机制支持分钟级回退；
    
- 风险爆炸半径管控：风险越高的代码，校验越严格；
    
- 内部试用、埋点遥测快速发现退化；
    
- 事故复盘面向系统流程优化，而非追责个人。
