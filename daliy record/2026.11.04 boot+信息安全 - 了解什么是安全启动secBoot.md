# 什么是安全启动

<mark style="background: #FF5582A6;">**安全启动（Secure Boot）是设备在启动时，先验证即将执行的软件是否可信，验证通过才允许运行的机制。**</mark>

它主要解决两个问题：

- **真实性**：软件是否来自被授权的发布者？
- **完整性**：软件有没有被篡改？

以汽车 ECU 的 Bootloader 为例，普通启动可能直接从 Flash 跳转到应用程序；<mark style="background: #FF5582A6;">安全启动则在跳转前验证应用程序。</mark>

典型过程如下：

```
ECU 上电或复位
      ↓
执行受保护的启动代码
      ↓
验证 Bootloader
      ↓ 验证通过
Bootloader 验证应用程序
      ↓ 验证通过
跳转到应用程序运行

任一环节验证失败 → 拒绝运行该软件，进入受控恢复或故障处理流程
```

**它如何判断软件可信？**

常见做法是使用数字签名：

1. **发布时**：厂商用私钥对固件及相关元数据签名。
2. **启动时**：ECU 使用受保护的公钥验证签名，并核对固件内容。
3. **判断结果**：固件被修改，或者由未授权的密钥签名，验证就无法通过。

<mark style="background: #FF5582A6;">私钥通常由厂商安全保管，ECU 中保存公钥或其可信摘要。攻击者即使能够修改 Flash，也不能仅靠修改程序和校验值，让恶意固件通过签名验证。</mark>

这里有一个关键前提：<mark style="background: #FF5582A6;">**最初负责验证的代码，以及它使用的信任依据，必须受到保护。** 比如将启动代码放在芯片 ROM，将公钥摘要放在 OTP 等受保护区域。这构成了“信任根”，后续逐级验证形成“信任链”。如果攻击者能随意替换验证代码或可信公钥，整个机制就失去了作用。</mark>

安全启动也不代表软件运行后绝对安全：**一份签名合法的固件仍然可能存在漏洞。** 它守住的是“<mark style="background: #FF5582A6;">设备从什么软件开始运行</mark>”这道关口。

## 校验本身的逻辑是:

> [!NOTE]
> 在 **M 7 160 MHz、HSE 80 MHz** 条件下，对 **1024 KB 数据进行 SHA-256 内存验证，典型时间约 13.6 ms**。



读取指定 Flash 区域的数据   (谁在读?读的快?:  <mark style="background: #FFB8EBA6;"> M 7 通过 MU 模块提交 FLS 地址和长度,HSE 子系统读取这个区域</mark>)
           ↓
计算 <mark style="background: #FF5582A6;">SHA-256</mark>   (<mark style="background: #FFB8EBA6;">HSE 通过片上总线访问 PFLASH,计算 SHA-256,可以理解为整段程序内容的指纹 32 字节</mark>)
           ↓       (<mark style="background: #FFB8EBA6;">这个过程是 HSE 在进行的,把计算的 SHA-256 放到 RAM 中</mark>)
使用密钥计算 AES-CMAC  (<mark style="background: #FFB8EBA6;">SHA-256 没有密钥,单独使用不能证明数据经过授权,消息认证码计算</mark>)
           ↓
与指定地址保存的 CMAC 比较(如果程序改了,是否必须要重新修改?)
           ↓
返回通过／失败，由调用方选择后续路径


感觉没有流程真简单,就是跟功能安全的一样,只不过使用的算法更复杂罢了...
<mark style="background: #FF5582A6;">指定程序区域的数据 → SHA-256 → 使用密钥计算 AES-CMAC</mark>

### 为什么计算完 SHA-256 还需要继续计算 AES-CMAC

|只比较 SHA-256|比较 AES-CMAC|
|---|---|
|修改者可以自行计算新摘要，并替换保存的摘要|在密钥保密的前提下，修改者无法自行生成匹配的新认证值|

### 计算 AES -CMAC 时,需要密钥,密钥在哪里,从哪里来?

工程采用的是“固定台架密钥，运行时导入 HSE RAM 密钥槽”的方案。

#### 密钥从哪里来?


![](assets/2026.11.04%20boot+信息安全%20-%20了解什么是安全启动secBoot/file-20261104142652643.png)


```
Std_ReturnType SecMod_Aes128Cmac_GetKey(uint8* pu8Key, uint32 u32KeyLength)
{
    uint8 u8Index;
    if ((NULL_PTR == pu8Key) || (u32KeyLength < SECM_CMAC_KEY_LENGTH))
    {
        return E_NOT_OK;
    }
    SecMod_Aes128Cmac_ObfuscateKey(au8Aes128InputKey, au8Aes128OutputKey);
    for (u8Index = 0u; u8Index < SECM_CMAC_KEY_LENGTH; u8Index++)
    {
        pu8Key[u8Index] = au8Aes128OutputKey[u8Index];
    }
    return E_OK;
}                  
```

<mark style="background: #FFB86CA6;">固定数组 `au8Aes128InputKey`，经过一组位运算得到实际密钥;;;;*输入数组不变，得到的密钥就不变。**这不是每次启动随机生成新密钥。</mark>


#### 得到密钥后放在哪里?

Csm_KeyElementSet(..., au8Key, 16u);这个函数把密钥交给 HSE.当前 BM、FBL 的 Crypto 配置都将这把密钥映射到：

HSE 密钥句柄：0x00020000
含义：RAM 密钥目录，第 0 组、第 0 个槽
这个句柄是密钥的编号，不是可以直接解引用的内存地址。**后续请求 CMAC 时，驱动向 HSE 提交密钥句柄，HSE 使用该槽中的密钥计算。




#### 是否一直保存，是否会更新？

|问题|答案|
|---|---|
|固定密钥的来源数据是否一直存在？|存在，编译进程序镜像，保存在 Flash|
|HSE 中当前使用的密钥槽是否永久保存？|不是，当前映射到 **HSE RAM 目录**，不能依赖它跨复位保留|
|启动后怎么办？|准备流程尝试确认密钥可用，不可用时重新导入|
|每次重新导入的值一样吗？|固定台架配置不变时，一样|
|会自动定期换密钥吗？|当前没有这种机制|





## 如果代码程序变了,是否需要修改已保存的 CMAC

<mark style="background: #FF5582A6;">只要被校验区域的实际字节发生变化，就需要重新计算并更新对应的 CMAC。</mark>

新版 APP 编译生成 HEX
          ↓
完成 CRC 写入、地址提取和 FF 填充等处理
          ↓
使用约定密钥重新计算 CMAC
          ↓
将新 CMAC 写到 0 x 0045 DF 20
          ↓
程序数据与新 CMAC 一起烧录

             等待 HSE 就绪

> BM → 认证 FBL → FBL → 认证 APP/CAL → APP


# 我该如何修改 FBL APP CAL 的 CMAC 来存放在数组里

Step 1. CreateBootStandaloneCMAC.bat 给 FBL 制作 CMAC ,会自动把 CMAC 写入输出 hex 的指定地址里.


它调用：

```
Tools/SecBoot/stamp_secboot_cmac.py
```

处理流程是：

```
FBL 编译生成的 HEX
        ↓
填充空缺，计算 SHA-256 → AES-CMAC
        ↓
自动将16字节 CMAC 写入 HEX 的 0x0045BF00 地址记录
        ↓
生成 *_ALLfillWITHCMAC.hex
        ↓
烧录这份新 HEX
        ↓
芯片 Flash 的 0x0045BF00 保存 CMAC
```

**这里不需要修改 `au8FlashDrvArray`。**那个数组保存的是 Flash 擦写驱动机器码，与程序镜像的 CMAC 是两回事。

需要你做的是：**运行制作脚本，并使用它生成的新 HEX 进行后续打包、烧录。**当前普通编译不会自动完成这一步；如果接入构建流程，才可以做到编译后自动生成。
