# 什么是 DTC

在汽车诊断中，**DTC 是 Diagnostic Trouble Code（诊断故障码），用于记录 ECU 检测到的故障。**

例如：

- 传感器断路或短路
- CAN 通信超时
- 电源电压过高或过低
- 执行器无法正常工作
- 信号超出合理范围

一个典型的 UDS DTC 是 **3 字节故障码 + 1 字节状态**：

```
DTC：12 34 56
状态：09
```

DTC 状态字节的每一位表示一种状态，例如：

| 位     | 含义                                       |
| ----- | ---------------------------------------- |
| bit 0 | `testFailed`：本次测试失败                      |
| bit 1 | `testFailedThisOperationCycle`：本运行周期测试失败 |
| bit 2 | `pendingDTC`：待定故障                        |
| bit 3 | `confirmedDTC`：已确认故障                     |
| bit 4 | `testNotCompletedSinceLastClear`         |
| bit 5 | `testFailedSinceLastClear`               |
| bit 6 | `testNotCompletedThisOperationCycle`     |
| bit 7 | `warningIndicatorRequested`：请求点亮故障灯      |

常见 UDS 服务包括：

- `0x19`：读取 DTC 信息
- `0x14`：清除 DTC

例如读取已确认的 DTC：

```
请求：19 02 08
```

含义是使用 `0x19` 服务的 `0x02` 子功能，查询状态中 `confirmedDTC`（`0x08`）置位的故障。

DID 和 DTC 的区别可以简单理解为：

<mark style="background: #FFB8EBA6;">- **DID**：读取或写入 ECU 的“数据”，例如 VIN、软件版本、传感器值。
- **DTC**：记录 ECU 的“故障”，例如电压异常、通信丢失、执行器故障。</mark>

在 AUTOSAR Classic 中，<mark style="background: #FFB8EBA6;">DTC 通常由 **DEM（Diagnostic Event Manager）** 管理；软件首先上报 Event 状态，DEM 再负责故障确认、状态位、去抖、存储和老化等处理。</mark>

# 为什么 FIM 模块也会更新？

对，你已经生成成功了。FiM 代码也变化是正常的。

原因是 FiM 依赖 Dem 的事件配置。你新增了 `DTC_0x416001_Event`，Dem 的事件数量、事件 ID、事件状态接口都会变化；生成器会同步重算 FiM 能引用的 Dem EventId，以及 FiM 的失效抑制（inhibition）相关表和宏。

即使你没有专门给这个 DTC 配置 FiM 功能抑制，ETAS 的一次 BSW 生成通常也会重新输出 FiM 的生成文件，所以文件内容/时间戳可能更新。

判断是否“真的引入了 FiM 行为”，看生成后的 FiM 配置里是否出现了 `DTC_0x416001_Event`、`DemEventId` 对应条目，或新的 `FiM_FID` 映射：

- 出现：该事件已经被纳入 FiM 的依赖/抑制映射。
- 未出现：只是 Dem 改动触发了 FiM 全量重新生成，不代表这个故障会影响任何功能抑制。

FiM 是 **Function Inhibition Manager，功能抑制管理器**。它不负责判断故障，也不保存 DTC；这些属于 Dem。FiM 的职责是：**根据 Dem 的故障状态，决定某项功能是否还允许执行。**

关系可以记成：


<mark style="background: #FF5582A6;">SWC 监测 → Dem 形成事件/DTC状态 → FiM 判断是否抑制 → 功能SWC执行或降级</mark>


例如你的右气室压力传感器信号丢失：

- SWC 检测到异常，向 Dem 报 `PREFAILED`
- 达到 300 ms 后，Dem 将事件判定为 Failed，并关联到 DTC `0x416001`
- FiM 订阅这个 Dem EventId
- FiM 把“自动高度调节”对应的 FID 判成 inhibited
- 控制软件查询 FiM 后，停止闭环调压，转为安全策略，例如保持当前阀状态、禁止继续充放气、请求降级

核心对象：

- **Dem Event**：故障的实时状态来源，例如 `DTC_0x416001_Event`
- **FID（Function Identifier）**：FiM 管理的“功能编号”，例如 `FID_AutoLevelControl`
- **FiM inhibition configuration**：把某个 Dem Event 与某个 FID 关联，并规定什么状态下抑制

应用侧通常不是“看到 DTC 就自己 if/else”，而是问 FiM：

```
if (FiM_GetFunctionPermission(FID_AutoLevelControl, &permission) == E_OK
    && permission == TRUE)
{
    /* 允许自动高度调节 */
}
else
{
    /* 进入降级或安全策略 */
}
```

这里最重要的区别是：

- <mark style="background: #FF5582A6;">**Dem Failed**：说明故障已成立，诊断上要记录/上报。
- **FiM 不允许功能**：说明业务功能是否继续运行。</mark>

两者不必一一对应。一个 DTC 可以抑制多个功能；一个功能也可以由多个故障共同抑制。并且可以配置成只要故障“当前激活”就抑制，或直到 DTC 清除、重新上电等特定条件后才恢复。

因此，你这次新增 Dem Event 后 FiM 文件被重新生成，是因为 FiM 的输入集合就是 Dem Event；生成器需要重新维护这份事件—功能抑制关系。即使还没有把 `0x416001` 绑定到具体 FID，FiM 生成文件也可能被全量刷新。

```

- 诊断仪执行清除 DTC 后，它才消失。

**你会改成哪一个 Dem API 调用？给出完整的一行代码。****



```

    DemConf_DemEventParameter_RR_HEIGHT_OPEN,
    DEM_EVENT_STATUS_PREPASSED);

#  场景 4：故障持续存在，但读不到 DTC

台架现象：

- `ipd_flg_KL30_MHighFlt = 1` 持续 5 秒
- 10 ms runnable 持续执行
- UDS 请求：`19 02 FF`
- 响应：`59 02 FF 00`，没有任何 DTC
- `0x14` 清除成功
- ECU 无 DET、无复位

现场代码：

```
if (ipd_flg_KL30_MHighFlt == 1)
{
    syncCall9 =
        Rte_Call_Event_DTC_0x411001_Event_SetEventStatus(
            DEM_EVENT_STATUS_FAILED);
}
else
{
    syncCall9 =
        Rte_Call_Event_DTC_0x411001_Event_SetEventStatus(
            DEM_EVENT_STATUS_PASSED);
}
```

已知配置：

```
DemDtcValue                       = 0x411001
DemEventId                        = 4
DemEventAvailable                 = true
Debounce algorithm               = CounterBased
IncrementStepSize                = 1
FailedThreshold                  = 1
DecrementStepSize                = 1
PassedThreshold                  = -1
NvStorageStrategy                = IMMEDIATE_AT_FIRST_OCCURRENCE
```

限制：

- 现在不能改代码或配置。
- 你只能增加最多 **3 个观测点**。
- 这是第 **1 次提交**；即使猜中，我也不会揭晓。

<mark style="background: #FF5582A6;">**答案：`Dem` 拒绝了事件上报。**</mark>

```
syncCall9 = E_NOT_OK
```

说明监控逻辑已经进入 `FAILED` 分支，但事件没有被 Dem 接受。此题设定的根因是：

```
DTC_0x411001_Event 在运行时被 ControlEventAvailable(FALSE) 禁用
```

`DemEventAvailable = true` 只是初始配置，不代表运行期间始终可用。因此：

- `Dem_SetEventStatus(...FAILED)` 返回 `E_NOT_OK`
- 防抖计数器不更新
- DTC 状态不置位
- `19 02 FF` 读不到 `0x411001`
- NvM 尚未参与，问题不在存储层

验证方法：

```
boolean available;
Dem_GetEventAvailable(
    DemConf_DemEventParameter_DTC_0x411001_Event,
    &available);
```

或对 `Dem_SetEventAvailable`、对应的 `ControlEventAvailable` RTE 接口下断点，寻找谁把该事件设成了 `FALSE`。

修复方向：纠正运行时事件使能条件，在允许诊断监控时恢复：

```
Dem_SetEventAvailable(
    DemConf_DemEventParameter_DTC_0x411001_Event,
    TRUE);
```

另外，代码里的 `syncCall9` 被多个 DTC 调用反复覆盖，调试时应为每个事件保留独立返回值，否则第一个失败很容易被后续成功调用掩盖。

## `DemDTCAttributes` 配置

- `DemMemoryDestinationRef = DemPrimaryMemory`  
    确认后的事件记录进入主故障存储器，UDS `19 02` 才能从这里筛选读取。
    
- `DemImmediateNvStorage = true`

- `DemAgingAllowed = false`  
    即使故障之后长期不再发生，DEM 也不会因老化周期自动删除它。下面仍保留的 `DemAgingCycleRef` 不会在运行时生效。
    
- `DemDTCPriority = 2`  
    当主存储器空间紧张、发生故障记录置换时，DEM 用它参与优先级判断。

## 配置 `DTC_0x416001_Event` 的“事件绑定和运行前提”

![](assets/2026.07.29%20DTC%20配置以及使用开发/file-20260730110958973.png)

通过。`DTC_0x416001_Event` 的事件绑定与运行前提符合当前要求。

原理：

- `DemEventKind = DEM_EVENT_KIND_SWC`  
    这个事件由应用 SWC 经 RTE 上报；后续会生成 `Rte_Call_Event_DTC_0x416001_Event_SetEventStatus()` 一类接口。
    
- `DemDTCRef = DemDTC_DTC_0x416001`  
    将 SWC 上报的事件状态关联到刚才配置的 DTC 编号、主存储器和冻结帧属性。
    
- `DemEnableConditionGroupRef = DemEnableConditionGroup_0`  
    该组包含“系统初始化完成”和“电压正常”；任一条件不满足时，监控结果不应推进故障判定。
    
- `DemOperationCycleRef = DemOpCycle_POWER`  
    DEM 以 `POWER` cycle 计算本次故障的确认、测试和恢复相关状态。
    
- `DemEventConfirmationThreshold = 1`  
    防抖完成并形成 `FAILED` 后，一个符合条件的故障周期即可确认；不会再额外等待多个 `POWER` cycle。
    
- `DemEventRecoverableInSameOperationCycle = true`  
    同一个上电周期内，信号恢复后 DEM 可以接受 `PASSED`，并进入恢复路径。
    
- `DemStorageConditionGroupRef = DemStorageConditionGroup_0`  
    即使事件已失败，是否允许写入故障存储器仍要经过该存储条件的门控。

重新生成 FlatView 的入口叫 **Create ECUExtract**，它会同时更新 FlatView、FlatMap 和 ECU Extract。

![](assets/2026.07.29%20DTC%20配置以及使用开发/file-20260730173636525.png)
<mark style="background: #FF5582A6;">`Create ECUExtract` 的作用是：**从整车/系统级设计中，提取属于当前 ECU 的软件配置，并把多层 Composition 展平成 RTE 可以处理的单层视图。**</mark>
在你的工程中，流程是：

```
TopLevelComposition
        │
        │ Create ECUExtract，选择 ECU = ETAS
        ▼
ETAS_FlatView_SWCD.arxml
ETAS_FlatMap.arxml
System_EcuExtr.arxml
        │
        │ RTE Generate
        ▼
Rte_Asw_Swc.h、Rte.c
```

它主要完成三件事：

1. ECU 专属提取  
    根据 `SWC → ECU Instance ETAS` 映射，只保留当前 ECU 使用的 SWC、通信和连接关系。
    
2. Composition 展平  
    将可能存在多层嵌套的 Composition 转换成一个单层 `ETAS_FlatView`，让 RTE 能直接看到所有 SWC 实例和端口连接。
    
3. 建立源模型与展平模型的映射  
    `ETAS_FlatMap.arxml` 记录：
    

```
TopLevelComposition 中的对象
              ↕
FlatView 中生成的对象
```

本次操作的实际效果就是把新连接：

```
CPT_Asw_Swc / Event_DTC_0x416001_Event
        →
CPT_Dem / Event_DTC_0x416001_Event
```

从 `TopLevelComposition` 传播到了 [ETAS_FlatView_SWCD.arxml (line 4150)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ETAS_FlatView_SWCD.arxml:4150)。

需要注意：

- 它不生成 C 代码。
- 它不等于 RTE Generate。
- 它不负责创建 Dem DTC 配置。
- 它会检查系统连接器是否合法，所以这次也暴露了两个旧的 `0xC01101` 无效连接器。
- 一般修改 `TopLevelComposition`、SWC 到 ECU 映射、Composition 端口或连接器后需要重新执行。
- 只修改应用 C 代码不需要执行。
- 只把 Server Call Point 从异步改成同步，通常直接重新生成 RTE 即可。

一句话概括：<mark style="background: #FF5582A6;">**Create ECUExtract 是把系统设计转换成“本 ECU 的 RTE 输入模型”。**</mark>

你当前最有用的是以下几个：

### 查询当前有状态的 DTC

```
19 02 FF
```

### 查询当前失败的 DTC

```
19 02 01
```

### 查询 Confirmed DTC

```
19 02 08
```

### 查询支持的所有 DTC

```
19 0A
```

与 `19 02 FF` 的区别是：

- `19 02 FF`：只返回状态字与掩码匹配的 DTC，状态 `0x00` 通常不返回。
- `19 0A`：返回 ECU 配置支持的所有 DTC，包括当前没有故障的 DTC。

### 读取 `0x416001` 的扩展数据

```
19 06 41 60 01 FF
```

其中：

- `41 60 01`：DTC 编号
- `FF`：读取所有允许的扩展数据记录

### 读取 `0x416001` 的快照

通常可以发送：

```
19 04 41 60 01 FF
```

但具体快照记录号是否支持，要看 Dem 中有没有为该 DTC 配置 FreezeFrame/Snapshot Record。

不是所有 ECU 都支持上述全部子服务，实际取决于 Dcm/Dem 配置。如果子服务未配置，常见响应是：

```
7F 19 12
```

即 `SubFunctionNotSupported`。
