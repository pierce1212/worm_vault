# 什么是 DID

在汽车诊断（UDS，ISO 14229）中，**DID** 是 **Data Identifier（数据标识符）**，用于**唯一标识 ECU 中的一项可诊断数据。**

DID 通常是一个 **16 位编号**，例如：

- `0xF190`：车辆识别码 VIN
- `0xF187`：零件编号
- `0xF18C`：ECU 序列号

诊断仪通过 UDS 服务访问 DID：

- `0x22`：ReadDataByIdentifier，读取 DID
- `0x2E`：WriteDataByIdentifier，写入 DID

例如读取 VIN：

```
请求：22 F1 90
响应：62 F1 90 <VIN数据>
```

其中：

- `22`：读取 DID 服务
- `F1 90`：DID `0xF190`
- `62`：肯定响应（`0x22 + 0x40`）

一个 DID 的配置一般包括数据长度、读写权限、支持的诊断会话、安全等级、数据来源，以及对应的读取或写入处理函数。

这几个节点共同完成一件事：定义“某个 DID 是什么、允许谁访问、数据由谁提供、多个数据怎样排进诊断报文”。

### 1. `DcmDspDids [52]`：DID 本体

这里配置 ECU 支持的 DID，共 52 个。每个 `DcmDspDid` 通常包含：

- `DcmDspDidIdentifier`：16 位 DID 编号，例如 `0xF190`
- `DcmDspDidInfoRef`：引用访问权限配置
- `DcmDspDidUsePort`：DID 与应用层/RTE 的连接方式
- 一个或多个 `DcmDspDidSignal`
- 是否支持动态定义、原子 Sender/Receiver 访问等厂商扩展选项

可以把它理解成 DID 的“目录项”。

当前工程中的一个实例是 `DcmDspDid_DID_0xA`：

- `DcmDspDidIdentifier = 10`，即 `0x000A`
- 引用 `DcmDspDidInfo_DID_0xA`
- 包含一个偏移为 0 的 Signal

配置可见于 [RTA_BIP_Dcm_EcucValues.arxml (line 4285)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ecu_config/bsw/gen/RTA_BIP_Dcm_EcucValues.arxml:4285)。

### 2. `DcmDspDidInfos [52]`：访问权限

`DcmDspDidInfo` 不保存数据，而是定义这个 DID 能否被读写，以及在什么条件下允许访问。

常见子容器包括：

- `DcmDspDidRead`
    - 允许读取的诊断会话
    - 允许读取的安全等级
    - ModeRule、授权条件等
- `DcmDspDidWrite`
    - 允许写入的诊断会话
    - 允许写入的安全等级
- `DcmDspDidControl`
    - 用于 `0x2F InputOutputControlByIdentifier`
- `DcmDspDidDynamicallyDefined`
    - 是否为 `0x2C DynamicallyDefineDataIdentifier` 定义的动态 DID

例如工程中的 DID `0x000A`：

- 读取：默认会话和扩展会话均允许
- 写入：只允许扩展会话
- 写入前还需要解锁 `Unlocked_L1`

因此：

```
22 00 0A       默认会话可以读取
2E 00 0A ...   默认会话不能写
2E 00 0A ...   扩展会话 + L1解锁后才可以写
```

相关配置位于 [RTA_BIP_Dcm_EcucValues.arxml (line 2630)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ecu_config/bsw/gen/RTA_BIP_Dcm_EcucValues.arxml:2630)。

### 3. `DcmDspDidSignal`：DID 内部的数据布局

**一个 DID 可以由一个或多个数据元素组成，每个元素用一个 `DcmDspDidSignal` 放入 DID 数据区。**

主要参数：

- `DcmDspDidByteOffset`：该数据在 DID 数据区中的起始字节
- `DcmDspDidDataRef`：引用哪个 `DcmDspData`

例如一个日期 DID：

```
Byte 0~1：Year
Byte 2  ：Month
Byte 3  ：Day
```

可以配置成：

```
Signal Year  → Offset 0 → Data_Year（2字节）
Signal Month → Offset 2 → Data_Month（1字节）
Signal Day   → Offset 3 → Data_Day（1字节）
```

读取响应就可能是：

```
62 F1 XX 07 EA 07 1C
         └─年─┘ 月 日
```

截图中的 `DcmDspDidSignals [8]` 是编辑器在当前分组中显示的 Signal 配置数；不能仅凭这个数字断定全部 52 个 DID 只有 8 个 Signal。部分 Signal 会作为 `DcmDspDid` 的子容器显示，需要展开具体 DID 查看。

---

### 4. `DcmDspDatas [72]`：实际数据元素

`DcmDspData` 描述某一段诊断数据的属性和获取方式。

主要配置包括：

- `DcmDspDataByteSize`：数据占用多少字节
- `DcmDspDataType`：如 `UINT8`、`UINT16`、`UINT8_N`
- `DcmDspDataEndianness`：大端、小端或 `OPAQUE`
- `DcmDspDataUsePort`：DCM 如何连接数据提供者
- 读函数、写函数、长度获取函数
- 读取条件检查函数
- 是否异步处理

常见 `UsePort`：

- `USE_DATA_SYNCH_CLIENT_SERVER`：DCM 通过同步 Client/Server 调用应用函数
- `USE_DATA_ASYNCH_CLIENT_SERVER`：异步调用，可能返回 `DCM_E_PENDING`
- `USE_DATA_SENDER_RECEIVER`：通过 RTE Sender/Receiver 数据元素访问
- `USE_DATA_ELEMENT_SPECIFIC_INTERFACES`：为具体数据元素生成专用接口
- `USE_DATA_SYNCH_FNC`：直接调用配置的同步 C 函数

当前工程中 DID `0x000A` 对应的数据配置为：

- 类型：`UINT8_N`
- 长度：4 字节
- 字节序：`OPAQUE`
- 接口：`USE_DATA_SYNCH_CLIENT_SERVER`
- 不使用额外的读取条件检查函数

见 [RTA_BIP_Dcm_EcucValues.arxml (line 1357)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ecu_config/bsw/gen/RTA_BIP_Dcm_EcucValues.arxml:1357)。

`OPAQUE` 一般表示 DCM 将它当作原始字节序列处理，不进行数值型大小端转换。

---

### 5. `DcmDspDataInfo`：数据的附加信息

这是可选的数据元信息容器。在当前参数定义中，它主要与诊断数据的 Scaling Information 有关，例如：

- 是否提供缩放信息
- 缩放信息长度
- 配合 `0x24 ReadScalingDataByIdentifier` 使用

截图中它没有 `[数量]`，通常表示当前没有实例，或者该 AUTOSAR/供应商配置版本没有启用此功能。普通的 `0x22` DID 读取一般不需要配置它。

---

### 6. `DcmDspDidRange`：按范围处理 DID

用于定义一段连续的 DID 范围，例如：

```
0xF200 ～ 0xF2FF
```

DCM 不需要逐个建立 256 个 DID，而是把该范围交给统一的回调处理，回调根据收到的 DID 计算并返回数据。

适用于：

- 大量规则相似的 DID
- 动态生成的数据
- Bootloader 或供应商私有诊断范围

截图中该节点没有数量，说明当前很可能没有配置 DID Range。

### 一次 `0x22` 请求的完整流程

以 `22 00 0A` 为例：

```
诊断仪发送 22 00 0A
        ↓
DcmDspDid：查找 DID 0x000A
        ↓
DcmDspDidInfo：检查当前会话、安全等级和访问条件
        ↓
DcmDspDidSignal：确定数据从 ByteOffset 0 开始
        ↓
DcmDspData：通过同步 Client/Server 获取4字节数据
        ↓
DCM组装响应 62 00 0A xx xx xx xx
```

所以最容易记忆的对应关系是：

- `Did`：编号是什么
- `DidInfo`：谁能访问
- `DidSignal`：数据放在哪里
- `Data`：数据多长、什么类型、从哪里取得
- `DidRange`：批量处理一段 DID 编号范围



# DcmDsd

启用 `0x22/0x2E/0x2F` 服务及服务级权限
即使 `DcmDsp` 配置了 DID，如果 DSD 没有启用对应服务，诊断请求仍然无法处理。

主要关系：

- 读取 DID：`0x22 ReadDataByIdentifier`
- 写入 DID：`0x2E WriteDataByIdentifier`
- IO 控制：`0x2F InputOutputControlByIdentifier`
- 动态 DID：`0x2C DynamicallyDefineDataIdentifier`
- 周期读取：`0x2A ReadDataByPeriodicIdentifier`

当前工程已经配置：

- `ReadDataByIdentifierClass`
    - SID 为十进制 34，即 `0x22`
- `WriteDataByIdentifierClass`
    - SID 为十进制 46，即 `0x2E`

见 [RTA_BIP_Dcm_EcucValues.arxml (line 589)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ecu_config/bsw/gen/RTA_BIP_Dcm_EcucValues.arxml:589)。

DSD 和 DID 自身权限是两级检查：

```
DSD服务权限
     ∩
DcmDspDidInfo的DID权限
     =
最终是否允许访问
```

例如，DSD 允许 `0x22` 在编程会话中执行，但某个 DID 的 `DcmDspDidRead` 没有配置编程会话，那么这个 DID 在编程会话中仍然不能读取。

# 整体调用链

当前代码中，DID 采用的是“配置表查找 + 函数指针 + RTE 调用”机制，不是业务代码里用 `switch(DID)` 手工判断。
以读取 VIN：`22 F1 90` 为例：

```
诊断请求 22 F1 90
    ↓
DSD根据SID 0x22找到RDBI处理函数
    ↓
Dcm_Prv_DspReadDataByIdentifier()
    ↓
在Dcm_DIDConfig[]中查找0xF190
    ↓
检查会话、安全等级和数据长度
    ↓
Dcm_GetDIDData()
    ↓
调用Rte_Call_...F190_ReadData()
    ↓
调用Dcm_Swc中的RE_DataServices_DID_0xF190_Read_func()
    ↓
读取NvM RAM Block中的VIN
    ↓
返回 62 F1 90 + 17字节VIN

```



52 个 DID 被生成成一个排序的配置数组
每个表项包含：

- DID 编号
- 总长度
- 信号数量
- Signal 配置地址
- 是否固定长度
- 是否动态 DID
- 读写会话、安全等级
- IO Control 配置

# 实战

## 新增 DID `0xF1B0`，用于读取电机供电电压，期望返回 2 字节


你新增 DID `0xF1B0`，用于读取电机供电电压，期望返回 2 字节。

配置：

```
DcmDspDidIdentifier = 0xF1B0
DcmDspDataByteSize  = 2
DcmDspDataType      = UINT8_N
DcmDspDataUsePort   = USE_DATA_SYNCH_CLIENT_SERVER
DcmDspDidByteOffset = 0

允许读取会话：
EXTENDED_DIAGNOSTIC_SESSION
```

RTE 已生成有效调用：

```
Rte_Call_Dcm_DataServices_DcmDspData_DID_0xF1B0_ReadData()
{
    return RE_DataServices_DID_0xF1B0_Read_func(Data);
}
```

Runnable：

```
Std_ReturnType RE_DataServices_DID_0xF1B0_Read_func(uint8 *Data)
{
    Data[0] = 0x12;
    Data[1] = 0x34;
    return E_OK;
}
```

测试仪上电后直接发送：

```
Tx: 22 F1 B0
Rx: 7F 22 31
```

规则：答案锁定；至少经历两次错误尝试才会揭露。

第 1 次诊断：你认为问题最可能在哪一层？你下一条准备发送什么诊断报文，或者检查哪个配置项？只给出一个判断和一个动作。


### 完整关系
DcmDspDid
├─→ DcmDspDidInfo
└─→ DcmDspDidSignal
      └─→ DcmDspData
### 创建 `DcmDspData_DID_0xF1B0`
数据长度：2 字节
数据形式：字节数组
访问方式：同步 Client/Server
不做 DCM 字节序转换
不使用 ConditionCheckRead
![](assets/2026.07.28%20DID诊断配置以及开发/file-20260729104253623.png)
- `UINT8_N`：表示不定元素数形式的 `uint8` 数组，适合把 DID 数据当原始字节流传递。
- `ByteSize = 2`：固定该数据元素占 2 字节，DCM 据此计算响应长度。
- `USE_DATA_SYNCH_CLIENT_SERVER`：DCM 作为 Client，通过 RTE 同步调用应用 SWC 的 `ReadData` Operation。
- **`OPAQUE`：DCM 不进行大小端转换，Runnable 写入 `Data[0]`、`Data[1]` 的顺序就是总线返回顺序**。
- `ConditionCheckReadFncUsed = false`：读取前不额外调用条件检查接口，但会话和安全权限仍由 `DcmDspDidInfo` 检查。
- `ReadFnc` 留空是正常的：因为这里选择了 Client/Server，后续通过生成的 R-Port、Connector 和 Runnable 完成调用，不使用手填的直接 C 函数。

```

需求：

允许 Default Session
允许 Extended Session
不允许 Programming Session
不要求 SecurityAccess
不是动态 DID
```

</mark>



|子容器|对应服务|
|---|---|
|`DcmDspDidRead`|`0x22 ReadDataByIdentifier`|
|`DcmDspDidWrite`|`0x2E WriteDataByIdentifier`|
|`DcmDspDidControl`|`0x2F InputOutputControlByIdentifier`|
只读 DID 不应该创建空的 Write/Control 配置。因为一旦存在，生成器可能：
- 生成 `WriteData` 或 IO Control Operation；
- 生成额外的 R-Port 接口；
- 把会话和安全等级写入权限表；
- 要求应用 SWC 提供相应 Runnable；
- 使本应拒绝的服务进入处理路径。
保留 `DcmDspDidRead` 并引用 Default 和 Extended 后，生成代码会形成读取会话掩码。当前工程通常表现为：
0 x 5 uL  /* Default + Extended */
**安全等级列表为空，在当前工具生成逻辑中通常表示读取不要求解锁；但最终权限仍然是两级交集：**
0 x 22 服务级权限 ∩ 当前 DID 读取权限
`DcmDspDidDynamicallyDefined = false` 表示它是编译期静态 DID：
- 编号固定进入 `Dcm_DIDConfig[]`；
- `0x22` 通过静态表查找；
- 不依赖 `0x2C` 在运行时创建。

### 建立 DID 与 Data 的关联


![](assets/2026.07.28%20DID诊断配置以及开发/file-20260729111720911.png)![](assets/2026.07.28%20DID诊断配置以及开发/file-20260729111852833.png)
`DcmDspDidIdentifier = 0xF1B0`

DCM 收到：

```
22 F1 B0
```

后，会把请求中的 `F1 B0` 组合成 16 位数值 `0xF1B0`，然后在生成的 `Dcm_DIDConfig[]` 中查找它。

`DcmDspDidUsePort = USE_DATA_ELEMENT_SPECIFIC_INTERFACES`

表示这个 DID 的每个 Data 元素使用自己专属的接口。结合 Data 中的：

```
USE_DATA_SYNCH_CLIENT_SERVER
```

生成器会创建类似：

```
DataServices_DcmDspData_DID_0xF1B0
└─ ReadData
```

`DcmRbAtomicSenderReceiverCommunication = false`

这里不是 Atomic Sender/Receiver 方案，而是普通的、按 Data 元素访问的同步 Client/Server 调用。

`DcmDspDidInfoRef = DcmDspDidInfo_DID_0xF1B0`

把 DID 编号和访问权限绑定起来。运行时找到 `0xF1B0` 后，DCM 会用这个 Info 检查 Default/Extended 会话。

Signal 配置也正确：

```
ByteOffset = 0
DataRef    = DcmDspData_DID_0xF1B0
```

它表示 2 字节数据从 DID 数据区第 0 字节开始：

```
响应：62 F1 B0 12 34
                 ↑  ↑
Offset 0 ────────┘  │
Offset 1 ───────────┘
```

`DcmDspDidSize` 留空没有问题。当前 DID 是固定长度，工具可以从 Signal 引用的 `DcmDspDataByteSize = 2` 推导总长度：

```
TotalByteSize = max(ByteOffset + DataByteSize)
              = 0 + 2
              = 2
```

`DcmDspDidDataPos` 也可以留空；当前使用按字节排列，`DcmDspDidByteOffset` 已经足够。

```

这只是可维护性建议，不影响功能。

### 创建 Runnable 和 Event

![](assets/2026.07.28%20DID诊断配置以及开发/file-20260729134239516.png)

![](assets/2026.07.28%20DID诊断配置以及开发/file-20260729135216974.png)
- `OperationInvokedEvent` 是 Client/Server 接口服务端的触发事件。
- `Event Properties = ReadData` 指定是哪个接口操作触发事件。
- `Event Source` 指定这个操作属于哪个 P-Port。
- `Start Runnable Entity` 指定调用 `ReadData` 时运行哪个 Runnable。
- Runnable 的 `Function Name` 最终决定生成代码调用哪个 C 函数。
- 因此，将来 DCM 执行：
- 
```
- Rte_Call_DataServices_DcmDspData_DID_0xF1B0_ReadData(Data);
```
- 
- RTE 应该把它路由到：
- 
```
- RE_DataServices_DID_0xF1B0_Read_func(Data);
```

有一个问题，我之前在 ECU navigator 中的 Dcm 中修改的 F 1 B 0 的 DID,也会在 AR_Explorer 中产生 R-PORT 吗
会。你当前工程里，ECU Navigator 中的 F 1 B 0 配置已经让 Dcm Generator 产生了对应的 R-Port。

但要准确理解：不是 `DcmDspDidIdentifier = 0xF1B0` 单独产生 R-Port，而是这项配置决定的：

```
DcmDspDataUsePort = USE_DATA_SYNCH_CLIENT_SERVER
```

生成关系如下：

```
ECU Navigator：Dcm BSW配置
│
├─ DcmDspDid：定义0xF1B0及访问权限
├─ DcmDspDidSignal：把DID关联到Data
└─ DcmDspData
   └─ UsePort = USE_DATA_SYNCH_CLIENT_SERVER
             │
             ▼ Dcm Generate
Dcm_Cfg_SWCD.arxml
├─ ClientServerInterface
│  └─ DataServices_DcmDspData_DID_0xF1B0
│     └─ ReadData(Data[2])
├─ Dcm的R-Port
│  └─ DataServices_DcmDspData_DID_0xF1B0
└─ SynchronousServerCallPoint
   └─ ReadData
             │
             ▼
AR Explorer显示这些生成对象
```

当前工程的实际证据：

- Dcm 的 R-Port：[Dcm_Cfg_SWCD.arxml (line 192)](E:\\github\\ECAS_qirui_Single_Chamber\\BasicSoftware\\ecu_config\\bsw\\gen\\swcd\\Dcm_Cfg_SWCD.arxml:192)
- 同步 `ReadData` 调用点：[Dcm_Cfg_SWCD.arxml (line 1130)](E:\\github\\ECAS_qirui_Single_Chamber\\BasicSoftware\\ecu_config\\bsw\\gen\\swcd\\Dcm_Cfg_SWCD.arxml:1130)
- 生成的 Client/Server Interface：[Dcm_Cfg_SWCD.arxml (line 5800)](E:\\github\\ECAS_qirui_Single_Chamber\\BasicSoftware\\ecu_config\\bsw\\gen\\swcd\\Dcm_Cfg_SWCD.arxml:5800)

一个关键区别：

- ECU Navigator 负责编辑 Dcm 的 ECUC/BSW 配置。
- Dcm Generator 根据配置生成 `Dcm_Cfg_SWCD.arxml`。
- AR Explorer 主要是读取并展示生成的 SWC、端口和接口，不是 AR Explorer 自己凭空创建 R-Port。

如果只修改配置但没有重新执行 Dcm Generate、刷新或重新加载模型，AR Explorer 里可能暂时看不到新 R-Port。

另外，如果将 `DcmDspDataUsePort` 改成直接函数方式，例如 `USE_DATA_SYNCH_FNC`，生成器通常会采用回调函数，而不是生成现在这种 Client/Server R-Port。因此，“有没有 R-Port”主要由 `DcmDspDataUsePort` 决定。![](assets/2026.07.28%20DID诊断配置以及开发/file-20260729142656784.png)
