# NM / CanNm 工程配置说明

> 工程：`E:\github\ECAS_qirui_Single_Chamber`  
> 依据：当前工程 ARXML、生成代码、`NmUT`/`ExeMgrUT` 示例代码、RTE 生成结果、有道云笔记中“网络管理 / CanNm / NM 报文 / CBV / PN / 唤醒”相关内容。  
> 本文中心：解释当前工程的 `Nm + CanNm + ComM + EcuM/CanSM/CanIf` 如何共同完成 CAN 网络唤醒、保持、释放和休眠，并给出 ISOLAR 配置项含义、当前工程值、调试时应该看哪里。

## 1. 这篇文章想解决什么问题

这篇文章不是单纯介绍 AUTOSAR NM 标准，而是解决当前工程里的几个实际问题：

1. ISOLAR 里 `Nm`、`CanNm`、`ComM` 的配置项太多，不知道每个配置项影响什么。
2. 当前工程到底是哪个 NM 通道、哪个 Tx/Rx ID、哪个 ComM User、哪些定时器值，经常容易和别的工程混淆。
3. 应用层变量、RTE 端口、ComM 请求、EcuM 唤醒、CanNm 状态机之间的关系不清楚，导致调试时只盯着某一个模块。
4. 有道云笔记里关于一帧/两帧唤醒、CBV、PNC、诊断唤醒的内容很多，但需要按工程问题重新归类，而不是堆概念。

## 2. 如何解决

本文按 4 条线整理：

| 线索 | 关注点 | 当前工程里的抓手 |
|---|---|---|
| 应用请求线 | 谁请求 FullCom，谁释放 NoCom | `ComM_RequestComMode()`、`EcuM_CheckWakeup()`、`NmUT` 测试变量 |
| NM 状态线 | RMS/NOS/RSS/PBSM/BSM 如何跳转 | `Nm_StateChangeIndication()`、`CanNm_GetState()` |
| NM 报文线 | Tx/Rx NM PDU、NID、CBV、UserData | Tx `0x60B`、Rx `0x616`、NID byte0、CBV byte1 |
| 硬件唤醒线 | Transceiver/Controller/CanIf/EcuM 是否让 CAN 可收发 | `CanIf_CheckWakeup()`、`CanTrcv` wakeup reason、EcuM wakeup source |

## 3. 难点在哪里

- `Nm` 是接口层，`CanNm` 是 CAN 总线实现层，`ComM` 才是应用请求通信模式的入口。把三者混在一起看，很容易误判。
- 被动唤醒时，第一帧 CAN/NM 报文可能只唤醒 Transceiver/SBC/MCU，软件栈未必已经能处理这帧。
- 本工程 `ComM` 配了 PNC，`CanNmGlobalPnSupport` 也是 `true`，但当前 CanNm 通道 `CanNmPnEnabled=false`，所以不能直接按完整 PNC 过滤主线分析。
- `NmUT.c` 里有测试变量和 RTE 端口，但请求/释放相关 RTE 写当前是注释状态，`PP_NmState` 生成结果也是未连接空 API。调试时只改 `Nm_Test[0].request_b` 不等于真的请求了 ComM。

## 4. 当前工程结论

当前工程主线是普通 CAN NM 通道，带快发配置，不是 Passive Node，也不是当前通道启用 PNC 过滤的节点。

### 5.1 NmGlobalFeatures

`NmGlobalFeatures` 控制 Nm Interface 层对外开放哪些能力。它不直接决定 CAN ID 和发送周期，但会影响回调、user data、通信控制等 Nm 层行为。

| 配置项 | 当前值 | 含义 | 当前工程判断 |
|---|---:|---|---|
| `NmUserDataEnabled` | `true` | Nm 层允许 user data API | 可以通过 `Nm_GetUserData()` / `Nm_SetUserData()` 路径处理 NM user data |
| `NmComControlEnabled` | `true` | 允许 Nm 通信控制 API | 可支持 `Nm_EnableCommunication()` / `Nm_DisableCommunication()` 这类控制 |
| `NmPduRxIndicationEnabled` | `true` | 收到 NM PDU 后通知上层回调 | `Nm_RxIndicationCallback()` 会被挂入回调表 |

| `NmRemoteSleepIndEnabled` | `false` | 远端睡眠指示功能 | 不把 Remote Sleep 当主线排查 |
| `NmBusSynchronizationEnabled` | `false` | 总线同步请求 | 本工程不走 Bus Synchronization 主线 |
| `NmCoordinatorSupportEnabled` | `false` | NM Coordinator 支持 | 当前不是协调器网络管理主线 |
| `NmCoordinatorSyncSupport` | `false` | Coordinator 同步支持 | 不做同步协调睡眠分析 |

## 7. 当前代码里的实际链路

### 7.1 `NmUT` 不是完整的请求控制器

`NmUT.c` 中有测试变量：

```c
Nm_Test_t Nm_Test[NM_NUMBER_OF_CHANNELS];
uint8 Trggr_RepeatState = 0;
```

`request_b` / `release_b` 分支保留了注释意图：

```c
/* S/R to request COMM_FULL_COMM mode by ExeMgrUT */
//Rte_Write_PP_NmState_uint8(APP_READY_FOR_NM_REQUEST);

/* S/R to request COMM_NO_COMM mode by ExeMgrUT */
//Rte_Write_PP_NmState_uint8(APP_READY_FOR_NM_RELEASE);
```

但是当前工程里这两行是注释状态，且 RTE 生成日志显示 `PP_NmState` 未连接，`Rte_Write_PP_NmState_uint8()` 是空实现。因此：

- 只把 `Nm_Test[0].request_b = TRUE`，不会真正请求 ComM FullCom。
- 只把 `Nm_Test[0].release_b = TRUE`，也不会真正释放 ComM NoCom。
- `NmUT` 更适合做 Nm 回调、user data、Repeat Message 的测试观察点。

`NmUT` 的 RTE Client/Server 端口已经生成了 ComM API 宏：

```c
Rte_Call_UR_ComMUser_Can_Network_ETAS_Channel_RequestComMode(ComMode)
```

它最终映射到：

```c
ComM_RequestComMode(0, ComMode)
```

但当前 `NmUT.c` 没有实际调用这个宏。

### 7.2 `NmUT` 的接收和 user data 行为

收到 NM PDU 后，Nm 回调会置位：

```c
Nm_Test[NetworkHandle].IsNmReceived = TRUE;
```

`RE_NmUT_func()` 看到该标志后调用：

```c
Nm_GetUserData(index_chanel, Nm_Test[index_chanel].nm_rx_data);
```

注意：当前代码没有清掉 `IsNmReceived`，清标志那行也是注释：

```c
//Nm_Test[index_chanel].IsNmReceived = 0;
```

`Nm_StateChangeIndication()` 里当前使用直接 API 写 user data：

```c
Nm_SetUserData(NetworkHandle, Nm_Test[NetworkHandle].nm_tx_data);
```

这和当前配置一致：`CanNmUserDataEnabled=true`，但 `CanNmComUserDataSupport=false`，所以不要按 COM signal user data 主线分析。

### 7.3 `ExeMgrUT` 对 NM 接收的消费

`ExeMgrUT` 会读取 `Nm_Test[0].IsNmReceived`：

```c
else if(TRUE == Nm_Test[0].IsNmReceived)
{
    RxLostCnt = 0u;
    Nm_Test[0].IsNmReceived = FALSE;
    WakeupSrc = EcuMConf_EcuMWakeupSource_ECUM_WKSOURCE_INTERNAL_CAN;
}
```

这说明 `Nm_RxIndicationCallback()` 不只是测试观察点，也会影响 `ExeMgrUT` 的内部 CAN 唤醒源判断。

### 7.4 EcuM 唤醒链路

当前工程可见的直接 FullCom 请求点在：

```c
void EcuM_CheckWakeup(EcuM_WakeupSourceType wakeupSource)
{
    ComM_RequestComMode(0, COMM_FULL_COMMUNICATION);
    CanIf_CheckWakeup(wakeupSource);
}
```

调试总线唤醒时要特别注意：这里先请求 `ComM_RequestComMode(0, COMM_FULL_COMMUNICATION)`，再调用 `CanIf_CheckWakeup()`。因此如果看到唤醒后 ComM 被拉到 FullCom，要把 EcuM wakeup path 也纳入分析，不要只查应用 SWC。

## 9. 推荐调试路径

### 9.1 主动请求网络后不发 `0x60B`

按这个顺序排查：

1. 是否真的调用了 `ComM_RequestComMode(0, COMM_FULL_COMMUNICATION)`，不要只看 `Nm_Test[0].request_b`。
2. `ComMUser_Can_Network_Channel_Can_Network` 是否绑定到 `Can_Network_Channel_Can_Network`。
3. `ComMNmVariant` 是否为 `FULL`。
4. `NmChannelConfig` 是否引用同一个 ComM channel。
5. `Nm_NetworkRequest()` 是否被调用。
6. `CanNm_NetworkRequest()` 是否被调用。
7. `CanSM_RequestComMode()` 是否让 CAN controller / CanIf / CanTrcv 到可收发状态。
8. `CanIf` PDU mode 是否允许 Tx。
9. CANoe/CANalyzer 上是否看到 `0x60B`，唤醒初期是否有 20ms 快发。

### 9.2 收到 `0x616` 后没有被动唤醒

按这个顺序排查：

1. CanTrcv 是否已经唤醒并进入 Normal。
2. CAN Controller 是否 STARTED。
3. CanIf 是否收到 `NM_Rx_0x616_ETAS_CAN_IN`。
4. `CanNm_RxIndication()` 是否进来。
5. `Nm_RxIndicationCallback()` 是否置位 `Nm_Test[0].IsNmReceived`。
6. `ExeMgrUT` 是否消费该标志并设置 `ECUM_WKSOURCE_INTERNAL_CAN`。
7. 若第一帧没进软件栈，连续发送多帧 NM，区分硬件唤醒帧和软件可处理帧。

### 9.3 释放网络后不睡眠

优先看：

1. 是否还有 ComM User 保持 FullCom。
2. DCM 是否 ActiveDiagnostic 或仍在非默认会话。
3. 是否仍收到外部 `0x616`，刷新了 NM Timeout。
4. `CanNmTimeoutTime = 3.0s` 和 `CanNmWaitBusSleepTime = 4.0s` 是否还没到。
5. BswM/ComM 是否允许进入 NoCom。
6. `Nm_StateChangeIndication()` 是否出现 `PREPARE_BUS_SLEEP -> BUS_SLEEP`。

### 9.4 网络太快睡眠

常见原因：

- 没有实际 ComM FullCom 请求。
- 请求只经过 `NmUT.request_b`，但当前代码没有调用 ComM。
- 外部没有周期 NM，当前节点也释放了网络。
- ComM User/Channel/Nm Channel 引用错。
- 只看到 EcuM/MCU 被唤醒，但 CanNm 没进入 Network Mode。

### 9.5 Repeat Message Request 无效

检查：

- 当前状态是否在 RSS 或 NOS，而不是 Bus Sleep / Prepare Bus Sleep。
- `CanNmNodeDetectionEnabled = true` 是否生效。
- `Nm_RepeatMessageRequest(0)` 的通道号是否正确。当前单通道时 0 合理，多通道后不能硬编码。
- CAN 上 CBV bit0 是否符合预期。

## 11. 最终结论

当前工程的 NM 主线可以压缩成：

```text
EcuM/应用/诊断触发通信需求
  -> ComM User 0 请求 FULL / NO communication
  -> ComM channel: Can_Network_Channel_Can_Network
  -> CanSM/CanIf/CanTrcv 保证 CAN 可收发
  -> Nm Interface 转调 CanNm
  -> CanNm 通过 0x60B / 0x616 维护网络状态
  -> NmUT/ExeMgrUT 通过回调和标志观察 NM 接收与状态变化
```

调试时最先确认 3 件事：

1. `ComM_RequestComMode(0, COMM_FULL_COMMUNICATION)` 是否真的发生。
2. `0x60B` 是否按 `20ms * 20` 快发、再按 `1s` 周期发送。
3. 外部 `0x616` 是否真正进入 `CanNm_RxIndication()` 和 `Nm_RxIndicationCallback()`。

### 12.1 工程问题：主动唤醒和被动唤醒怎么区分

来源笔记：

- `Autosar网络管理：主动唤醒源被动唤醒源与网络主动唤醒被动唤醒的关系.clip`
- `Autosar网络关系：网络主动唤醒细细碎.clip`
- `Autosar网络管理：网络管理报文的收发与网络管理时间配置参数解析.clip`

归纳：

- 主动唤醒：本节点有通信需求，通常由 KL15、定时器、传感器、诊断、应用 User 等触发，软件上走 `ComM_RequestComMode()` / `CanNm_NetworkRequest()`。
- 被动唤醒：本节点收到其他节点 NM 报文或总线唤醒事件，软件上走 `CanNm_PassiveStartup()` 或 `Nm_NetworkStartIndication()` 相关路径。
- 当前工程 `CanNmPassiveModeEnabled=false`，所以本节点有主动发 NM 的能力。
- 当前工程 `CanNmImmediateNmTransmissions=20`，主动唤醒后应关注快发 NM。

### 12.2 工程问题：为什么一帧 NM 不一定能唤醒软件网络

来源笔记：

- `Autosar网络管理：一帧有效的网络管理报文是如何唤醒网络的？.clip`
- `Autosar网络管理：为什么需要2帧网络管理报文唤醒网络？.clip`
- `从CAN Transceiver角度，理解两帧网络管理报文唤醒网络的原理.clip`

归纳：

```text
第一帧 CAN/NM
  -> Transceiver/SBC/INH/电源唤醒
  -> MCU 上电或退出低功耗
  -> 软件初始化
  -> CanTrcv Normal
  -> CAN Controller STARTED
  -> CanIf/CanNm 初始化完成
  -> 后续 NM 才能被软件栈处理
```

因此第一帧可能只是硬件唤醒帧，不一定被 CanNm 软件处理到。当前工程排查被动唤醒时，要用连续 `0x616` 验证，不能只发一帧就判断 CanNm 失败。

### 12.3 工程问题：第一帧外发必须是 NM 吗

来源笔记：

- `Autosar网络管理：确保第一帧是网络管理报文方法.clip`
- `Autosar通信：网络管理报文和应用报文，谁先发？.clip`
- `Autosar网络管理：CanNM网络状态机真的全看懂了？.clip`

归纳：

- 主动唤醒节点通常希望第一帧是 NM，目的是先同步网段内其他节点的网络状态。
- 优先靠工具配置解决：CanNm 快发配置、BswM/CanSM/Com I-PDU Group 打开顺序、PDU 优先级。
- 不建议优先改 Can Driver/CanIf 静态代码去拦截应用报文。
- 当前工程已经配置 `20ms * 20` 的 NM 快发，测试时应看唤醒初期 `0x60B` 是否快发，而不是沿用旧结论“没有快发”。

### 12.4 工程问题：CBV 的 RMR/AWB/PNI 怎么看

来源笔记：

- `Autosar网络管理：网络管理报文CBV(Control Bit Vector)字节详解.clip`
- `Autosar网络管理：RepeatMessageRequestBit作用，你清楚吗？.clip`

归纳：

- RMR bit0：请求进入 Repeat Message State。当前 `CanNmNodeDetectionEnabled=true`，`Nm_RepeatMessageRequest(0)` 有意义。
- AWB bit4：主动唤醒标记。当前 `CanNmActiveWakeupBitEnabled=true`，主动唤醒测试要观察 bit4。
- PNI bit6：表示 NM PDU 包含 PN 信息。当前通道 `CanNmPnEnabled=false`，不要把 PNI/PNC 作为当前 CanNm 主线。

### 12.5 工程问题：诊断报文能不能唤醒网络

来源笔记：

- `Autosar网络管理：诊断报文能否唤醒网络？.clip`
- `诊断基础：不同会话(Session)，诊断报文如何维持网络状态？.clip`

归纳：

- 诊断报文能不能唤醒 ECU，取决于硬件 Transceiver/SBC 是否会因该帧唤醒，以及 EcuM 是否验证该唤醒源。
- 诊断报文不应被当作 NM PDU 去走 `CanNm_PassiveStartup()`。
- 软件上通常是 DCM 作为 ComM User，通过 `ComM_DCM_ActiveDiagnostic()` 请求 FullCom，再由 ComM/Nm/CanNm 进入网络。
- 当前工程如果网络不睡，要同时查 DCM 是否还保持 ActiveDiagnostic 或非默认会话。

### 12.6 工程问题：PN/PNC 和当前工程到底有什么关系

来源笔记：

- `Autosar网络管理：从CanNM模块看Partial Networking.clip`
- `Autosar PN网络管理：PNC信息的收发流程.clip`
- `Autosar网络管理：从ComM模块看Partial Networking.clip`
- `AUTOSAR PNC数据流分析.clip`

归纳：

- PN 的目的：不是让整网所有 ECU 同醒同睡，而是只唤醒相关 PNC 节点。
- PN 判断通常依赖 PNI bit、PN 信息区、PN filter mask、ERA/EIRA、ComM PNC 状态机。
- 当前工程 ComM 有 `ComMPnc_0`，CanNm 全局 PN 支持也开了，但当前 CanNm 通道 `CanNmPnEnabled=false`，`CANNM_PN_INFOLENGTH=0u`，所以不能按完整 PNC 过滤链路解释 `0x616/0x60B`。
- 如果后续要启用 PN，需要同时检查 CanNm、ComM、PduR、COM、BswM、CanTrcv 的 PN/PNC 链路，而不是只打开一个 CanNm 开关。

### 12.7 工程问题：EcuM/CanTrcv/CanIf 在唤醒里是什么关系

来源笔记：

- `从EcuM角度看唤醒源状态切换.clip`
- `Can Wakeup时序，简单点说（一）.clip`
- `TJA1145配置休眠唤醒.clip`
- `（节点唤醒==网络唤醒）？FALSETRUE；.clip`

归纳：

- ECU 上电或 MCU 醒来，不等于 CanNm 已进入 Network Mode。
- 硬件先发现唤醒事件，通常通过 `EcuM_SetWakeupEvent()` 或相关 callout 上报 EcuM。
- EcuM 要启动 wakeup sources，让 Transceiver/Controller 具备收发能力，再验证 wakeup source。
- 验证通过后才通知 ComM/BswM，让通信被允许。
- 当前工程 `EcuM_CheckWakeup()` 里直接请求 ComM FullCom 并调用 `CanIf_CheckWakeup()`，所以调试唤醒要看 EcuM callout 的工程实现，而不是只看 AUTOSAR 标准流程图。
