## 运行时 FCCU 导致复位

`MpuDiag_Record.state` 所在的 ECC 区域错误。

|项目|值|
|---|---|
|ERM SR 0| `0x0C000000`，SBC 1、NCE 1 均置位|
|ERM EAR 1| `0x20463E18` |
|FCCU NCF_S[0]| `0x04` |
|DCMROD 3| `0x01000000`，PRAM 1 _MULTI_ERR|
代码：
 启动代码看到 `FES.SW_FUNC` 后，跳过 `.Magic_Flag`。
- 如果这块内存原本 ECC 无效，软件复位后仍跳过，就不会被修复。
- CPU 读取、部分写入，甚至调试器自动刷新 Watch，都可能再次访问该故障区域。

修复方向：
冷启动／RAM 不可信 → 建立整块 ECC，旧记录作废
符合保留条件的暖复位 → 保留已有有效记录

### 我使用 int_Magic_Flag 这个地址段为什么会 ECC 校验失败

**软件复位后 ECC 仍坏**：当前启动路径保留了这块坏内存，复位不会自动修复它。


按这个顺序验证：

1. **断开调试器，真正断电再上电**，正常启动后用不复位、不写 RAM 的方式 Attach，检查 ECC 状态。
2. **触发 MPU 故障并软件复位**，确认记录保留、DTC 能上报。
![](assets/2026.09.08%20%20诊断调查表测试（五）/file-20260909110709065.png)![](assets/2026.09.08%20%20诊断调查表测试（五）/file-20260909110823921.png) 

修改成了，
- `DES.F_POR = 1`：初始化整段 SRAM，包含 `.Magic_Flag`。
- 非上电复位：沿用原逻辑，`SW_FUNC` 时保留 `.Magic_Flag`。
- POR 判断优先于 SW_FUNC

为什么产生了 ECC 错误呢？
SRAM 除了数据，还保存对应的 ECC 校验位。上电后，不能假设两者天然匹配；必须按芯片要求初始化，再读取。

冷上电 → 初始化记录区，建立有效 ECC
       → 程序正常运行
       → 发生 MPU 故障，写入故障记录
       → 软件复位，跳过记录区初始化
       → APP 读取记录并上报
跳过软件复位时的初始化，本身不会导致 ECC 错误。

```
Mcu_Init 会把复位原因清除。
```

| 调用                     | 当前代码的行为                                                |
| ---------------------- | ------------------------------------------------------ |
| `Mcu_Init()`           | 先将 FES 保存到 `FesResetStatus`，再清除硬件 FES；**没有清除 DES**     |
| `Mcu_GetResetReason()` | 将 DES 保存到 `DesResetStatus`，再清除硬件 DES，包括 POR；根据条件处理 FES |



### 正确的调试步骤

Down → Up → 停在复位入口 → Go /SingleCORE
                              ↓
                         命中断点
                              ↓
                       Go /SingleCORE
   注：0 x 0401408 是 boot 的首地址，0 x 45452 c 是 APP 运行的首地址。down up 后，停在了 boot 的首地址。Up 会复位目标；这套操作用于从复位入口调试，不等于真正断电上电。

#### 为什么有时候 down - up 点击上面的 go，就可以正常到断点，但是有时候就会 stopped at vector catch .
**这次已确认是“复位入口被调试器捕获”，当前现场没有 ECC/FCCU 报错。**

我通过 MCP 实际读到：

|项目|结果|
|---|---|
|PC| `0x00401408`，Boot 复位入口|
|FES| `0x20000000`，软件功能复位|
|FCCU、PRAM 1 故障状态|都为 `0` |
|CFSR、HFSR|都为 `0` |
|DEMCR 的复位捕获位|已开启，与勾选 `ResBreak` 一致|

所以这次停下来的机制是：

```
软件复位 → 进入 Boot 复位入口
         → 调试器的复位捕获生效
         → stopped at vector catch
```

**我随后执行了一次 MCP Go，程序正常到达 `RamInit（0x004545BE）`，没有再次回到复位入口，ECC/FCCU 状态仍为零。**

结合你描述的 **Down → Up**，<mark style="background: #FF5582A6;">这次现象符合 **Up 请求复位后，由 ResBreak 捕获停机**。[TRACE32 官方说明](https://www2.lauterbach.com/pdf/debugger_cortexm.pdf)</mark>

需要明确：我确认了停止机制和随后正常运行的结果；**尚未捕获最初是谁发出了软件复位，不能仅凭 `SW_FUNC` 断言来自 Boot 或 MPU。**此前把这种停机直接解释为 ECC 导致，过于笼统。

当前已替你运行到 **APP `RamInit` 断点**，CPU 保持停止，原断点设置已恢复。

#### 取消了 resbreak,还是会一样的现象

**<mark style="background: #FF5582A6;">找到原因了：取消 `ResBreak` 后，独立的“核心复位向量捕获”仍然开启。</mark>

刚通过 MCP 读到：

```
DEMCR = 0x010007F1
bit 0（VC_CORERESET）= 1 → 仍会在核心复位时停住
PC = 0x00401408
```

<mark style="background: #FF5582A6;">TrOnchip.Set MMERR OFF 用来自动关闭 MemManage Vector Catch。</mark>

TRACE 32 对这个捕获有单独的设置。请在底部命令栏执行：

```
TrOnchip.Set CORERESET OFF  
```

然后点击顶部 **Go**。这<mark style="background: #FF5582A6;">条命令只关闭复位向量捕获，保留其他异常捕获和你设置的断点。</mark>

```
SYStem.Option.PWRDWNRecover ON   调试接口失联后持续尝试重连
```


**关闭捕获不会自动恢复当前停机，也不会阻止 MCU 复位，所以还需要点击 Go。**这次 FCCU、PRAM 1、CFSR、HFSR 仍全部为零，当前没有 ECC 故障证据。

当前 MCP 没有修改 `TrOnchip` 设置的接口，因此这条命令需要你执行；我尚未替你关闭它。

如果从一上电开始就一直是正常的，不存在 BUS OFF，所以就会处在这样的状态，并没有报 DTC。这个需要更改。
但是我加了一个就是周期函数中调用的时候，设置 PASSED，但是 CanSM 还卡在 Bus-off 恢复检查，通信关闭没有完成。
CanSM_BusOff_Indicated_ab[lnetwork] != TRUE  接受关闭通信的条件

```
ECU 等待发送成功，完成 Bus-off 恢复
→ 通信没有恢复，Bus-off 标志不清除
→ 关闭通信的请求又被这个标志挡住
→ CanNm 已睡眠，但 ECU 没完成关断
```
