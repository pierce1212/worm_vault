| 所属对象          | 引用参数               | 指向的公共 PDU               |
| ------------- | ------------------ | ----------------------- |
| `RX_UdsRxPhy` | `CanTpRxNPduRef`   | 物理接收 PDU，`0x6D2`        |
| `RX_UdsRxPhy` | `CanTpTxFcNPduRef` | 物理发送 PDU，`0x6D3`        |
| `RX_UdsRxFnc` | `CanTpRxNPduRef`   | 功能接收 PDU，`0x7DF`        |
| `TX_UdsTxPhy` | `CanTpRxFcNPduRef` | **同一个物理接收 PDU，`0x6D2`** |

理解成 **2 个接收入口＋1 个发送出口**：

| 公共 PDU   | CAN ID  | 用来传什么                 | 針對  |
| -------- | ------- | --------------------- | --- |
| 物理接收 PDU | `0x6D2` | 接收诊断请求；接收诊断仪的流控帧 FC   |     |
| 功能接收 PDU | `0x7DF` | 接收功能寻址请求              |     |
| 物理发送 PDU | `0x6D3` | 发送诊断响应；发送 ECU 的流控帧 FC |     |
![](assets/2026.10.19%20autosar%20NM及CAN%20通讯测试报告bug修复/file-20261019112814334.png)

<mark style="background: #FF5582A6;">**图里实际只有 1 个 CanTp 通道。** 你红框圈出的，是这个通道下的**数据帧和流控帧的收发配置**。</mark>

**下面所有 Rx／Tx，都站在 ECU 的角度看。**

#### **为什么“接收”下面还有 Tx，“发送”下面还有 Rx？**

因为 CanTp 传输长报文时，需要接收方发送 **FC（Flow Control，流控帧）**，告诉发送方：“可以继续发，每批发多少帧、间隔多长”。CanTp 负责这种分段、流控和重组。[AUTOSAR CanTp 规范](https://autosar.org/fileadmin/standards/R4.0.3/CP/AUTOSAR_SWS_CANTransportLayer.pdf)

对应你圈出的配置：

|所属对象|红框中的配置|ECU 用它做什么|
|---|---|---|
|物理请求接收 `RX_UdsRxPhy` | `CanTpRxNPdu` |**接收请求数据帧**|
|物理请求接收 `RX_UdsRxPhy` | `CanTpTxFcNPdu` |收到多帧请求时，**发送流控帧**|
|功能请求接收 `RX_UdsRxFnc` | `CanTpRxNPdu` |**接收功能寻址请求**|
|响应发送 `TX_UdsTxPhy` | `CanTpTxNPdu` |**发送响应数据帧**|
|响应发送 `TX_UdsTxPhy` | `CanTpRxFcNPdu` |发送多帧响应时，**接收诊断仪的流控帧**|

结合你工程里的实际 CAN ID，看两个过程就清楚了。

**① 诊断仪发送一个长请求：**

```
诊断仪                                  ECU
   ── 首帧 FF，0x6D2 ──────────────────→  CanTpRxNPdu
   ←─ 流控 FC，0x6D3 ──────────────────   CanTpTxFcNPdu
   ── 连续帧 CF，0x6D2 ────────────────→  CanTpRxNPdu
```

<mark style="background: #FF5582A6;">**所以，接收长请求时，ECU 也需要向外发送流控帧。**
</mark>
**② ECU 发送一个长响应：**

```
诊断仪                                  ECU
   ←─ 首帧 FF，0x6D3 ──────────────────   CanTpTxNPdu
   ── 流控 FC，0x6D2 ──────────────────→  CanTpRxFcNPdu
   ←─ 连续帧 CF，0x6D3 ────────────────   CanTpTxNPdu
```

所以，**发送长响应时，ECU 也需要接收诊断仪的流控帧。**

#### CANtp 具体参数的配置

| **CanTpNcr**                 | `0.15`                 | 进入等待下一帧 CF 的状态后，最多等 **150 ms**；超时则终止本次接收                                                |

| **CanTpRxPaddingActivation** | `CANTP_ON`             | 启用接收填充规则，要求报文满足对应的填充长度规则；有效诊断数据长度仍由协议字段指出                                               |

### EcuC 的真正作用
![](assets/2026.10.19%20autosar%20NM及CAN%20通讯测试报告bug修复/file-20261019135213063.png)

**EcuC 这里是整个 ECU 的“公共 PDU 清单”，供 CanIf、CanTp、PduR、Dcm、Com 等模块引用。** 每一项描述报文在某两个模块之间传递时使用的 PDU 对象。

| 诊断方向   | CanIf ↔ CanTp：CAN 帧层        | CanTp ↔ PduR：诊断数据层    | PduR ↔ Dcm：诊断数据层    |
| ------ | --------------------------- | --------------------- | ------------------- |
| 接收功能请求 | `NPdu_UdsRxFnc_CanIf2CanTp` | `UdsRxFnc_CanTp2PduR` | `UdsRxFnc_PduR2Dcm` |
| 接收物理请求 | `NPdu_UdsRxPhy_CanIf2CanTp` | `UdsRxPhy_CanTp2PduR` | `UdsRxPhy_PduR2Dcm` |
| 发送响应   | `NPdu_UdsTxPhy_CanTp2CanIf` | `UdsTxPhy_PduR2CanTp` | `UdsTxPhy_Dcm2PduR` |
CAN 总线
   │
 CanIf
   │  NPdu_UdsRxPhy_CanIf 2 CanTp…
   ▼
 CanTp     ← 接收 CAN 帧，完成多帧重组
   │  UdsRxPhy_CanTp 2 PduR…
   ▼
 PduR      ← 按配置把诊断数据转给 Dcm
   │  UdsRxPhy_PduR 2 Dcm…
   ▼
 Dcm       ← 解析、执行 UDS 服务

## 常见问题：如果只有函数指针，如何查看调用关系

**不用先看调试器。最快的方法是：找到“函数指针成员名”，再查它的引用。** 只搜索函数名，往往只能找到注册地址的位置。


**① 先确定地址存到了哪个成员**

[Nm_Cfg.c (line 129)](/E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Nm/Nm_Cfg.c:129)：

```
const Nm_UserCallbackType_tst Nm_UserCallbacks = {
    &Nm_RxIndicationCallback,
    &TestNm_RemoteSleepCancellation,
    &TestNm_RemoteSleepIndication,
    &Nm_StateChangeIndication
};
```

这是按结构体成员顺序初始化。查看 [Nm_Priv.h (line 635)](/E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Nm/api/Nm_Priv.h:635)，第四个成员是：

```
void (*StateChangeInd)(
    NetworkHandleType NetworkHandle,
    Nm_StateType nmPreviousState,
    Nm_StateType nmCurrentState);
```

因此，这次初始化建立了关系：

```
Nm_UserCallbacks.StateChangeInd
              ↓ 保存的函数地址
Nm_StateChangeIndication
```

**② 全局搜索 `StateChangeInd`，就能找到真正调用的位置**

在 VS Code 按 **Ctrl＋Shift＋F**，搜索：

```
StateChangeInd
```

会找到 [Nm_Extensions.c (line 211)](/E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Nm/src/Nm_Extensions.c:211)：

```
UserCallback_pcst = &Nm_UserCallbacks;

if (UserCallback_pcst->StateChangeInd != NULL_PTR)
{
    (*UserCallback_pcst->StateChangeInd)(
        nmNetworkHandle, nmPreviousState, nmCurrentState);
}
```

**最后这行才是在调用函数。** 按当前注册表，它实际调用的就是：

```
Nm_StateChangeIndication(
    nmNetworkHandle, nmPreviousState, nmCurrentState);
```

**③ 再往上追当前所在函数**

上面代码属于 `Nm_StateChangeNotification()`。继续搜索这个名字，就能找到 CanNm 的各个状态切换调用点，例如 [CanNm_Inl.h (line 1042)](/E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/CanNm/api/CanNm_Inl.h:1042)：

```
CanNm_ReadySleepToNO()
    → Nm_StateChangeNotification()
        → 通过 StateChangeInd 函数指针
            → Nm_StateChangeIndication()
```

以后遇到这种情况，就沿着：

```
函数地址注册 → 结构体成员名 → 搜索成员的调用 → 向上追调用者
```

编辑器索引正常时，可在成员 `StateChangeInd` 上按 **Shift＋F 12 查找引用**，通常比全文搜索更快。

**源码追踪用来找可能的调用关系；调用栈用来确认“这一次运行实际走了哪条路径”。** 你现在这个问题，静态搜索就能查清楚。
