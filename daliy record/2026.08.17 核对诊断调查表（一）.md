`C1E4047` 是面向人的标准故障码表示，共 7 个字符。
故障类别 | 第二字符 | 第三字符
C = 01   | 1 = 01   | E = 1110
对象名也遵循工程现有规则，使用 DEM 中实际的三字节数值，而不是七字符显示形式。

### 第 2 关：属性配置现场

现有 DTC 属性模板中可以看到：

```
DemImmediateNvStorage             = true
DemAgingAllowed                   = true
DemDTCSignificance                = DEM_EVENT_SIGNIFICANCE_FAULT
DemMaxNumberFreezeFrameRecords    = 2
DemAgingCycleCounterThreshold     = 3
DemDTCPriority                    = 2
DemAgingCycleRef                  = DemOpCycle_POWER
DemMemoryDestinationRef           = DemPrimaryMemory
```

而 `C1E4047` 的需求是：

```
Level：3
Clear DTC：Aging 40 times Self Clean
           UDS 14 FF FF FF clear
恢复条件：ECU 重启且故障消失
```
![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837499.png)
- `DemDTCPriority` 是事件存储区满时的置换优先级，数值越小优先级越高；它不是需求表中的故障等级。
- 当前工程原有 156 个 DTC 全部使用 `DemDTCPriority=2`，没有证据支持把 `Level=3` 直接映射为 `3`。所以本项目沿用基线值 `2`。
- 原有 DTC 的 `DemImmediateNvStorage` 全部为 `true`。Watchdog 故障可能紧接着导致复位，因此应立即触发持久化请求；配置为 `false` 可能使故障只存在于 RAM，复位后无法通过 `19` 服务读到。实际能否在复位前写完，后续还要验证 NvM 时序。
- `DEM_EVENT_SIGNIFICANCE_FAULT` **<mark style="background: #ADCCFFA6;">表示这是故障事件，而非仅用于统计发生次数的事件。</mark>**
  TFSLC = Test Failed Since Last Clear
      = 自上次清除后测试曾失败


`DemOpCycle_POWER` 属性为空并不代表没有周期。它定义的是一个“周期身份”，不是周期时长；真正的一次周期由运行时接口启动、结束或重启。

![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837401.png)
<mark style="background: #FF5582A6;">因此配置虽然合法，却不能证明老化实际会推进。这是后续必须上车或沿调用链验证的风险。</mark>

![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837139.png)


### 第 3 关：事件到底是谁上报

现有事件模板是：

```
SHORT-NAME                       DTC_0x411001_Event
DemEventAvailable                true
DemEventConfirmationThreshold    1
DemEventKind                     DEM_EVENT_KIND_SWC
```

现在准备创建：

```
DTC_0x5E4047_Event
```

Watchdog 故障来源有两个：

```
1. WdgM 发现程序周期或程序流异常
2. 读取到外部看门狗异常故障位
```

![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837481.png)

WdgM Alive/Deadline/Logical supervision
  → Global Status = STOPPED
  → WDGM_E_SUPERVISION
  → DTC _0 x 5 E 4047_ Event

外部看门狗异常位
  → 独立的硬件状态监控
  → 同一个 DTC _0 x 5 E 4047_ Event
  所以不要创建两个事件再依赖 DEM 把它们组合成同一个 DTC。应保持一个事件。外部看门狗监控如果也直接上报同一 EventId，必须明确上报所有权，避免一个来源报 `PASSED`、另一个来源报 `FAILED`。本需求要求重启后才恢复，因此本周期内不应随意报 `PASSED`。

### 第 5 关：计数边界

10 ms Runnable 中设计两个计数器：

```
awake：3s
battery recovery：0.5s
```

![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837474.png)
<mark style="background: #FF5582A6;">
**WdgM 已经完成监督判定并报告最终 `FAILED` **，所以 DEM 不需要保存半完成的去抖过程。</mark>

| WdgM/监控器上报  | DEM Counter 处理           |
| ----------- | ------------------------ |
| `PREFAILED` | 按 `IncrementStepSize` 增加 |
| `PREPASSED` | 按 `DecrementStepSize` 减少 |
| `FAILED`    | 直接设为 `FailedThreshold`   |
| `PASSED`    | 直接设为 `PassedThreshold`   |
|             |                          |
WdgM 只在 Global Status 首次进入 `STOPPED` 时报告一次 `FAILED`。后续不会因为 `awake3s=true` 自动再报一次。因此，2.5 秒发生的故障被忽略是需求预置条件带来的预期结果。

解决办法是：
-  MPU 故障必须走功能复位，不能沿默认 `OFF` 目标正常下电。
- `MpuDiag_Record` 必须放入真正的 NOINIT/保留段，而不是当前 cleared 段。



Magic_Flag 段：512 个字节，boot 使用，不会被启动清零。（其他的段会被 init_data_bss 清除）
FES 复位源：
![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837165.png)


S 32 K 324 的 Functional Reset 和 Destructive Reset 不是两个不同的“Reset Domain”。S 32 K 3 只有一个主复位域 Main Reset Domain（RD 0）；POR、Destructive Reset、Functional Reset 是这个主复位域里的三种 Chip Reset Sequence。

### core 0 的代码断点停不下来是为什么？

注入故障的后， core 0 确实发生了功能性复位，但是的首地址是 0 x 401408
![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837097.png)
![](assets/2026.08.17%20核对诊断调查表（一）/file-20260910172837082.png)
Core 0 经过 `0x004E1D98` 时，Core 0 的 FPB 硬件断点还没有恢复；现在 Break.List 显示已安装，只能证明“当前已安装”，不能证明 Core 0 经过该地址时已经安装。

`0x00401408` 是 Boot；真正导致断点错过的是 Boot 中间还有一次软件复位，Core 0 的 ONCHIP 断点被第二次清掉。

```
→ Core0 FPB调试寄存器失效/需要恢复
→ Core0立即从Reset_Handler启动
→ TRACE32检测复位并重新配置断点
Core0启动速度比TRACE32恢复断点更快，因此可能出现：

Core0已经执行过EcuM_Init
→ TRACE32才重新写入FPB断点
→ Break.List现在显示ONCHIP-I
→ 但已经错过这次执行
```

ASIL B Application”不等于 AUTOSAR 中的“Trusted OS-Application：
AUTOSAR 的 Trusted 表示可以拥有特权和较少限制，不表示“安全等级更高”。为了故障隔离，ASIL B 应用通常更适合以受保护的 Non-Trusted OS-Application 运行；确实需要特权的 MCAL 操作，放入尽量小的 Trusted BSW 服务，通过受控接口调用。AUTOSAR 对 Trusted 和 Non-Trusted 应用的区别也明确强调了内存、OS API 和特权模式限制。

正确的开发顺序：
安全需求与 ASIL 分区
→ OS-Application 划分
→ Task/ISR 归属
→ 链接段划分
→ MPU/XRDC 权限
→ 故障源与目标地址识别
→ 安全反应
→ 跨复位 DTC 记录
→ QM 越权故障注入测试
最**<mark style="background: #FF5582A6;">终还需要依据项目的 Safety Concept、DFA 以及 NXP S 32 K 3 Safety Manual 确认具体保护强度和诊断覆盖率。</mark>**
