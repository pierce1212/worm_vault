

**Zephyr（读作“泽弗”）是一套专门运行在 MCU、嵌入式控制器上的开源实时操作系统 RTOS。**

你可以把它理解成：

> **Zephyr = 实时内核 + 标准驱动框架 + 硬件配置系统 + 通信协议栈 + 文件系统 + 调试测试工具。**

它由 Linux Foundation 托管，主要面向资源受限的 MCU、传感器、控制器、物联网和可穿戴设备，不是运行在电脑上的桌面操作系统。([Zephyr Project](https://www.zephyrproject.org/learn-about/?utm_source=chatgpt.com "About the Zephyr Project – Zephyr Project"))

## 最简单的例子

假设你用 S 32 K、STM 32 或 nRF 芯片做一个控制器，需要同时完成：

```text
任务1：每10 ms读取传感器
任务2：接收CAN报文
任务3：执行控制算法
任务4：保存故障码
任务5：通过串口输出日志
任务6：执行OTA升级
```

裸机程序通常要自己处理：

- 主循环
    
- 中断
    
- 定时调度
    
- 任务优先级
    
- 缓冲区
    
- 驱动接口
    
- 线程同步
    

使用 Zephyr 后，可以创建不同优先级的线程：

```c
void control_task(void)
{
    while (1) {
        read_sensor();
        run_control_algorithm();
        k_msleep(10);
    }
}
```

Zephyr 内核负责决定任务什么时候运行、谁先运行、任务之间如何通信。

## 它不只是一个“任务调度器”

这是 Zephyr 和 FreeRTOS 给人的最大区别。

Zephyr 自带或统一管理许多组件：

```text
Zephyr
├── 实时调度内核
├── 线程、信号量、消息队列、定时器
├── GPIO / UART / SPI / I²C / CAN 驱动框架
├── Bluetooth / TCP-IP / USB
├── 文件系统和 Flash 管理
├── 日志与 Shell
├── 电源管理
├── OTA / MCUboot
├── 设备树 Devicetree
├── Kconfig 配置系统
└── 自动化测试框架
```

官方将其定位为小内核基础上的完整嵌入式平台，并提供大量子系统、服务和板卡支持。([Zephyr Project Documentation](https://docs.zephyrproject.org/latest/index.html?utm_source=chatgpt.com "Zephyr Project Documentation — Zephyr Project Documentation"))

## Zephyr 最重要的三个概念

### 1. Devicetree：描述硬件

例如你的控制器上：

- 哪个 CAN 控制器启用
    
- UART 使用哪些引脚
    
- SPI 外接了什么芯片
    
- 寄存器地址是什么
    
- 中断号是多少
    

这些内容尽量不写死在业务代码中，而是放在设备树文件里：

```dts
&can0 {
    status = "okay";
    bitrate = <500000>;
};
```

这样换板子、换引脚时，主要修改设备树，不必大量修改应用程序。

### 2. Kconfig：选择软件功能

例如：

```text
CONFIG_CAN=y
CONFIG_LOG=y
CONFIG_SHELL=y
CONFIG_BLUETOOTH=n
```

设备树主要描述“板子上有什么硬件”，Kconfig 主要决定“这次编译启用什么软件功能”。Zephyr 使用的 Kconfig 与 Linux 内核的配置体系同源，目标是尽量不修改源代码就能完成系统裁剪。([Zephyr Project Documentation](https://docs.zephyrproject.org/latest/build/dts/dt-vs-kconfig.html?utm_source=chatgpt.com "Devicetree versus Kconfig — Zephyr Project Documentation"))

### 3. 标准驱动 API

传统 MCU 厂商 SDK 可能分别写成：

```c
S32K_CAN_Send();
STM32_CAN_Transmit();
NXP_FLEXCAN_Write();
```

Zephyr 希望应用层统一调用：

```c
can_send(dev, ...);
```

下面究竟是 NXP、STM 32 还是其他芯片，由驱动和设备树负责适配。

这使业务代码更容易跨芯片迁移，但真正做产品时，芯片初始化、DMA、Cache、时钟和高性能控制等部分仍可能需要厂商专用代码。

## 和 FreeRTOS、Linux 是什么关系

可以这样理解：

```text
裸机
只提供CPU和外设，调度全靠自己写

FreeRTOS
重点是轻量级实时内核和任务调度

Zephyr
实时内核 + 驱动 + 配置 + 协议栈 + 完整开发框架

Linux
适合资源更丰富、通常具有MMU和大内存的MPU/SoC
```

所以 Zephyr 不是“小型 Linux”，也没有直接使用 Linux 内核；只是大量采用了 Linux 社区已经验证过的设计思想，例如设备树、Kconfig、统一驱动和子系统抽象。

## 对你做汽车控制器有什么价值

对你的汽车 MCU、S 32 K、电机和机器人方向，Zephyr 比较适合承担：

- CAN/CAN FD 通信
    
- 诊断和日志
    
- 传感器管理
    
- 参数存储
    
- OTA 升级
    
- 网络和蓝牙
    
- 控制器状态管理
    
- 多任务调度
    
- 机器人外围设备管理
    

Zephyr 官方代码中已经存在 NXP S 32 K 3 的引脚控制、电源管理等设备树绑定，也有基于 S 32 K 3 的板卡支持案例，说明它确实在向汽车 MCU 生态扩展。([Zephyr Project Documentation](https://docs.zephyrproject.org/latest/build/dts/api/bindings/pinctrl/nxp%2Cs32k3-siul2-pinctrl.html?utm_source=chatgpt.com "nxp,s 32 k 3-siul 2-pinctrl — Zephyr Project Documentation"))

但它目前不能简单替代你汽车项目里的所有东西。对于以下部分仍需谨慎：

- FOC 电流环
    
- 高频 PWM 控制
    
- 微秒级中断响应
    
- ASIL 功能安全链路
    
- AUTOSAR Classic 项目
    
- 厂商 MCAL 和安全认证组件
    

尤其是量产汽车控制器，是否使用 Zephyr 不只取决于技术好不好，还取决于芯片支持、功能安全认证、供应商责任、工具链和主机厂要求。

**一句话总结：**

<mark style="background: #FF5582A6;">> Zephyr 是一套试图把 MCU 开发从“厂商 SDK 加手工作坊式代码”，升级成“类似 Linux 的标准化嵌入式软件平台”的开源实时操作系统。</mark>


Zephyr 并不是突然从零写出来的。它的历史可以分成两条线：

1. **内核代码的技术血统**
    
2. **2016 年以后 Linux 基金会主导的开源项目历史**
    

## 一、早期血统：Virtuoso → Rocket

Zephyr 最早的技术源头，可以追溯到一套名为 **Virtuoso** 的 DSP 实时操作系统。后来相关技术被 Wind River 收购，内核经过改造后被称为 **Rocket Kernel**。

因此，最初的 Zephyr 并不是“把 Linux 内核缩小”，而是以一套传统嵌入式实时内核为起点。Zephyr 官方资料将其技术演变概括为：

```text
Virtuoso DSP OS
       ↓
Wind River Rocket Kernel
       ↓
Zephyr RTOS
```

不过，今天的 Zephyr 已经经过十年社区开发，代码架构、驱动、网络、安全和构建系统都发生了巨大变化，不能简单理解成“Rocket 换了个名字”。([Zephyr Project](https://www.zephyrproject.org/zephyr-an-operating-system-for-iot/ "Zephyr – An Operating System for IoT – Zephyr Project"))

## 二、2015—2016 年：代码开源，Zephyr 项目正式成立

部分早期代码在 **2015 年**进入开放开发阶段。

真正具有标志性的时间点是：

> **2016 年 2 月 17 日，Linux 基金会正式宣布成立 Zephyr Project。**

早期支持者包括：

- Intel，以及当时相关的 Wind River、Altera 团队
    
- NXP
    
- Synopsys
    
- UbiquiOS
    

当时的目标很明确：Linux 对于极小型设备太重，而市场又缺少一套由多个厂商共同维护、避免被单一芯片公司控制的开源 RTOS。

最初公开支持的开发板只有少数几款，包括 Arduino 101、Arduino Due、Intel Galileo Gen 2 和 NXP FRDM-K 64 F。([Zephyr Project](https://www.zephyrproject.org/the-linux-foundation-announces-project-to-build-real-time-operating-system-for-internet-of-things-devices/ "The Linux Foundation Announces Project to Build Real-Time Operating System for Internet of Things Devices – Zephyr Project"))

这一时期的 Zephyr 更像：

```text
小型实时内核
+ 基础驱动
+ 蓝牙和简单网络
```

远没有今天这么完整。

## 三、2016—2018 年：从“小内核”变成完整平台

随后几年，Zephyr 开始大量吸收 Linux 和现代开源软件的开发方法，包括：

- Kconfig 配置系统
    
- Devicetree 设备树
    
- 统一驱动模型
    
- CMake 构建系统
    
- 自动化测试
    
- 多架构支持
    
- 网络协议栈
    
- 蓝牙协议栈
    
- 文件系统
    
- 电源管理
    
- 用户态隔离
    

Zephyr 逐渐不再只是类似 FreeRTOS 的“任务调度器”，而是开始形成完整的软件平台：

```text
应用
↓
通信、存储、传感器等子系统
↓
统一驱动接口
↓
SoC和厂商HAL
↓
硬件
```

安全也从项目成立之初就被放在重要位置，包括建立安全委员会、漏洞报告和处理流程。到 2018 年前后，项目获得了 Linux Foundation Core Infrastructure Initiative 的 Gold Best Practices Badge。([Zephyr Project](https://www.zephyrproject.org/celebrating-a-decade-of-zephyr-and-the-journey-ahead/?utm_source=chatgpt.com "Celebrating a Decade of Zephyr—and the Journey Ahead – Zephyr Project"))

## 四、2019 年：第一次真正面向量产产品

**2019 年 4 月，Zephyr 1.14 LTS 发布。**

这是它的第一个长期支持版本，意义非常大：以前 Zephyr 更新很快，更像一个开发中的技术项目；有了 LTS 后，企业才更容易将其用于需要维护数年的商业产品。

当时 Zephyr 已经支持：

- 160 多种板卡配置
    
- 8 种处理器架构
    
- 大约 500 名贡献者
    

同时开始强调长期安全修复、稳定性和可认证性。([Zephyr Project](https://www.zephyrproject.org/learn-more-about-zephyr-1-14-0-lts/?utm_source=chatgpt.com "Learn more about Zephyr 1.14.0 LTS – Zephyr Project"))

同年发布的 Zephyr 2.0 又进一步加强了：

- 64 位架构兼容
    
- Cortex-R 支持
    
- 高精度超时和无节拍调度
    
- BLE 控制器
    
- 更多硬件平台
    

这时 Zephyr 开始从“物联网小系统”向工业控制、无线设备和复杂嵌入式系统扩展。([Zephyr Project](https://www.zephyrproject.org/zephyr-rtos-2-0-release-highlights/?utm_source=chatgpt.com "Zephyr RTOS 2.0 Release Highlights – Zephyr Project"))

## 五、2020—2021 年：进入快速扩张阶段

到 2020 年，Zephyr 已经有：

- 200 多款支持板卡
    
- 超过 4 万次代码提交
    
- 更完整的蓝牙、网络、USB、存储和安全体系
    

项目也建立了比较正式的漏洞响应机制，包括 PSIRT，并成为可以分配 CVE 编号的 CNA。这意味着它开始按照成熟基础软件项目的方式处理安全漏洞。([Linux Foundation](https://www.linuxfoundation.org/press/press-release/the-zephyr-project-marks-critical-milestones-for-security-and-product-ready-maturity "The Zephyr Project Marks Critical Milestones for Security and Product-Ready Maturity - Linux Foundation"))

到了 2021 年：

- 贡献者超过 1,000 人
    
- 提交数超过 55,000 次
    
- 举办了第一届 Zephyr Developer Summit
    
- Zephyr 2.6 开始支持构建时生成 SBOM
    
- Zephyr 2.7 成为第二个 LTS 版本
    

2.7 LTS 后来成为很多商业产品的长期基础版本。([Linux Foundation](https://www.linuxfoundation.org/press/press-release/antmicro-doubles-down-on-commitment-to-the-zephyr-project-as-community-grows-to-more-than-1000-contributors "Antmicro Doubles Down on Commitment to the Zephyr Project as Community Grows to More Than 1,000 Contributors - Linux Foundation"))

这个阶段，Zephyr 已经不再是“小众爱好者 RTOS”，而开始被芯片公司和产品公司真正纳入 SDK 及产品路线。

## 六、2022—2024 年：适应多核和复杂 SoC

随着 MCU 越来越复杂，Zephyr 面对的设备不再只是单核 Cortex-M，而开始出现：

- 多核 MCU
    
- Cortex-M 与 Cortex-R 混合
    
- 多种架构共同存在
    
- 多 SoC 板卡
    
- AMP 异构多处理器
    
- MCU 上的图形、音频和机器学习
    

因此，Zephyr 重新设计了硬件描述模型。

**2024 年 7 月发布的 Zephyr 3.7 LTS** 引入了新的硬件模型，更好地支持：

- 多核 SoC
    
- 多架构 AMP
    
- 多 SoC 板卡
    
- 更复杂的板卡变体
    
- 更完整的 POSIX 接口
    
- HTTP/1.1 和 HTTP/2 服务
    
- 扩展的蓝牙和音频能力
    

3.7 是目前仍受支持的第三代 LTS 版本，计划维护至 2029 年。([Zephyr Project Documentation](https://docs.zephyrproject.org/latest/hardware/porting/board_porting.html?utm_source=chatgpt.com "Board Porting Guide - Zephyr Documentation"))

汽车行业的参与也在增强。例如大众集团软件公司 CARIAD 在 2024 年成为 Zephyr 项目的白金成员，说明车企已经开始把它看作值得参与建设的嵌入式基础平台，但这不代表 Zephyr 已经全面替代 AUTOSAR。([Zephyr Project](https://zephyrproject.org/zephyr-project-welcomes-cariad-alif-and-arm-as-it-launches-the-lts-release/?utm_source=chatgpt.com "Zephyr Project Welcomes CARIAD as a Platinum Member and Alif Semiconductor and Arm as Silver Members as it Launches the Long Term Support (LTS) Release – Zephyr Project"))

## 七、2025—2026 年：从 IoT RTOS 走向通用嵌入式基础设施

进入 4.x 版本后，Zephyr 持续扩展到：

- 更复杂的工业设备
    
- 无线通信模组
    
- 机器人
    
- 汽车电子
    
- 边缘 AI
    
- 多核异构 SoC
    
- 安全和长期生命周期产品
    

截至 2026 年，Zephyr 已经发展到：

- 支持超过 1,000 款板卡
    
- 全球贡献者超过 3,000 人
    
- 被大量组织用于商业产品
    
- 形成了稳定版与 LTS 并行的发布制度
    

当前最新稳定版是 **Zephyr 4.4.0，于 2026 年 4 月 14 日发布**；项目也已转向大约每六个月发布一个主要版本的节奏。([Zephyr Project](https://www.zephyrproject.org/zephyr-turns-10-as-global-adoption-surges-and-long-term-embedded-use-expands/ "Zephyr Turns 10 as Global Adoption Surges and Long-Term Embedded Use Expands – Zephyr Project"))

与此同时，项目正在继续推进 IEC 61508、ISO 26262 等功能安全方向的工作。但“正在为安全认证准备”和“任何 Zephyr 项目天然满足 ASIL”是两回事，具体产品仍需要确定版本、工具链、配置、证据链和独立认证。([Zephyr Project](https://zephyrproject.org/zephyr-at-10-years-survey-feedback-kate-stewart-hilary-carter-the-linux-foundation/?utm_source=chatgpt.com "Zephyr at 10 Years: Survey Feedback – Kate Stewart & Hilary Carter, The Linux Foundation – Zephyr Project"))

## 它十年的核心变化

可以压缩成四个阶段：

```text
2015—2016
传统RTOS内核
Rocket → Zephyr

2016—2019
开源物联网RTOS
增加驱动、蓝牙、网络、设备树和Kconfig

2019—2024
面向商业产品的平台
LTS、安全机制、SBOM、多架构、多核支持

2024—2026
通用嵌入式基础设施
工业、汽车、机器人、边缘AI和复杂SoC
```

所以图里说“MCU 未来的两条主流之一是 Zephyr”，并非完全没有依据。它过去十年的发展路径，本质上是：

> **从一套小型实时内核，发展成一个类似“MCU 世界公共基础设施”的厂商中立开源平台。**

<mark style="background: #FF5582A6;">但在汽车领域，它目前更可能先进入通信控制器、网关、辅助 MCU、智能传感器、执行器和非最高安全等级功能，而不是马上取代成熟的 AUTOSAR Classic、商用安全 RTOS 和厂商 MCAL。
</mark>
