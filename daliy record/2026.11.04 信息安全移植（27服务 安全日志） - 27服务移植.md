## 主要的问题是 27 服务没有使用 HSE 的发生器

PBL 中当前工程的 Seed 是调用 HSE 随机数服务生成的 16 字节随机数据，不是根据 APP 内容或共享密钥计算出来的。
而 APP 中使用的是伪随机。这两个是一样的吗？需要确认一下

**两者都可能通过确定性算法生成数列，但 HSE 面向密码安全，普通 `rand()` 通常不具备这种安全性。**

| 对比   | `srand()` / `rand()` | 当前 HSE 随机数服务    |
| ---- | -------------------- | --------------- |
| 初始来源 | 程序传给 `srand()` 的种子   | 硬件真随机源提供熵       |
| 生成机制 | 普通伪随机算法              | 面向密码用途的随机数生成机制  |
| 可预测性 | 种子已知时，通常容易预测         | 正确工作时，设计目标是难以预测 |
| 用途   | 模拟、普通随机选择等           | 安全访问挑战值、密钥生成等   |
|      |                      |                 |
使用相同实现、每次以相同种子初始化，就会得到相同数列。`srand(time(NULL))` 的种子来自时间，也可能被猜到。

*HSE 也不意味着每个输出字节都直接来自物理噪声。**它使用真随机源提供熵，再由密码学随机数生成器产生输出

> [!NOTE] 伪随机
>**“伪随机”的意思是：看起来杂乱，但背后按固定算法计算。** `srand()` 设置起点，`rand()` 从这个起点对应的序列中取数；相同起点会重现相同序列，这是 C 规定的行为。

# 27 服务这种安全真的需要吗？

1.为什么要先 请求 seed,再让诊断仪提交 key，为什么不直接发送同一个固定的密码？
如果是固定的密码，那可能会被截获，就会被反复使用。那现在这种 27 服务的意义就是，虽然 seed & key 也可能会被监听到，这种机制的价值在于，让一次验证的答案与当次的 seed 关联，在种子生成和算法涉及合理的前提，别人截获上一次的 key,也不能直接用于下一次解锁。这就是 ：<mark style="background: #FF5582A6;"> 防重放
</mark>

> [!NOTE] 虽然 seed 每次请求都会变化，但是 seed 和 key 的关系固定，可以列举出所有的关系吗？
> 首先请 seed,并不会同时获取正确的 key，这个 key 需要你自己校验。实际可能出现的 seed,如果是 16 个字节，可能有 3.4* *1 0^8
>

客户需求：

1. 标准的 UDS 协议--27 服务[^3]
2. 最大错误访问尝试次数应为 3 次。达到时，需要 10 s 的时间延迟才能对服务进行响应。
3. 当Delay _ Timer未被激活时，ECU上电/复位时不需要延时。如果在Delay _ Timer运行过程中出现ECU复位或掉电OFF - ON，则ECU必须重新启动Delay _ Timer。

5. 如果在接收到SecurityAccess ' requestSeed '消息时，请求的安全级别已经解锁，ECU应使用种子值为零的SecurityAccess ' requestSeed '正响应消息服务进行响应。对于当前锁定的给定安全级别，ECU不得发送全零种子。
6. 如果与requestSeed 0x05相关的安全等级是激活的，并且一个测试人员的请求成功地解锁了与requestSeed 0x03相关的安全等级，那么此时只有与requestSeed 0x03相关的安全等级支持的安全功能才会被解锁。任何以前由与请求Seed 0x05相关的安全级别解锁的附加安全功能将不再激活。安全等级编号具有任意性，并不暗示等级之间存在任何关系。（每个时刻都是只有一个安全等级被激活，不能同时）

## MU 实际是如何起作用的？

- **MU 寄存器传递地址、响应码和状态。**
- **双方可访问的内存保存请求参数、输入数据和输出数据。**

| 寄存器     | 地址                 | M7 侧用途          | 1                                    | 2                                                              |
| ------- | ------------------ | --------------- | ------------------------------------ | -------------------------------------------------------------- |
| `FSR`   | `0x4038C104`       | 读取 HSE 状态和通道忙标志 |                                      |                                                                |
| `TSR`   | `0x4038C124`       | 检查发送寄存器是否为空     |                                      |                                                                |
| `RSR`   | `0x4038C12C`       | 检查是否收到响应        | ```<br>RSR.RF0 = 1：通道0有响应可读<br>```   |                                                                |
| `TR[n]` | `0x4038C200 + 4×n` | 写入请求描述符地址       | M 7 先在 RAM 中填好请求描述符，把描述符地址写入 `TR[0]` | MU 硬件把这条消息传到 HSE 侧，HSE 据此知道有新的服务请求。之后，HSE 通过内部总线读取该地址上的描述符和参数。 |
| `RR[n]` | `0x4038C280 + 4×n` | 读取服务响应码         | HSE 执行服务，把版本信息写回 RAM                 |                                                                |
| `RCR`   | `0x4038C128`       | 配置接收响应中断        |                                      |                                                                |
|         |                    |                 |                                      |                                                                |

**① M 7 先在 RAM 中填好请求描述符**

当前 `GetAttr()` 固定使用 **MU 0、通道 0**，主要填写：

```
desc->srvId = HSE_SRV_ID_GET_ATTR;

desc->hseSrv.getAttrReq.attrId  = HSE_FW_VERSION_ATTR_ID;
desc->hseSrv.getAttrReq.attrLen = sizeof(hseAttrFwVersion_t);
desc->hseSrv.getAttrReq.pAttr   = (HOST_ADDR)&gHseFwVersion;
```


**② M 7 把描述符地址写入 `TR[0]` **

底层操作等价于：

```
MU0_MUB.TR[0] = (uint32_t)desc;
```

**这里发送的是描述符的地址，不是版本号，也不是整个描述符。**

MU 硬件把这条消息传到 HSE 侧，HSE 据此知道有新的服务请求。之后，HSE 通过内部总线读取该地址上的描述符和参数。

**③ HSE 执行服务，把版本信息写回 RAM**

HSE 读取 `pAttr`，然后把版本字段写入：

```
gHseFwVersion
```

这就是你在 Watch 中看到 `majorVersion=2、minorVersion=55、patchVersion=0` 的来源。

**④ HSE 通过 MU 返回服务响应码**

HSE 在对应通道返回响应，M 7 侧会观察到：

```
RSR.RF0 = 1：通道0有响应可读
```

M 7 随后读取：

```
response = MU0_MUB.RR[0];
```

成功码是：

```
HSE_SRV_RSP_OK = 0x55A5AA33
```

因此这次调用的两种结果分别存放在：

```
RAM 中的 gHseFwVersion → 版本数据
MU 的 RR[0]           → 本次服务是否成功
```

当前同步调用通过轮询 `RSR` 等待响应，读取 `RR` 后还会等待该通道的 `FSR` 忙标志清除。见 [HSE_Send (line 189)](/E:/github/ZYNP_FBL_5_1_001/MCAL/Crypto_43_HSE/src/hse_host.c:189)。

## DLL 是如何起作用的？

**CANoe 识别 `27` 服务，依靠 CDD 诊断描述；调用 DLL，依靠约定好的函数接口。** 这两件事分别配置。

|部分|告诉 CANoe 什么|
|---|---|
|**CDD 文件**|ECU 有哪些诊断服务、子功能、参数和数据长度|
|**Seed & Key DLL**|如何根据 Seed 算出 Key|
|**ECU 程序**|实际接收并处理 `27` 请求、验证 Key|
<mark style="background: #FF5582A6;">DLL 通过固定接口提供计算功能: GenerateKeyEx(Seed, Seed 长度, 安全级别, 其他参数, 输出 Key);</mark>
