
# 问题 
![](assets/2026.08.25%20%20唤醒源都有效会导致通信丢失/file-20260825143142669.png)
`if (KL15) ... else if (CAN)`，两者同时存在时只记录 KL 15。但 EcuM 仍可能保留 CAN Pending 事件



![](assets/2026.08.25%20%20唤醒源都有效会导致通信丢失/file-20260825143217756.png)

设置 `CANIF_OFFLINE`，<mark style="background: #FF5582A6;">不是为了让 CAN Controller 停止，而是为了让当前 ETAS CanIf 进入“唤醒校验接收模式”。</mark>

当前 CanIf 接收路径是这样判断的：

```
if(PduMode == CANIF_TX_OFFLINE ||
   PduMode == CANIF_ONLINE ||
   PduMode == CANIF_TX_OFFLINE_ACTIVE)
{
    ModeChkStatus = CANIF_PRV_VALID_CHANNEL_MODE;
}
else
{
    ModeChkStatus = CANIF_PRV_WAKEUP_MODE;
}
```

![](assets/2026.08.25%20%20唤醒源都有效会导致通信丢失/file-20260826111859941.png)

只有进入 `CANIF_PRV_WAKEUP_MODE`，并收到配置的 CanNm PDU，才会执行：

```
ControllerState_ps->ValidationSts_b = CANIF_SET;
```

见 [CanIf_RxIndication.c (line 488)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/CanIf/src/CanIf_RxIndication.c:488)。

随后：

```
CanIf_CheckValidation(wakeupSource);
```

检查到 `ValidationSts_b == CANIF_SET`，才回调：

```
EcuM_ValidateWakeupEvent(wakeupSource);
```
![](assets/2026.08.25%20%20唤醒源都有效会导致通信丢失/file-20260826112016238.png)

完整链路是：

```
CANIF_OFFLINE
    ↓
普通 Rx indication 和 Tx 被禁止
    ↓
收到配置的 CanNm PDU
    ↓
ValidationSts_b = CANIF_SET
    ↓
CanIf_CheckValidation()
    ↓
EcuM_ValidateWakeupEvent(CAN)
    ↓
CAN wakeup 验证成功
```

如果不设置 Offline：

- CanIf 会走普通接收路径；
- CanNm PDU 会向上层正常上报；
- 但不会设置 `ValidationSts_b`；
- `CanIf_CheckValidation()` 就无法确认 CAN wakeup；
- CAN 唤醒会一直 Pending，最后可能超时。

`CANIF_TX_OFFLINE` 也不能替代，因为它在当前实现中仍属于普通接收模式，不会进入 Wakeup Validation 分支。

所以准确地说：

> 不是 AUTOSAR 在所有实现中都强制要求这里 Offline，而是当前 ETAS CanIf 的唤醒校验机制依赖 Offline 状态。

它只能用于“纯 CAN 唤醒校验窗口”，不能在 KL 15 已经建立 FullCom 时反复设置；这也是前面增加 IGN/Vbat 判断和一次性 Offline 标志的原因。


![](assets/2026.08.25%20%20唤醒源都有效会导致通信丢失/file-20260825143305303.png)


KL 15 在 [ExeMgrUT.c (line 174)](E:/github/ECAS_qirui_Single_Chamber/ASW/SWC/ExeMgrUT/src/ExeMgrUT.c:174) 请求 `FULL_COMMUNICATION`；但 CAN 校验同时在 [EcuM_Callout_Stubs.c (line 359)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/integration/src/bsw/EcuM/integration/EcuM_Callout_Stubs.c:359) 强制执行


![](assets/2026.08.25%20%20唤醒源都有效会导致通信丢失/file-20260825145215961.png)


这张断点图已经基本确认了冲突链路，而且证据比上一张更直接。

断点停在：

```
CanIf_SetPduMode(CanIfConf_CanIfCtrlCfg_ETAS_CAN, CANIF_OFFLINE)
```

此时右侧状态同时显示：

- `EcuM_Prv_dataPendingWakeupEvents_u32 = 32`，即 `0x20`，说明 CAN 唤醒仍处于待校验状态。
- `EcuM_Prv_dataValidatedWakeupEvents_u32 = 128`，即 `0x80`；如果配置中 `0x80` 对应 KL 15，则 KL 15 已经验证成功。
- `ComM_ChannelsStruct[0].UserRequestCtr_u16 = 1`，存在有效通信用户请求。
- `ChannelState_e = COMM_FULL_COM_NETWORK_REQUESTED`，ComM 正在请求 Full Communication。
- `CanNm_RamData_s[0].Mode_en = NM_MODE_NETWORK`。
- `CanNm_RamData_s[0].State_en = NM_STATE_REPEAT_MESSAGE`。

也就是说，同一时刻的状态是：

```
ComM：要求全通信
CanNm：已经进入网络模式/Repeat Message
EcuM：仍在执行 CAN 唤醒校验
CanIf：即将被设置成 OFFLINE
```

这正是典型的上下层状态不一致：

```
上层 ComM / CanNm：网络应该运行
             ↓
下层 CanIf：禁止正常 PDU 收发
```

代码注释也说明了该调用的原始意图：

```
/* Keep normal Rx indications disabled until a configured CanNm PDU validates */
```

单独发生 CAN 唤醒时，这种处理可能合理：先关闭普通报文通知，仅通过专用校验路径等待合法 CanNm 报文。但当 KL 15 已经让系统进入 Full Communication 时，CAN 唤醒校验路径仍无条件执行 `CANIF_OFFLINE`，就会把已经启动的通信链路再次关闭。

因此目前可以确认：

> `0x20` CAN Pending 唤醒事件没有在 KL 15 启动通信时被清除、确认或仲裁，导致 `EcuM_CheckValidation()` 继续执行 CAN 专用唤醒校验，并覆盖了 KL 15 建立的 Full Communication 状态。

# 优化


## IGN 优先，重叠时 CAN 唤醒视为冗余并清除

- [EcuM_Callout_Stubs.c (line 347)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/integration/src/bsw/EcuM/integration/EcuM_Callout_Stubs.c:347)
    
    - IGN 已验证或物理有效时，清除冗余 CAN Pending，避免执行 `CANIF_OFFLINE`。
    - 增加 `EcuM_CanValidationOfflineApplied_b`，纯 CAN 唤醒时 Offline 只设置一次。
    - 在校验成功、停止校验和 IGN 接管时复位标志。
- [ExeMgrUT.c (line 676)](E:/github/ECAS_qirui_Single_Chamber/ASW/SWC/ExeMgrUT/src/ExeMgrUT.c:676)
    
    - 恢复 `lastCtlStep != ctlStep` 判断。
    - 使用 `0xFF` 初值，确保第一次有效 Vbat 状态仍会下发。

验证结果：

- 两个文件均通过 GHS 独立对象编译。
- `git diff --check` 通过。
- 未重新链接，也没有覆盖你现有的 ELF/MAP。

建议重点测试：

1. CAN Pending 后 KL 15 拉高：
    
    - `PendingWakeupEvents` 的 `0x20` 应被清除。
    - `ValidatedWakeupEvents` 保留 IGN 的 `0x80`。
    - IGN 有效后不应再到达 `CanIf_SetPduMode(...OFFLINE)`。
    - CanIf 最终应保持 `CANIF_ONLINE`。
2. 纯 CAN 唤醒：
    
    - Offline 应只执行一次。
    - 收到合法 CanNm PDU 后 CAN 从 Pending 转为 Validated。
3. Vbat：
    
    - `Rte_Switch_PP_VbatCommCtl_currentMode()` 只在电压状态跨区间时执行。

当前策略是“IGN 优先，重叠时 CAN 唤醒视为冗余并清除”。测试时也请覆盖 IGN 很快再次关闭的场景，确认这符合整车需求。

- CAN-only 唤醒并收到合法 NM；
- IGN-only 启动；
- CAN Pending 后 IGN 拉高；
- IGN 有效时 CAN 唤醒到达；
- IGN 在重叠后快速关闭；
