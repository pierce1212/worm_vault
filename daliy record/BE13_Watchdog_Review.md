## 1. 结论：停止喂狗应能触发复位，但应用故障复位链路不完整

当前代码具备 BE13 SPI 问答喂狗实现。正常运行时约每 20 ms 写一次 WDMR；当前没有开启软件调试关闭分支，也没有开启停止喂狗测试。

在 BE13 正常工作、DEBUG 引脚未使看门狗禁用、硬件看门狗处于使能状态、RSTB 正确连接 MCU 复位输入的前提下，停止发送 WDMR 应触发 BE13 的超时复位。默认超时典型值 512 ms，规格范围 408～616 ms，计时参考是最后一次被芯片接收并用于重启计时的看门狗服务，而非 MCU 软件停止的任意时刻。

但不能由此认定“当前所有软件故障均能被外部看门狗复位”。BE13 在 Core1 的周期任务中自行喂狗，没有连接 WdgM 的触发许可。其他任务或其他核失效，而该任务继续执行时，BE13 仍可能持续收到正确答案。

本次是源码和手册审查，没有读取实板寄存器、原理图或测量 RSTB，也没有验证当前已烧录固件与源码一致。因此结论是“具备有条件的硬件超时复位能力”，不是“板上验证通过”。没有修改固件代码。

## 2. BE13 看门狗到底检查什么

BE13/900719 使用通过 SPI 服务的问答式看门狗。MCU 必须在允许的时间内交出按规定算法计算的 16 位答案。

它同时检查三件事：

1. 时间：MCU 和 BE13 的时钟及周期执行是否仍工作。
2. 计算：MCU ALU 与 BE13 内部运算逻辑是否得到一致结果。
3. 通信：SPI 命令能否完整、正确地到达芯片。

普通 SPI 访问不能代替喂狗。关键动作是写 `WDMR`。写种子、读取状态、控制阀或电机都不等价于这次问答。

### 2.1 关键寄存器

地址为十六进制，位号指 16 位数据域。

| 地址   | 寄存器              | 作用                          |
| ---- | ---------------- | --------------------------- |
| 0x20 | WDCFG            | 看门狗配置和状态                    |
| 0x21 | WDSEED           | MCU 写入的 16 位种子；写 0xFFFF 被忽略 |
| 0x22 | WDMR             | MCU 算出的答案；写入触发一次服务和比较       |
| 0x23 | WDAR             | BE13 算出的答案，MCU 可读回进行反向检查    |
| 0x35 | INT1.WDFLT       | 看门狗超时故障标志                   |
| 0x3A | SVFLT.ALU_OVRFLW | 运算不匹配计数达到复位阈值的标志            |

WDCFG 的 D14:D7 为 WD_RN，D6 为 WD_DIS，D5:D3 为 T_WD_SEL，D2:D0 为 WD_ER_CNT；D15 保留。默认数据为 `0x0038`：看门狗使能，超时选择 111，错误计数为零。

| T_WD_SEL |   典型超时 |        最小～最大 |
| -------- | -----: | -----------: |
| 000      |   4 ms |   3.2～4.8 ms |
| 001      |   8 ms |   6.4～9.6 ms |
| 010      |  16 ms | 12.8～19.2 ms |
| 011      |  32 ms |     25～39 ms |
| 100      |  64 ms |     51～77 ms |
| 101      | 128 ms |   102～154 ms |
| 110      | 256 ms |   204～308 ms |
| 111      | 512 ms |   408～616 ms |

虽然手册称其为 windowed watchdog，这几节和电气表并没有明确给出一个“前半窗禁止喂狗”的独立最小服务时间。不能套用其他芯片的 50% 关闭窗规则，推断 20 ms 喂狗过早。第 106 页表述中的 “timeout check disable = ...” 也不应理解为这些取值关闭看门狗；第 125 页明确列出对应超时，禁用流程另见 6.21.5。

### 2.2 6.21.3：正常模式的运算和时序

正常上电且不处于测试模式时，RSTB 释放后看门狗自动启动。它不会等到 CDD 初始化函数执行后才启动。

MCU 首先写 WDSEED。首次 ALU 输入直接使用这个种子。后续每轮使用推进后的 LFSR 值。根据图 41：

```text
feedback = NOT(bit15 XOR bit13 XOR bit12 XOR bit10) AND 1
next = ((current << 1) OR feedback) AND 0xFFFF
```

图 42 的 ALU 运算顺序为：乘 4，加 6，减 4，按位取反，再除以 4，得到 16 位答案。项目用 18 位中间结果掩码处理乘法扩展：

```text
answer = ((NOT(current * 4 + 6 - 4)) AND 0x3FFFF) >> 2
```

该数学结果等于输入的 16 位取反，但实际实现保留手册规定的运算链更便于核对 ALU 检查意图；不要只为简化表达而改掉运算链。

当前初值 0x5A5A 的前六轮应为：

| 轮次 | ALU 输入 | 写入 WDMR 的答案 |
|---|---|---|
| 1 | 0x5A5A | 0xA5A5 |
| 2 | 0xB4B4 | 0x4B4B |
| 3 | 0x6969 | 0x9696 |
| 4 | 0xD2D2 | 0x2D2D |
| 5 | 0xA5A5 | 0x5A5A |
| 6 | 0x4B4A | 0xB4B5 |

MCU 写 WDMR 后，芯片执行自身运算、更新 WDAR 并比较。MCU 可读 WDAR 核对 BE13 是否正常。SPI 返回数据属于前一笔事务，因此应按返回地址、CRC 和流水关系配对，不能把当前帧的 MISO 直接当成当前请求结果。

改变 T_WD_SEL 不会清零正在运行的计时器。缩短窗口时，必须在计时尚未达到新超时前完成配置和服务。

### 2.3 6.21.4：两类故障怎样复位

| 故障 | 判定 | 动作 |
|---|---|---|
| 超时 | 看门狗计时到期 | 拉低 RSTB，置 WDFLT |
| 答案错误累积 | MR/AR 不匹配使 WD_ER_CNT 增加，达到 5 | 拉低 RSTB，置 ALU_OVRFLW |

答案匹配时错误计数减少。因此“达到 5”不是必须连续错五次；它是带恢复机制的累积计数。也不要把一次错误答案等同于立即复位。

故障会引起 SPI 寄存器映射复位，需要重新建立配置和种子。6.21.4 同时说明对应故障标志被置位；不要把“SPI map reset”理解为故障证据必然全部消失。故障标志需按各寄存器清除属性处理。

BE13 自己拉低 RSTB 或 MCU 拉低 RSTB 都会复位看门狗。第 23 页给出的 RSTB reset recovery 为典型 45 ms、36～54 ms；实际复位波形还取决于故障条件与板级电路。RSTB 释放不等于应用立即恢复，之后还有 MCU 启动、Boot 和应用初始化时间。

### 2.4 补充 6.21.5：禁用不是写一个位就完成

硬件方式：芯片被唤醒时 DEBUG 引脚施加 3.3 V，可禁用看门狗。连接 TRACE32 本身不能证明 BE13 的 DEBUG 引脚处于这个状态，必须查板级连接或实测。

SPI 方式必须完成：

1. 写 WD_DIS=1。
2. 读取 WD_RN[7:0]。
3. 用 `WD_RN:WD_RN` 拼成 16 位种子，并计算 ALU 答案。
4. 把答案写到 WDMR，随后确认 WD_DIS 的读回状态。

第 125 页还给出关闭确认超时 tACK：最小 8 ms、典型 10 ms、最大 12 ms，实现必须考虑此约束。

重新启用需要写 WD_DIS=0、写 WDSEED、写正确 WDMR，并继续周期服务；前三步应在手册规定的开放窗口内完成。

## 3. 当前项目的真实调用路径

工程配置为 S32K324 / Cortex-M7 / GHS，运行在 AUTOSAR OS 周期任务环境。

```text
OsTask_CanOsApp_BSW_1ms（Core1）
  -> RE_Core1_Swc_Bsw_1ms
    -> CddBE13_L2_MainFunction
      -> CddBE13_L2_MsgSR
        -> NORMAL_STATE
          -> CddBE13_L2_FeedWatchDog
          -> CddBE13_L2_SpiTrans
            -> Spi_AsyncTransmit
```

入口依据：`BasicSoftware/src/rte/gen/Rte.c:12980`、`ASW/SWC/Core1_Swc/src/Core1_Swc.c:187`。实际喂狗位于 `CDD/L2_Cdd_BE13/L2_Cdd_BE13.c:3073`，不是空的 `CDD/BE13/.../BE13_Init` 或 `CDD/ExtWdg/.../ExtWdg_Init`。

当前配置：

| 项目 | 当前值/行为 | 代码位置 |
|---|---|---|
| 调试禁用开关 | STD_OFF | L2_Cdd_BE13_Cfg.h:90 |
| 停喂测试开关 | 0，正常喂狗 | L2_Cdd_BE13_Cfg.h:169 |
| 初始种子 | 0x5A5A | L2_Cdd_BE13_Cfg.h:91 |
| 喂狗间隔 | 每 20 次正常状态调用，按 1 ms 任务约 20 ms | L2_Cdd_BE13.c:3075、3098 |
| SPI 帧位置 | 16 帧缓冲区的下标 12 | L2_Cdd_BE13_Cfg.h:131 |
| WDCFG 初始化 | 正常分支只读，不写 | L2_Cdd_BE13.c:1374 |
| WDSEED 初始化 | INIT_STATE2 写 0x5A5A | L2_Cdd_BE13.c:1389 |

初始化先走自检，再走 INIT_STATE1/2/3，最后到 NORMAL_STATE。自检判断按 1 ms 调用计数等待 11 次左右，首次喂狗在整个 CDD 状态机开始后约 16 ms，具体取决于任务调度和 SPI。这个时间不包含 RSTB 释放至 Boot、OS 启动、首次 CDD 调度的时间。上电首次服务必须从 RSTB 释放起整体测量，不能仅用 CDD 的 16 ms 认定启动预算满足。

## 4. 已确认的问题与限制

### 4.1 WdgM 无法通过当前 ExtWdg 接口停止 BE13 喂狗

`BasicSoftware/src/bsw/WdgIf/WdgIf_Cfg.c` 将外部设备映射到 ExtWdg。但 `CDD/ExtWdg/src/ExtWdg.c` 中 Init、SetTriggerCondition 没有实现，SetMode 直接返回 E_OK。BE13 CDD 也没有消费该接口维护的触发许可。

结果：调用外部设备的 SetTriggerCondition(0) 不会禁止 CDD 写 WDMR。其他任务异常但 Core1 喂狗任务仍运行时，不应期待 BE13 自动识别该业务故障。内部看门狗或其他复位机制是否动作是另一条链路，不能算作外部看门狗覆盖。

建议：把健康监督结果接入喂狗许可/期限，覆盖被监督任务与核。许可失效后禁止所有 WDMR 服务路径；不能只修改 ExtWdg 的空函数而保留无条件 CDD 喂狗。

### 4.2 当前依赖硬件默认窗口，软件配置值并未写入

Lcfg 中虽设置 WD_EN 和 T_WD_512MS，正常初始化最终执行的是 READ WDCFG。当前设置恰好与芯片正常复位默认值一致，所以这本身不意味着当前无法工作。

但修改 Lcfg 为其他超时时间不会改变芯片窗口；如果此前的软件或调试过程关闭了看门狗，这条只读路径也不能当成完整的重新使能流程。

建议：按明确的启动前提配置并读回 WDCFG，检查 WD_DIS、T_WD_SEL 和 WD_ER_CNT。涉及从禁用恢复时执行完整重新启用握手。

### 4.3 调试禁用分支没有实现完整握手

把 ECAS_DEBUG_DISABLE_BE13_WATCHDOG 改为 STD_ON 后，只会写带 WD_DIS 的 WDCFG，后面仍按固定 0x5A5A 种子服务。未看到读取 WD_RN、以 WD_RN:WD_RN 计算关闭答案并确认成功的流程。

因此注释所说“调试时不能复位 MCU”没有充分实现依据。此问题目前是未启用分支的问题，不能据此说当前看门狗已经禁用。

### 4.4 SPI 异常会造成服务状态失步或任务卡死

`L2_Cdd_BE13.c:3079` 在实际传输成功前就计算答案并推进软件 LFSR。`Spi_SetupEB` 返回值被忽略，`Spi_AsyncTransmit` 结果没有驱动状态机的成功/失败分支。

如果 WDMR 没有被 BE13 接收，软件仍前进，后续问答可能失步。初始化种子写失败也未被显式处理。

`L2_Cdd_BE13.c:908` 对任何非 SPI_SEQ_OK 状态无限等待，包括失败状态；没有超时恢复。这会使任务卡住。若 BE13 看门狗有效，它应最终因停喂复位；若看门狗已经禁用，就失去这层兜底。

建议：区分 pending、failed、成功；为等待设置期限，保持异步缓冲区生命周期正确。根据事务是否确定被接收设计 LFSR 提交/重新同步策略，避免简单重发造成重复推进。

### 4.5 没有逐轮反向核对 WDAR，启动清标志过早

通用读状态逻辑会轮询 WDCFG 和 WDAR，但没有看到逐轮把返回的 WDAR 与对应 WDMR 配对比较并处理异常的逻辑。通用轮询跨度约 75 个任务周期，不能直接把其中的 WDAR 与“当前最新 WDMR”比较。

这不妨碍 BE13 内部比较 MCU 答案，却缺少 MCU 对 BE13 的反向监控。

`L2_Cdd_BE13.c:1658` 设置待写 WDFLT 清除位，随后在 INIT_STATE1 中写 INT1；SVFLT 也有初始化清除命令。正常状态轮询发生在之后，可能已经看不到上次看门狗复位证据。建议先保存 MCU 复位原因以及 BE13 INT1/SVFLT/WDCFG，再清标志。

这些是待执行验证项，不是本次已经完成的测试。负载测试应在执行器不会造成意外动作的台架条件下进行。

建议同步抓取 RSTB、CSB、SCLK、MOSI、MISO。复位原因必须在清标志之前记录；仅看到调试器断连或应用重启不能区分 BE13、内部 SWT、软件复位和供电异常。
