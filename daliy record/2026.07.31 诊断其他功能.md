### 2. 四种上报状态的区别

```
DEM_EVENT_STATUS_PREFAILED
DEM_EVENT_STATUS_PREPASSED
DEM_EVENT_STATUS_FAILED
DEM_EVENT_STATUS_PASSED
```

含义：

- `PREFAILED`：监控认为存在故障倾向，由 Dem 执行配置的去抖。
- `PREPASSED`：监控认为正在恢复，由 Dem 执行恢复去抖。
- `FAILED`：应用已经完成去抖，直接告诉 Dem 最终失败。
- `PASSED`：应用已经完成去抖，直接告诉 Dem 最终通过。

因此，如果使用：

```
DEM_EVENT_STATUS_FAILED
```

通常不会等待配置的 `0.3s`，因为应用已经给出了最终结果。要验证 Dem 的时间去抖，需要周期上报：

```
DEM_EVENT_STATUS_PREFAILED
```

<mark style="background: #FF5582A6;">`FAILED` 是最终判定，`PREFAILED` 才是交给 Dem 继续去抖。下一步进入 Operation Cycle、Pending 和 Confirmed，因为老化、快照触发、状态位变化都依赖它们。</mark>

> <mark style="background: #FF5582A6;">`FAILED` 可以绕过去抖，却不一定绕过 Confirmed 的确认周期策略。</mark>


配置见：

[RTA_BIP_Dem_EcucValues.arxml (line 29151)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ecu_config/bsw/gen/RTA_BIP_Dem_EcucValues.arxml:29151)

### 1. POWER Operation Cycle

可以先把它理解为一次 ECU 运行周期：

```
ECU上电/周期开始
       │
       │ 监控执行
       │
ECU下电/周期结束
```

它是逻辑周期，不应简单理解成“程序运行一次”或者“Runnable 执行一次”。

Operation Cycle 通常由 EcuM、BswM 或应用通过类似接口控制：
![](assets/2026.07.31%20诊断其他功能/file-20260731133240510.png)

```
Dem_SetOperationCycleState(
    OperationCycleId,
    DEM_CYCLE_STATE_START
);

Dem_SetOperationCycleState(
    OperationCycleId,
    DEM_CYCLE_STATE_END
);
```

### 2. 与状态位的关系

一个新周期开始时：

- `TestFailedThisOperationCycle` 重新开始统计。
- `TestNotCompletedThisOperationCycle` 先置位。
- 监控执行完成后，`TestNotCompletedThisOperationCycle` 清零。
- 如果本周期出现过失败，`TestFailedThisOperationCycle` 置位。
- 即使故障随后恢复，该位通常也表示“本周期曾经失败过”。

因此：

```
TestFailed
```

表示当前故障结果；而：

```
TestFailedThisOperationCycle
```

表示本周期是否曾经失败过。

二者不能混为一谈。

### 3. Confirmation Threshold

当前配置：

```
DemEventConfirmationThreshold = 1
```

表示第一次有效故障周期就可以达到确认要求。因此你看到：

```
StatusOfDTC = 0x2F
```

其中 `PendingDTC` 和 `ConfirmedDTC` 都已经置位。

如果改成：

```
DemEventConfirmationThreshold = 2
```

可以理解为需要两个满足条件的故障 Operation Cycle，才能成为 Confirmed DTC。

重点是：

```
10ms Runnable调用100次 FAILED
```

不等于经历 100 个 Operation Cycle。它仍可能只是同一个 POWER 周期中的重复上报。

### 4. RecoverableInSameOperationCycle

当前配置：

```
DemEventRecoverableInSameOperationCycle = true
```

表示本周期内故障成立后，如果随后报告有效的 `PASSED`，当前 `TestFailed` 可以在同一个周期恢复。

但是以下历史状态不一定同时消失：

- PendingDTC
- ConfirmedDTC
- TestFailedThisOperationCycle
- TestFailedSinceLastClear

所以故障恢复不等于 DTC 记录被清除。

### 2. 如何连接到 NVM

```mermaid
flowchart LR
    A["Dem Event Memory<br/>RAM数组"] --> B["Dem NvM映射<br/>NVM_ID_EVMEM_LOC_x"]
    B --> C["NvM<br/>逻辑NVRAM块"]
```

Dem_EvMemEventMemory[1] → NVM_ID_EVMEM_LOC_ 1
...
Dem_EvMemEventMemory[9] → NVM_ID_EVMEM_LOC_ 9

#### 写入过程

故障满足存储条件后：

1. Dem 更新 RAM 中的 Event Memory Entry。
2. Dem 调用或触发 `NvM_WriteBlock()`。
3. NvM 将写请求排队。
4. MemIf 把请求交给 Fee。
5. Fee 进行磨损均衡和逻辑地址管理。
6. Fls 驱动把数据写入 Data Flash。
7. 写完后，结果逐层返回 Dem。

因此应用和 Dem 通常不操作物理 Flash 地址。它们只使用 NvM Block ID。物理 Flash 位置由 Fee 管理，可能随着磨损均衡而变化。

#### 上电读取过程

上电时方向相反：

```
Data Flash → Fls → Fee → NvM → Dem回调 → Event Memory RAM数组
```

当前工程通过显式同步回调在 NvM 缓冲区和 Dem RAM 数组之间复制：

[Dem_NvmCallbacks.c (line 28)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/src/nvm/Dem_NvmCallbacks.c:28)

这也是为什么：

- RAM 掉电会丢失；
- 但已经成功写入 Fee/Data Flash 的 DTC，上电后仍能恢复；
- 如果 NvM 写入尚未完成就断电，最新记录可能丢失。


### 3. 什么是冻结帧（就是快照）
冻结帧 `Freeze Frame` 在 UDS 里也经常叫 `Snapshot Record`。

它表示：

> 故障达到指定触发状态时，把那一瞬间的一组环境数据拍照保存下来。

例如故障发生时保存：

```
电源电压
电机转速
压力值
温度
车速
里程
时间
传感器原始值
```

它解决的问题是：

> 维修人员之后读取 DTC 时，怎么知道故障发生时车辆处于什么工况？

例如：

```
DTC：电机过温
当前温度：45℃
冻结帧温度：132℃
故障发生时转速：7000 rpm
故障发生时电压：28.5 V
```

虽然现在温度恢复了，但冻结帧保留了故障发生瞬间的数据。
#### 冻结帧配置关系

```
DataElementClass
        ↓
DidClass
        ↓
FreezeFrameClass
        ↓
FreezeFrameRecordClass
        ↓
FreezeFrameRecNumClass
        ↓
DTCAttributes
```

各自作用：

- `DataElementClass`：数据从哪里读取、长度和类型是什么。
- `DidClass`：把一个或多个 Data Element 组成一个 DID。
- `FreezeFrameClass`：这条快照包含哪些 DID。
- `FreezeFrameRecordClass`：记录号、触发时机、是否允许更新。
- `FreezeFrameRecNumClass`：一个 DTC 允许使用哪些记录号。
- `DTCAttributes`：把 Freeze Frame 配置绑定到具体 DTC。

# 冻结帧


先理解配置对象之间的关系：

```
DTC 0x416001
    ↓
DTCAttributes
    ↓
FreezeFrameClass
    ↓
DidClass
    ↓
DataElementClass
    ↓
ReadData函数/端口
```
![](assets/2026.07.31%20诊断其他功能/file-20260731145556232.png)
![](assets/2026.07.31%20诊断其他功能/file-20260731150013425.png)

可以把它理解成一份“冻结帧采集配方”：

```
DTC 0x416001
  └─ DTCAttributes：这个 DTC 使用哪套存储规则
      └─ FreezeFrameClass：冻结帧由哪些 DID 组成
          └─ DidClass：其中一个数据项的标识符，例如 DID 0x007B
              └─ DataElementClass：该 DID 具体包含什么数据、类型和长度
                  └─ ReadData：运行时真正读取当前数据值
```

各层的职责如下：

|配置层|作用|
|---|---|
|`DTC 0x416001`|故障代码本身|
|`DTCAttributes`|设置优先级、存储位置、冻结帧类、扩展数据类等|
|`FreezeFrameClass`|定义一条冻结帧需要记录哪些 DID|
|`DidClass`|定义冻结帧中的一个数据标识符，以及它包含哪些 DataElement|
|`DataElementClass`|定义单个数据元素的类型、大小以及取数方式|
|`ReadData`|在故障触发时读取应用程序的实时数据，交给 Dem 保存|

<mark style="background: #FF5582A6;">这条链的核心作用是：**告诉 Dem，在 DTC 触发冻结帧时，需要采集哪些现场数据，以及去哪里读取这些数据。**</mark>


另一条链决定“什么时候拍、保存为几号记录”：

```
DTCAttributes
    ↓
FreezeFrameRecNumClass
    ↓
FreezeFrameRecordClass
    ├─ RecordNumber
    ├─ Trigger
    └─ Update
```
![](assets/2026.07.31%20诊断其他功能/file-20260731150929525.png)
这里的“记录号”可以理解为：**同一个 DTC 的多个冻结帧槽位编号**。它不是 DTC 编号、DID，也不是 Event Memory 的第几个 Entry。
测试仪读取冻结帧时，必须告诉 ECU 读取哪个槽位。
19 04 41 60 01 01
│  │  └──────┘ └─ Snapshot Record 0 x 01
│  └─ DTC 0 x 416001
└─ 读取 DTC 冻结帧
### 为什么一个 DTC 可以有两个记录

因为一个故障在其生命周期中可能需要保存多个时刻的现场，例如：

| 记录       | 触发时刻    | 可能保存的意义         |
| -------- | ------- | --------------- |
| Record 1 | 第一次检测失败 | 故障刚出现时的环境       |
| Record 2 | 故障被确认   | 故障持续存在、正式成立时的环境 |
|          |         |                 |
你配置了两个冻结帧槽位，但两个槽位具有完全相同的触发条件。

当 `ConfirmedDTC` 从 0 变为 1 时，两个记录都会匹配同一个触发条件，采集的内容和时间点基本相同。因此在当前设计下，Record 1 和 Record 2 很可能是重复数据，第二个记录没有体现出明显的诊断价值。

注意：`ON_CONFIRMED` 在你这个 Dem 实现中是状态的**上升沿触发**，代码检查的是 Confirmed 位从 0 变成 1；它不是每次上报 `FAILED` 都触发。

### Event Memory 具体的格式

一个 Event Memory Entry：NvM 分配 72 字节
├─ Event/DTC 标识
├─ 状态及内部管理信息
├─ FailureCounter
├─ OccurrenceCounter
├─ AgingCounter
├─ FreezeFrameCounter
├─ Trigger
├─ TimeId
├─ Extended Data：1 字节
├─ Freeze Frame Record 1：1 字节
└─ Freeze Frame Record 2：1 字节


Q : DTC 进入 Confirmed 时，Dem 通过什么方式取得要保存的那 1 字节数据？

应用变量/传感器值
        ↓
提供方 SWC 的 ReadData Runnable
        ↓
RTE 端口与 AssemblySwConnector
        ↓
Dem 调用 Rte_Call_..._ReadData()
        ↓
Dem 获得当前数据
        ↓
保存进 Event Memory
        ↓
后续通过 NvM 写入 Data Flash

所以必须区分两个阶段：

```
ReadData：从应用程序采集实时现场值
NvM：把已经采集的冻结帧持久化到 Data Flas
```



# Extended Data（扩展数据）


**<mark style="background: #FF5582A6;">冻结帧记录的是“故障发生时现场是什么样”，扩展数据记录的是“这个故障经历了什么”。</mark>**

| 项目     | 冻结帧 Snapshot      | 扩展数据 Extended Data   |
| ------ | ----------------- | -------------------- |
| 主要用途   | 保存故障时的环境          | 保存计数、历史和辅助信息         |
| 典型内容   | 电压、温度、转速          | 发生次数、老化计数、FDC        |
| 数据组织   | DID + DataElement | Record + DataElement |
| UDS 读取 | `19 04`           | `19 06`              |

例如：

```
DTC 0x416001

冻结帧：
  故障确认时电压 = 9V
  温度 = 90℃
  转速 = 2000rpm

扩展数据：
  故障发生次数 = 5
  老化计数 = 2
  最大 FDC = 127
```

```
FDC 是 **Fault Detection Counter（故障检测计数器）**，用于表示故障当前“偏向正常”还是“偏向故障”的程度。

完全正常                                    故障完全成立
-128  ←──────────────  0  ───────────────→  +127

对于计数器去抖，每次上报通常按照配置的步长增加或减少内部计数；对于时间去抖，则根据 `PREFAILED/PREPASSED` 持续时间换算成 FDC。
```


### 配置引用链

```
DTCAttributes
    ↓
ExtendedDataClass
    ↓
ExtendedDataRecordClass
    ├─ RecordNumber
    ├─ Trigger
    ├─ Update
    └─ DataElementClassRef
```
![](assets/2026.07.31%20诊断其他功能/file-20260731155235377.png)
参数含义：

- `RecordNumber`：扩展数据记录号，例如 `0x01`；
- `Trigger`：什么时候采集，例如 Confirmed；
- `Update`：再次出现相应触发时，是否允许覆盖旧值；
- `DataElementClassRef`：这条记录具体保存哪些数据。

扩展数据的 Record 1 和冻结帧的 Record 1 是两个独立概念，不会相互冲突。

### 两种数据来源

扩展数据可以来自 Dem 内部：

```
OccurrenceCounter
AgingCounter
FailedCycles
CurrentFDC
MaxFdcSinceLastClear
```

这种数据由 Dem 自己维护，通常不需要连接应用 SWC。

也可以来自应用程序：

```
应用累计故障时间
特定软件状态
传感器统计值
```

这种数据需要通过 RTE `ReadData` 从 SWC 获取。

### 诊断读取

读取 `0x416001` 的扩展数据 Record 1：

```
19 06 41 60 01 01
│  │  └──────┘ └─ Extended Data Record 0x01
│  └─ DTC 0x416001
└─ ReadDTCInformation
```

预期正响应开头：

```
59 06 41 60 01 ...
```



### 冻结帧和扩展数据最核心的区别
扩展数据可以保存与冻结帧相同的“数据内容”，但它不会因此变成冻结帧记录。

例如，故障确认时的电压 `9V`：

```
放进冻结帧：
  作为现场环境数据
  使用 19 04 读取

放进扩展数据：
  作为扩展数据字段
  使用 19 06 读取
```

区别不在于“能否保存这个字节”，而在于它被哪套配置组织、用哪个诊断服务读取：

| 区别        | 冻结帧                | 扩展数据                  |
| --------- | ------------------ | --------------------- |
| 配置入口      | `FreezeFrameClass` | `ExtendedDataClass`   |
| 数据组织      | DID 及其 DataElement | Record 及其 DataElement |
| 典型语义      | 故障瞬间的环境            | 历史、计数和辅助信息            |
| UDS 读取    | `19 04`            | `19 06`               |
| 是否能读取应用数据 | 可以                 | 可以                    |

例如将电压配置到 Extended Data：

```
ExtendedData Record 1
  Trigger = ON_CONFIRMED
  Update  = NO
  DataElement = 当前电压
```

它确实会保存确认故障时的电压，看起来很像快照；但测试仪必须使用：

```
19 06 41 60 01 01
```

而使用 `19 04` 读不到它，因为它不属于 `FreezeFrameClass`。

你的工程甚至把同一个 `DemDataElementClass_0` 同时用于冻结帧和扩展数据。如果端口接通，并且两者都在 Confirmed 时触发，相同的 1 字节应用值可能同时被存进两种记录：

```
同一个应用数据
├─ Freeze Frame Record → 19 04
└─ Extended Data Record → 19 06
```

工程设计上建议：

- 电压、温度、转速等故障现场 → 冻结帧；
- 发生次数、老化计数、FDC、失败周期数 → 扩展数据；
- 客户诊断规范明确要求通过哪个服务读取 → 严格按照规范配置。

所以最准确的结论是：**内容可以相同，但记录类型、诊断语义和读取接口不同。**




# Aging（老化）

Aging 用于处理这种情况：

> **<mark style="background: #FFF3A3A6;">DTC 曾经已经 Confirmed，但之后连续多个合格周期都没有再次发生，Dem 自动认为它已经长期恢复。</mark>**

<mark style="background: #FFB86CA6;">它不是故障去抖，也不是诊断仪发送 `14` 清故障，而是一种自动退出 Confirmed 状态的机制。</mark>（应该就是所谓的历史故障吧）

### 基本过程

假设配置：

```
DemAgingAllowed = true
DemAgingCycleRef = POWER
DemAgingCycleCounterThreshold = 3
```

状态变化可以简化为：

```
DTC 已 Confirmed
       ↓
第1个完整 POWER 周期检测结果正常
AgingCounter = 1
       ↓
第2个完整 POWER 周期检测结果正常
AgingCounter = 2
       ↓
第3个完整 POWER 周期检测结果正常
AgingCounter = 3
       ↓
达到阈值，DTC 被老化
ConfirmedDTC 状态清除
相关 Event Memory 记录按实现和配置处理
```

### 什么叫“合格的老化周期”

仅仅重新上下电不一定算一次有效老化。

通常需要：

1. Aging Cycle 执行了 START 和 END；
2. 监控程序在该周期真正运行过；
3. 检测结果达到 `PASSED`；
4. 该周期内没有再次达到 `FAILED`。

因此：

```
只上下电，但监控没有执行
→ TestNotCompleted
→ 通常不能增加 AgingCounter
```

同一次上电中调用 100 次 `PASSED`：

```
POWER Cycle 没有 END
→ 仍然只是一个周期
→ 不会增加100次老化计数
```

### 如果故障再次发生

假设已经正常两个周期：

```
AgingCounter = 2
```

第三个周期再次 `FAILED`：

```
AgingCounter 通常被重置
DTC继续保持Confirmed
必须重新累计连续正常周期
```

<mark style="background: #FFB86CA6;">“连续正常”是 Aging 的核心。</mark>

### Aging 和 ClearDTC 的区别

| 项目       | Aging     | `14 ClearDiagnosticInformation` |
| -------- | --------- | ------------------------------- |
| 谁触发      | Dem 自动判断  | 诊断仪请求                           |
| 是否立即处理   | 否         | 通常是                             |
| 是否要求正常周期 | 是         | 否                               |
| 是否需要阈值   | 是         | 否                               |
| 主要目的     | 长期恢复后自动老化 | 维修或测试时主动清除                      |

### 对状态位的影响

一个故障从当前失败恢复时，通常先发生：

```
PASSED
↓
bit0 TestFailed 清零
```

随后经过相应周期：

```
bit2 PendingDTC 清零
```

但是：

```
bit3 ConfirmedDTC
```

不会仅因为一次 `PASSED` 就马上清零，而是通常要等待 Aging 达到阈值，或者通过 `14` 清除。

`bit5 TestFailedSinceLastClear` 是否在老化时清除，还受全局状态位处理策略影响。你的工程配置为 `DEM_STATUS_BIT_NORMAL`，不要简单认为所有历史位都会随 Aging 一起清零。

### `0x416001` 当前实际配置

当前工程中：

```

DemAgingCycleRef = DemOpCycle_POWER
AgingThreshold   = 未配置
```

见 [RTA_BIP_Dem_EcucValues.arxml (line 29107)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ecu_config/bsw/gen/RTA_BIP_Dem_EcucValues.arxml:29107)。

虽然引用了 `POWER` Aging Cycle，但 `DemAgingAllowed=false`，所以引用实际上不会让 `0x416001` 自动老化。

也就是说：

```

        ↓
以后连续很多次正常上下电
        ↓
不会通过Aging自动消除Confirmed
```

它需要 `14` 清除、修改配置开启 Aging，或者由其他已配置的内存管理行为处理。


```

第 3 题补充：重新出现 `FAILED` 的周期本身不会记一次正常老化，计数先回到0；之后下一个合格正常周期才变成1。
```

# Enable Condition 与 Storage Condition

这两个条件很容易混淆：

```
Enable Condition：允许不允许 Dem 处理这个故障检测结果
Storage Condition：允许不允许 Dem 把故障记录存进 Event Memory
```

### Enable Condition

当 Enable Condition 为 `false` 时，Dem 暂停处理该 Event 的检测结果。

例如电压太低时，通信报文可能天然异常，此时不应该判断通信故障：

```
电池电压正常
Enable Condition = true
→ 允许监控通信故障

电池电压过低
Enable Condition = false
→ 暂停判断通信故障
```

此时即使 SWC 上报 `PREFAILED/FAILED`，Dem 通常也不会让这个 Event 产生新的状态变化。

已有的 Confirmed DTC 不会因为 Enable Condition 变成 false 而自动清除。它只是暂停监控，不是清故障。

### Storage Condition

当 Storage Condition 为 `false` 时：

```
Dem仍然可以处理FAILED/PASSED
DTC状态仍可能变化
但禁止把事件数据写入Event Memory
```

因此可能出现：

```
TestFailed = 1
但没有新的冻结帧、扩展数据和完整Event Memory记录
```

简化对比：

|条件|状态处理|Event Memory 存储|
|---|---|---|
|Enable=false|暂停或忽略新的检测结果|不产生新的故障存储|
|Enable=true、Storage=false|正常处理|禁止存储|
|两者都为 true|正常处理|正常存储|

### Condition Group
![](assets/2026.07.31%20诊断其他功能/file-20260803111546855.png)
![](assets/2026.07.31%20诊断其他功能/file-20260803111534324.png)


一个 Event 引用的是 Condition Group，Group 内可以包含多个条件，一般按照 AND 关系处理：

```
EnableConditionGroup
├─ SystemInit = true
└─ BatNormal  = false

最终Group = false
```

所有条件都满足，Group 才满足。

(<mark style="background: #FF5582A6;">手动配置的</mark>)

# Immediate NvM 与掉电保持

Dem 处理故障时，首先更新的是 RAM，不是直接写 Data Flash：

```
Dem_SetEventStatus()
        ↓
Dem更新RAM中的状态和Event Memory
        ↓
Dem向NvM请求写入
        ↓
NvM → MemIf → Fee → Fls
        ↓
Data Flash
```

### “立即存储”是什么意思

`Immediate Nv Storage` 表示故障记录变化后，Dem 立即向 NvM 提交写请求。
![](assets/2026.07.31%20诊断其他功能/file-20260803134047351.png)
它不表示：

```
Dem_SetEventStatus()内部阻塞，直到Flash写完
```

NvM、Fee 和 Fls 通常采用异步任务处理：

```
Dem提交请求
→ Dem_SetEventStatus返回
→ NvM_MainFunction处理
→ Fee_MainFunction处理
→ Fls完成实际Flash操作
```

所以故障刚成立后立刻断电，即使配置了 Immediate Nv Storage，也不能绝对保证数据已经写完。

### 当前 `0x416001` 配置
![](assets/2026.07.31%20诊断其他功能/file-20260803134701706.png)
```
Event Memory分配触发：
DEM_TRIGGER_ON_TEST_FAILED

DemNvStorageStrategy：
IMMEDIATE_AT_FIRST_OCCURRENCE

DemImmediateNvStorage：
true

ImmediateNvStorageLimit：
未启用
```

含义是：

1. `PREFAILED` 尚未达到最终失败阈值时，不分配 Event Memory；
2. 达到 `TEST_FAILED` 后，分配或更新 RAM Entry；
3. `0x416001` 允许触发立即 NvM 存储；
4. 当前实现未配置发生次数限制，相关 Entry 更新可能继续触发立即写请求。

这里的“立即”仍然只是**立即提交异步 NvM 请求**。

### 为什么不把所有变化都立即写 Flash

Data Flash 存在擦写寿命限制。如果一个故障频繁变化：

```
FAILED → PASSED → FAILED → PASSED
```

每次都写 Flash 会导致：

- Flash 磨损加快；
- NvM 队列拥堵；
- Fee 垃圾回收增加；
- 诊断请求可能频繁收到 `0x78 ResponsePending`；
- ECU 关机时间和实时性能受影响。

因此通常只对重要 DTC 启用立即存储，普通数据在正常 Shutdown 时统一写入。

### RAM 与 NvM 的区别

```
RAM Event Memory
优点：快
缺点：断电丢失

NvM/Data Flash
优点：掉电保持
缺点：写入慢、寿命有限
```

当前每个 Primary Event Memory 位置对应一个 72 字节 NvM Block。RAM 内容最终通过 NvM/Fee 持久化到 Data Flash。

### 第八课检查题

1. `DemImmediateNvStorage=true` 是否意味着 `Dem_SetEventStatus()` 返回时，Flash 一定已经写完？

```
Dem_SetEventStatus()
→ 更新 Dem 的 RAM 状态
→ 必要时提交 NvM 写请求
→ 函数返回
→ 后续周期执行 NvM/Fee/Fls 任务
→ 最终写入 Data Flash
```


3. 写出从 Dem 到 Data Flash 的存储栈路径。

`MemIf` 是统一抽象接口：
- 使用 Data Flash 时，通常转发给 Fee。
- 使用 EEPROM 时，通常转发给 Ea。
- `NvM_MainFunction`、`Fee_MainFunction` 等周期函数负责逐步推进异步任务。


4. 为什么不建议所有 DTC 的每次状态变化都立即写入 NvM？


不能在每次 DTC 状态变化时都立即写 Flash，主要原因是：
- Flash 擦写寿命有限。状态频繁变化会产生大量写操作，加速 Flash 磨损。
- 写入比较耗时，会增加 NvM/Fee 任务负载和 Flash 占用时间。
- NvM 写请求队列可能堆积，影响其他重要数据块的保存。
- 如果同一个状态短时间反复变化，保存每个中间状态通常没有意义。
- 写入过程中断电还可能增加数据一致性处理的复杂度。
- 
`Immediate` 表示尽快发起持久化请求，不表示同步写完；Event Memory 容量与 Flash 写入频率是两个独立概念。


# Indicator 与 Healing

Indicator 是故障指示灯，例如：

- 仪表故障灯
- MIL 灯
- 制动系统警告灯
- 某个软件故障提示状态

Event 需要通过类似下面的关系连接到 Indicator：

```
DemEventParameter
  ↓
DemIndicatorAttribute
  ├─ DemIndicatorRef
  ├─ IndicatorBehaviour
  ├─ FailureCycle/Threshold
  └─ HealingCycle/Threshold
```
![](assets/2026.07.31%20诊断其他功能/file-20260803142116275.png)
### WIR 状态位

DTC 状态字的 bit 7 是：

```
bit7 = WarningIndicatorRequested
```

也就是你之前看到的：

```
StatusOfDTC.Warning indicator requested
```

<mark style="background: #FF5582A6;">**它表示 Dem 是否请求点亮故障指示灯。**</mark>(返回的当前符合的状态 19 02 FF)

需要注意：

> DTC 进入 Confirmed 状态，不代表 WIR 一定置 1。

<mark style="background: #FF5582A6;">只有该 Event 配置了 Indicator，并且达到相应的点灯条件，WIR 才会置位。</mark>

### 什么是 Healing

<mark style="background: #FF5582A6;">Healing 译为“治愈”，主要负责故障指示灯恢复，而不是删除 DTC 记录。</mark>

例如配置：

```
HealingCycleCounterThreshold = 3
HealingCycle = POWER
```

表示故障消失后，需要经历 3 个合格的 POWER 周期，指示灯请求才会被清除。

这里统计的是 Operation Cycle，不是 Runnable 执行次数：

```
第1个无故障POWER周期结束 → HealingCounter = 1
第2个无故障POWER周期结束 → HealingCounter = 2
第3个无故障POWER周期结束 → HealingCounter = 3 → 清除WIR
```

### Healing 和 Aging 的区别

|功能|主要作用|
|---|---|
|Healing|取消故障指示灯请求，清除 WIR|
|Aging|经过多个正常周期后，让历史故障逐渐退出 Confirmed/事件存储|
|ClearDTC|诊断仪通过 `0x14` 主动清除故障记录|

因此可能出现：

```
TestFailed = 0
WIR = 0
ConfirmedDTC = 1
```

含义是：当前故障已经恢复，指示灯也熄灭了，但历史 Confirmed 记录还保留着。

# 第十课：ClearDTC 清除流程

诊断请求：

```
14 FF FF FF
```

含义是：

```
14       ClearDiagnosticInformation
FF FF FF 清除所有支持清除的DTC组
```

成功响应通常是：

```
54
```

### 1. 完整调用流程

```
诊断仪发送 14 FF FF FF
        ↓
Dcm检查长度、会话、安全等级和请求范围
        ↓
Dcm让Dem选择要清除的DTC
        ↓
Dem检查ClearAllowed条件
        ↓
清除RAM中的状态与Event Memory记录
        ↓
通知NvM持久化新的内容
        ↓
NvM → MemIf → Fee → Fls → Data Flash
        ↓
Dcm返回54
```

清除过程中，Dem 可能无法马上完成，所以你之前看到：

```
7F 14 78
```

它表示：

```
7F = 负响应格式
14 = 对服务0x14的响应
78 = Response Pending，处理尚未完成
```

`0x78` 不是最终清除失败，而是告诉诊断仪继续等待。之后应该收到：

```
54
```

或者收到一个最终 NRC。

### 2. 你当前工程的配置

当前配置是：

```
DEM_CFG_CLEAR_DTC_BEHAVIOR_NONVOLATILE_FINISH
```

见 [Dem_Cfg_Clear.h (line 30)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/Dem_Cfg_Clear.h:30)。

它意味着 <mark style="background: #FF5582A6;">Dem 要等待非易失性存储处理完成，才把 ClearDTC 报告为完成。因此清除 10 个 Event Memory 块时，出现一个或多个 `0x78` 是合理现象。</mark>

常见的三种策略是：
![](assets/2026.07.31%20诊断其他功能/file-20260803144421276.png)

|策略|什么时候认为清除完成|
|---|---|
| `VOLATILE` |RAM 清除完成|
| `NONVOLATILE_TRIGGER` |已触发 NvM 写请求|
| `NONVOLATILE_FINISH` |NvM 非易失性处理完成|

你当前使用第三种，响应时间更长，但掉电后重新出现旧记录的风险更低。

### 3. ClearAllowed

Event 可以配置 ClearAllowed 回调，用于决定当前是否允许清除，例如：

```
车速必须为0
点火状态满足
特定会话/安全等级
某个应用条件满足
```

你当前生成配置启用了 Event 级 ClearAllowed 能力：

```
#define DEM_CFG_EVT_CLEARALLOWEDCALLBACK DEM_CFG_EVT_CLEARALLOWEDCALLBACK_ON
```

见 [Dem_Cfg_Events.h (line 86)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/Dem_Cfg_Events.h:86)。

但“功能开启”不代表每个 Event 一定配置了回调，需要继续检查具体 Event 的 `CallbackClearAllowed`。

### 4. 清除 DTC 不等于修复故障

ClearDTC 清除的是 Dem 中的诊断记录，不会修复真实故障源。

例如 CAN CRC 故障仍然存在：

```
收到14请求
→ DTC被清除
→ 监控代码再次检测到CRC错误
→ 再次上报FAILED
→ DTC重新出现
```

因此测试清除功能时，最好先撤销故障注入，否则容易误以为“没有清干净”。






# 第十一课：Event Availability 与 DTC Suppression

<mark style="background: #FF5582A6;">**这两个功能都可能让诊断仪“看不到 DTC”，但含义完全不同。**</mark>

### 1. Event Availability

Event Availability 表示：

> <mark style="background: #FFB86CA6;">这个 Event 在当前车型、变体或系统状态下是否存在、是否可用。</mark>
![](assets/2026.07.31%20诊断其他功能/file-20260803150016860.png)
接口是：

```
Dem_SetEventAvailable(EventId, TRUE);   /* Event可用 */
Dem_SetEventAvailable(EventId, FALSE);  /* Event不可用 */
```

Event 不可用时：

- Dem 不再正常处理该 Event 的测试结果。
- Event 状态被当作不可用状态处理。
- 如果一个 DTC 关联的所有 Event 都不可用，该 DTC 会被抑制，不再出现在普通 DTC 查询结果中。
- 再次设为可用时，Dem 会重新初始化对应 Monitor。

### 2. 它和 EnableCondition 的区别

| 功能       | EnableCondition | Event Availability |
| -------- | --------------- | ------------------ |
| 主要含义     | 当前环境不适合诊断       | 当前 Event 不存在或不适用   |
| 常见用途     | 欠压、初始化未完成       | 车型变体、硬件未安装         |
| 已有故障记录   | 通常继续保留并可读取      | Event/DTC 可能被抑制    |
| 条件恢复     | 继续原来的诊断         | 重新启用并初始化 Monitor   |
| 是否适合频繁切换 | 可以              | 通常不适合              |

例如电压只有 8 V 时，应使用：

```
EnableCondition_BatNormal = FALSE
```

不应该把 Event 设置成 Unavailable，因为电压恢复后，这个诊断功能仍然存在，只是刚才没有合适的检测条件。

Event Availability 更适合这种情况：

```
高配车型安装高度传感器 → Event Available
低配车型没有高度传感器 → Event Unavailable
```

### 3. 当前工程支持什么

当前工程配置为：

```
#define DEM_CFG_SUPPRESSION DEM_EVENT_AVAILABILITY
```

见 [Dem_Cfg_Main.h (line 66)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/Dem_Cfg_Main.h:66)。

因此当前工程主要启用的是 Event Availability 方式，而不是独立的直接 DTC Suppression 方式。

另外，`Dem_GetEventAvailable()` 使用 AUTOSAR 语义：

```
TRUE  = Event可用
FALSE = Event不可用
```

见 [Dem_Cfg.h (line 147)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/Dem_Cfg.h:147)。

### 4. 当前实现有一个重要限制

当前代码在执行：

```
Dem_SetEventAvailable(EventId, FALSE)
```

<mark style="background: #BBFABBA6;">之前会检查 Event 状态。如果 Event 仍有这些状态之一：

- TestFailed
- PendingDTC
- ConfirmedDTC
- WarningIndicatorRequested</mark>

函数会返回 `E_NOT_OK`，不会直接把一个活动故障设置成 Unavailable，见 [Dem_EventFHandling.c (line 1020)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/src/event/Dem_EventFHandling.c:1020)。

<mark style="background: #FF5582A6;">所以不能把 Availability 当成“隐藏当前故障”的随意开关。</mark>

### 5. DTC Suppression

直接 DTC Suppression 主要表示：

> DTC 仍然可能在内部监控和保存，但对诊断读取进行隐藏。
![](assets/2026.07.31%20诊断其他功能/file-20260803150539708.png)
概念上类似：

```

```
Event继续上报FAILED
→ Dem继续处理状态
→ DTC被标记Suppressed
→ 诊断仪通过0x19通常查询不到它


Suppression 不是：

- ClearDTC
- 删除 Event Memory
- 修复物理故障
- 禁止应用继续监控

<mark style="background: #FFB8EBA6;">**只是控制 DTC 的诊断可见性。你当前工程没有配置独立的直接 DTC Suppression 模式。**</mark>






# 第十二课：Component 故障依赖

Component Dependency 用于解决这种情况：

```
一个上游部件故障
→ 导致多个下游功能异常
→ 下游同时上报大量DTC
```

例如：

```
传感器供电故障
├─ 压力传感器信号故障
├─ 高度传感器信号故障
└─ 温度传感器信号故障
```

真正根因可能只有“传感器供电故障”，其他都是连带故障。如果全部保存，Event Memory 会被大量次生故障占用。

### 1. 配置关系

一般配置为：

```
DemComponent：SensorPower
    ↓ ImmediateChildComponentRef
DemComponent：PressureSensor
    ↓
DemEvent：PressureSignalFault
```

主要对象包括：

```
DemComponent
├─ DemComponentId
├─ DemImmediateChildComponentRef
└─ DemComponentIgnoresPriority

DemEventParameter
└─ DemComponentClassRef
```

`DemImmediateChildComponentRef` 用来建立父子依赖关系：

```
上游Component
└─ 下游Component
   └─ 下游Event
```

### 2. 工作原理

假设：

```
Component_A：传感器供电
└─ Component_B：压力传感器
```

处理过程可能是：

```
A关联的供电Event上报FAILED
→ Dem判断Component_A失败
→ B是A的下游依赖Component
→ B后续出现的信号故障可能被判断为次生故障
→ 根据依赖、优先级和存储策略决定是否保存B的记录
```

重点是：

> Component Dependency 主要用于根因分析和 Event Memory 过滤，不代表下游应用代码停止检测。

下游 Event 仍可能上报 `FAILED`，只是 Dem 会结合依赖关系判断它是不是值得作为独立根因保存。

### 3. 它不自动修复故障

上游 Component 恢复后，不代表下游 DTC 立即全部清除：

```
上游恢复
→ 下游重新具备有效检测条件
→ 下游Monitor需要重新报告PASSED
→ 再按Healing、Aging或ClearDTC处理历史状态
```

Component 恢复只是依赖条件恢复，不等于执行 `0x14`。

### 4. 与其他 Condition 的区别

|功能|判断依据|主要目的|
|---|---|---|
|EnableCondition|电压、初始化等环境条件|当前能否可信地检测|
|StorageCondition|外部存储许可|故障能否写入 Event Memory|
|Component Dependency|其他部件是否已故障|区分根因与次生故障|
|Event Availability|Event 当前是否适用|车型/变体动态可用性|

### 5. 当前工程状态

当前工程没有启用 Component Dependency：

```
#define DEM_CFG_DEPENDENCY DEM_CFG_DEPENDENCY_OFF
```

见 [Dem_Cfg.h (line 131)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/Dem_Cfg.h:131)。

所以当前项目中的 DTC 不会通过 Dem Component 树自动判断根因和次生故障。各 Event 主要还是依靠：

```
Priority
EnableCondition
StorageCondition
Event Memory displacement
```

进行处理。
