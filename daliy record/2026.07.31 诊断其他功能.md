### 2. 四种上报状态的区别

```
DEM_EVENT_STATUS_PREFAILED
DEM_EVENT_STATUS_PREPASSED
DEM_EVENT_STATUS_FAILED
DEM_EVENT_STATUS_PASSED
```

含义：

- `PREFAILED`：监控认为存在故障倾向，由 Dem 执行配置的去抖。
- `PREPASSED`：监控认为正在恢复，由 Dem 执行恢复去抖。
- `FAILED`：应用已经完成去抖，直接告诉 Dem 最终失败。
- `PASSED`：应用已经完成去抖，直接告诉 Dem 最终通过。

因此，如果使用：

```
DEM_EVENT_STATUS_FAILED
```

通常不会等待配置的 `0.3s`，因为应用已经给出了最终结果。要验证 Dem 的时间去抖，需要周期上报：

```
DEM_EVENT_STATUS_PREFAILED
```

<mark style="background: #FF5582A6;">`FAILED` 是最终判定，`PREFAILED` 才是交给 Dem 继续去抖。下一步进入 Operation Cycle、Pending 和 Confirmed，因为老化、快照触发、状态位变化都依赖它们。</mark>

> <mark style="background: #FF5582A6;">`FAILED` 可以绕过去抖，却不一定绕过 Confirmed 的确认周期策略。</mark>


配置见：

[RTA_BIP_Dem_EcucValues.arxml (line 29151)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/ecu_config/bsw/gen/RTA_BIP_Dem_EcucValues.arxml:29151)

### 1. POWER Operation Cycle

可以先把它理解为一次 ECU 运行周期：

```
ECU上电/周期开始
       │
       │ 监控执行
       │
ECU下电/周期结束
```

它是逻辑周期，不应简单理解成“程序运行一次”或者“Runnable 执行一次”。

Operation Cycle 通常由 EcuM、BswM 或应用通过类似接口控制：
![](assets/2026.07.31%20诊断其他功能/file-20260731133240510.png)

```
Dem_SetOperationCycleState(
    OperationCycleId,
    DEM_CYCLE_STATE_START
);

Dem_SetOperationCycleState(
    OperationCycleId,
    DEM_CYCLE_STATE_END
);
```

### 2. 与状态位的关系

一个新周期开始时：

- `TestFailedThisOperationCycle` 重新开始统计。
- `TestNotCompletedThisOperationCycle` 先置位。
- 监控执行完成后，`TestNotCompletedThisOperationCycle` 清零。
- 如果本周期出现过失败，`TestFailedThisOperationCycle` 置位。
- 即使故障随后恢复，该位通常也表示“本周期曾经失败过”。

因此：

```
TestFailed
```

表示当前故障结果；而：

```
TestFailedThisOperationCycle
```

表示本周期是否曾经失败过。

二者不能混为一谈。

### 3. Confirmation Threshold

当前配置：

```
DemEventConfirmationThreshold = 1
```

表示第一次有效故障周期就可以达到确认要求。因此你看到：

```
StatusOfDTC = 0x2F
```

其中 `PendingDTC` 和 `ConfirmedDTC` 都已经置位。

如果改成：

```
DemEventConfirmationThreshold = 2
```

可以理解为需要两个满足条件的故障 Operation Cycle，才能成为 Confirmed DTC。

重点是：

```
10ms Runnable调用100次 FAILED
```

不等于经历 100 个 Operation Cycle。它仍可能只是同一个 POWER 周期中的重复上报。

### 4. RecoverableInSameOperationCycle

当前配置：

```
DemEventRecoverableInSameOperationCycle = true
```

表示本周期内故障成立后，如果随后报告有效的 `PASSED`，当前 `TestFailed` 可以在同一个周期恢复。

但是以下历史状态不一定同时消失：

- PendingDTC
- ConfirmedDTC
- TestFailedThisOperationCycle
- TestFailedSinceLastClear

所以故障恢复不等于 DTC 记录被清除。

### 2. 如何连接到 NVM

```mermaid
flowchart LR
    A["Dem Event Memory<br/>RAM数组"] --> B["Dem NvM映射<br/>NVM_ID_EVMEM_LOC_x"]
    B --> C["NvM<br/>逻辑NVRAM块"]
```

Dem_EvMemEventMemory[1] → NVM_ID_EVMEM_LOC_ 1
...
Dem_EvMemEventMemory[9] → NVM_ID_EVMEM_LOC_ 9

#### 写入过程

故障满足存储条件后：

1. Dem 更新 RAM 中的 Event Memory Entry。
2. Dem 调用或触发 `NvM_WriteBlock()`。
3. NvM 将写请求排队。
4. MemIf 把请求交给 Fee。
5. Fee 进行磨损均衡和逻辑地址管理。
6. Fls 驱动把数据写入 Data Flash。
7. 写完后，结果逐层返回 Dem。

因此应用和 Dem 通常不操作物理 Flash 地址。它们只使用 NvM Block ID。物理 Flash 位置由 Fee 管理，可能随着磨损均衡而变化。

#### 上电读取过程

上电时方向相反：

```
Data Flash → Fls → Fee → NvM → Dem回调 → Event Memory RAM数组
```

当前工程通过显式同步回调在 NvM 缓冲区和 Dem RAM 数组之间复制：

[Dem_NvmCallbacks.c (line 28)](E:/github/ECAS_qirui_Single_Chamber/BasicSoftware/src/bsw/Dem/src/nvm/Dem_NvmCallbacks.c:28)

这也是为什么：

- RAM 掉电会丢失；
- 但已经成功写入 Fee/Data Flash 的 DTC，上电后仍能恢复；
- 如果 NvM 写入尚未完成就断电，最新记录可能丢失。


### 3. 什么是冻结帧（就是快照）
冻结帧 `Freeze Frame` 在 UDS 里也经常叫 `Snapshot Record`。

它表示：

> 故障达到指定触发状态时，把那一瞬间的一组环境数据拍照保存下来。

例如故障发生时保存：

```
电源电压
电机转速
压力值
温度
车速
里程
时间
传感器原始值
```

它解决的问题是：

> 维修人员之后读取 DTC 时，怎么知道故障发生时车辆处于什么工况？

例如：

```
DTC：电机过温
当前温度：45℃
冻结帧温度：132℃
故障发生时转速：7000 rpm
故障发生时电压：28.5 V
```

虽然现在温度恢复了，但冻结帧保留了故障发生瞬间的数据。
#### 冻结帧配置关系

```
DataElementClass
        ↓
DidClass
        ↓
FreezeFrameClass
        ↓
FreezeFrameRecordClass
        ↓
FreezeFrameRecNumClass
        ↓
DTCAttributes
```

各自作用：

- `DataElementClass`：数据从哪里读取、长度和类型是什么。
- `DidClass`：把一个或多个 Data Element 组成一个 DID。
- `FreezeFrameClass`：这条快照包含哪些 DID。
- `FreezeFrameRecordClass`：记录号、触发时机、是否允许更新。
- `FreezeFrameRecNumClass`：一个 DTC 允许使用哪些记录号。
- `DTCAttributes`：把 Freeze Frame 配置绑定到具体 DTC。

# 冻结帧


先理解配置对象之间的关系：

```
DTC 0x416001
    ↓
DTCAttributes
    ↓
FreezeFrameClass
    ↓
DidClass
    ↓
DataElementClass
    ↓
ReadData函数/端口
```
![](assets/2026.07.31%20诊断其他功能/file-20260731145556232.png)
![](assets/2026.07.31%20诊断其他功能/file-20260731150013425.png)

可以把它理解成一份“冻结帧采集配方”：

```
DTC 0x416001
  └─ DTCAttributes：这个 DTC 使用哪套存储规则
      └─ FreezeFrameClass：冻结帧由哪些 DID 组成
          └─ DidClass：其中一个数据项的标识符，例如 DID 0x007B
              └─ DataElementClass：该 DID 具体包含什么数据、类型和长度
                  └─ ReadData：运行时真正读取当前数据值
```

各层的职责如下：

|配置层|作用|
|---|---|
|`DTC 0x416001`|故障代码本身|
|`DTCAttributes`|设置优先级、存储位置、冻结帧类、扩展数据类等|
|`FreezeFrameClass`|定义一条冻结帧需要记录哪些 DID|
|`DidClass`|定义冻结帧中的一个数据标识符，以及它包含哪些 DataElement|
|`DataElementClass`|定义单个数据元素的类型、大小以及取数方式|
|`ReadData`|在故障触发时读取应用程序的实时数据，交给 Dem 保存|

<mark style="background: #FF5582A6;">这条链的核心作用是：**告诉 Dem，在 DTC 触发冻结帧时，需要采集哪些现场数据，以及去哪里读取这些数据。**</mark>


另一条链决定“什么时候拍、保存为几号记录”：

```
DTCAttributes
    ↓
FreezeFrameRecNumClass
    ↓
FreezeFrameRecordClass
    ├─ RecordNumber
    ├─ Trigger
    └─ Update
```
![](assets/2026.07.31%20诊断其他功能/file-20260731150929525.png)
这里的“记录号”可以理解为：**同一个 DTC 的多个冻结帧槽位编号**。它不是 DTC 编号、DID，也不是 Event Memory 的第几个 Entry。
测试仪读取冻结帧时，必须告诉 ECU 读取哪个槽位。
19 04 41 60 01 01
│  │  └──────┘ └─ Snapshot Record 0 x 01
│  └─ DTC 0 x 416001
└─ 读取 DTC 冻结帧
### 为什么一个 DTC 可以有两个记录

因为一个故障在其生命周期中可能需要保存多个时刻的现场，例如：

| 记录       | 触发时刻    | 可能保存的意义         |
| -------- | ------- | --------------- |
| Record 1 | 第一次检测失败 | 故障刚出现时的环境       |
| Record 2 | 故障被确认   | 故障持续存在、正式成立时的环境 |
|          |         |                 |
你配置了两个冻结帧槽位，但两个槽位具有完全相同的触发条件。

当 `ConfirmedDTC` 从 0 变为 1 时，两个记录都会匹配同一个触发条件，采集的内容和时间点基本相同。因此在当前设计下，Record 1 和 Record 2 很可能是重复数据，第二个记录没有体现出明显的诊断价值。

注意：`ON_CONFIRMED` 在你这个 Dem 实现中是状态的**上升沿触发**，代码检查的是 Confirmed 位从 0 变成 1；它不是每次上报 `FAILED` 都触发。

### Event Memory 具体的格式

一个 Event Memory Entry：NvM 分配 72 字节
├─ Event/DTC 标识
├─ 状态及内部管理信息
├─ FailureCounter
├─ OccurrenceCounter
├─ AgingCounter
├─ FreezeFrameCounter
├─ Trigger
├─ TimeId
├─ Extended Data：1 字节
├─ Freeze Frame Record 1：1 字节
└─ Freeze Frame Record 2：1 字节


Q : DTC 进入 Confirmed 时，Dem 通过什么方式取得要保存的那 1 字节数据？

应用变量/传感器值
        ↓
提供方 SWC 的 ReadData Runnable
        ↓
RTE 端口与 AssemblySwConnector
        ↓
Dem 调用 Rte_Call_..._ReadData()
        ↓
Dem 获得当前数据
        ↓
保存进 Event Memory
        ↓
后续通过 NvM 写入 Data Flash

所以必须区分两个阶段：

```
ReadData：从应用程序采集实时现场值
NvM：把已经采集的冻结帧持久化到 Data Flas
```



# Extended Data（扩展数据）


**<mark style="background: #FF5582A6;">冻结帧记录的是“故障发生时现场是什么样”，扩展数据记录的是“这个故障经历了什么”。</mark>**

| 项目     | 冻结帧 Snapshot      | 扩展数据 Extended Data   |
| ------ | ----------------- | -------------------- |
| 主要用途   | 保存故障时的环境          | 保存计数、历史和辅助信息         |
| 典型内容   | 电压、温度、转速          | 发生次数、老化计数、FDC        |
| 数据组织   | DID + DataElement | Record + DataElement |
| UDS 读取 | `19 04`           | `19 06`              |

例如：

```
DTC 0x416001

冻结帧：
  故障确认时电压 = 9V
  温度 = 90℃
  转速 = 2000rpm

扩展数据：
  故障发生次数 = 5
  老化计数 = 2
  最大 FDC = 127
```

```
FDC 是 **Fault Detection Counter（故障检测计数器）**，用于表示故障当前“偏向正常”还是“偏向故障”的程度。

完全正常                                    故障完全成立
-128  ←──────────────  0  ───────────────→  +127

对于计数器去抖，每次上报通常按照配置的步长增加或减少内部计数；对于时间去抖，则根据 `PREFAILED/PREPASSED` 持续时间换算成 FDC。
```


### 配置引用链

```
DTCAttributes
    ↓
ExtendedDataClass
    ↓
ExtendedDataRecordClass
    ├─ RecordNumber
    ├─ Trigger
    ├─ Update
    └─ DataElementClassRef
```
![](assets/2026.07.31%20诊断其他功能/file-20260731155235377.png)
参数含义：

- `RecordNumber`：扩展数据记录号，例如 `0x01`；
- `Trigger`：什么时候采集，例如 Confirmed；
- `Update`：再次出现相应触发时，是否允许覆盖旧值；
- `DataElementClassRef`：这条记录具体保存哪些数据。

扩展数据的 Record 1 和冻结帧的 Record 1 是两个独立概念，不会相互冲突。

### 两种数据来源

扩展数据可以来自 Dem 内部：

```
OccurrenceCounter
AgingCounter
FailedCycles
CurrentFDC
MaxFdcSinceLastClear
```

这种数据由 Dem 自己维护，通常不需要连接应用 SWC。

也可以来自应用程序：

```
应用累计故障时间
特定软件状态
传感器统计值
```

这种数据需要通过 RTE `ReadData` 从 SWC 获取。

### 诊断读取

读取 `0x416001` 的扩展数据 Record 1：

```
19 06 41 60 01 01
│  │  └──────┘ └─ Extended Data Record 0x01
│  └─ DTC 0x416001
└─ ReadDTCInformation
```

预期正响应开头：

```
59 06 41 60 01 ...
```



### 冻结帧和扩展数据最核心的区别
扩展数据可以保存与冻结帧相同的“数据内容”，但它不会因此变成冻结帧记录。

例如，故障确认时的电压 `9V`：

```
放进冻结帧：
  作为现场环境数据
  使用 19 04 读取

放进扩展数据：
  作为扩展数据字段
  使用 19 06 读取
```

区别不在于“能否保存这个字节”，而在于它被哪套配置组织、用哪个诊断服务读取：

| 区别        | 冻结帧                | 扩展数据                  |
| --------- | ------------------ | --------------------- |
| 配置入口      | `FreezeFrameClass` | `ExtendedDataClass`   |
| 数据组织      | DID 及其 DataElement | Record 及其 DataElement |
| 典型语义      | 故障瞬间的环境            | 历史、计数和辅助信息            |
| UDS 读取    | `19 04`            | `19 06`               |
| 是否能读取应用数据 | 可以                 | 可以                    |

例如将电压配置到 Extended Data：

```
ExtendedData Record 1
  Trigger = ON_CONFIRMED
  Update  = NO
  DataElement = 当前电压
```

它确实会保存确认故障时的电压，看起来很像快照；但测试仪必须使用：

```
19 06 41 60 01 01
```

而使用 `19 04` 读不到它，因为它不属于 `FreezeFrameClass`。

你的工程甚至把同一个 `DemDataElementClass_0` 同时用于冻结帧和扩展数据。如果端口接通，并且两者都在 Confirmed 时触发，相同的 1 字节应用值可能同时被存进两种记录：

```
同一个应用数据
├─ Freeze Frame Record → 19 04
└─ Extended Data Record → 19 06
```

工程设计上建议：

- 电压、温度、转速等故障现场 → 冻结帧；
- 发生次数、老化计数、FDC、失败周期数 → 扩展数据；
- 客户诊断规范明确要求通过哪个服务读取 → 严格按照规范配置。

所以最准确的结论是：**内容可以相同，但记录类型、诊断语义和读取接口不同。**
