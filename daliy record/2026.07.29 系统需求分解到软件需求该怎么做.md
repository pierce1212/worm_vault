如果采用“每条系统需求下面机械地展开一串软件需求”的方式，需求数量会迅速膨胀、重复，最后很难维护。
正确做法不是一对一分解，而是：

> <mark style="background: #FF5582A6;">先对系统需求进行架构分配，再按照软件功能重新组织软件需求，最后用追溯矩阵建立多对多关系。</mark>

## 1. 系统需求和软件需求不是父子目录关系

实际追溯通常是多对多：

- 一条系统需求可能分配到软件、硬件、机械和系统测试。
- 多条系统需求可能共同派生一条软件需求。
- 一条公共软件需求可能支持多个系统需求。
- 软件还可能产生初始化、诊断、异常处理等派生需求。

例如：

```
SYS：0→14 bar时间≤135 s
├─ 软件：充气控制、时间监控、压力判断
├─ 硬件：压缩机流量和驱动能力
├─ 气路：泄漏率、流阻和罐体容积
└─ 系统测试：全温度和电压范围验证
```

软件需求文档中不需要再把这棵树完整复制一遍。

## 2. 推荐使用四层结构

### 第一层：系统需求

描述整机对外行为，例如：

- 充气性能；
- 工作温度；
- 压力控制；
- 通信功能；
- 故障处理；
- 诊断功能。

### 第二层：系统架构和分配矩阵

这一层回答“由谁实现”。

|系统需求|软件|电子硬件|机械/气路|系统验证|
|---|---|---|---|---|
|0→14 bar 时间≤135 s|部分|部分|部分|是|
|压力采集|部分|部分|否|是|
|压缩机驱动|控制命令|功率输出|压缩机|是|
|耐压要求|否|可能|是|是|

这里的“部分”还应补充具体责任说明，而不只是打勾。

### 第三层：软件需求规格书

软件需求按照软件功能组织，不按照系统需求 ID 组织。ASU 可以采用：

```
1. 软件运行模式与状态
2. 输入信号处理
   2.1 压力信号
   2.2 温度信号
   2.3 供电电压
   2.4 外部控制请求
3. 充气控制
   3.1 充气启动条件
   3.2 压缩机控制
   3.3 目标压力判断
   3.4 充气完成处理
4. 执行器控制
   4.1 压缩机
   4.2 阀门
5. 时间监控
6. 故障诊断与降级
7. 标定参数
8. AUTOSAR接口与时序要求
9. 非功能需求
```

这样阅读软件需求时，可以完整理解软件自身应做什么。

### 第四层：双向追溯矩阵

通过需求管理工具建立关系，而不是靠文档目录表示关系。

|软件需求|上游来源|类型|
|---|---|---|
| `SWR_PRS_001` 压力周期获取|压力采集系统需求|分配|
| `SWR_CTL_001` 接受充气请求|充气功能系统需求|分配|
| `SWR_CTL_002` 输出压缩机启动命令|充气功能、135 s 性能需求|分配|
| `SWR_CTL_003` 判断达到 14 bar|压力控制、135 s 性能需求|分配|
| `SWR_TIM_001` 监控充气持续时间|135 s 性能需求|分配|
| `SWR_DIA_001` 报告充气超时|135 s 性能需求、诊断需求|分配/派生|
| `SWR_DIA_002` 处理压力信号无效|安全分析/软件架构|派生|

## 3. 对 135 s 需求，不要无限分解

这条系统需求在软件侧可以只追溯到几条真正相关的核心需求：

1. 接受充气请求后及时启动压缩机；
2. 充气过程中执行压力控制；
3. 达到目标压力后及时结束充气；
4. 监控本次充气时间；
5. 超时后执行故障处理；
6. 满足所分配的软件响应时间。

压力采样、ADC 配置、OS 任务周期等，不需要在这条系统需求下全部复制一遍。这些可以作为公共软件需求，由多个上层需求共同引用。

例如：

```
SWR_PRS_001：软件应每10 ms获取一次有效气罐压力。
```

它可能同时支持：

- 充气时间性能；
- 目标压力控制；
- 过压保护；
- 泄漏诊断；
- 压力信号输出。

因此它只写一次，然后建立多个追溯链接。

## 4. 软件需求应该具体到什么程度

在 ASPICE 的 `SWE.1` 层面，一般具体到能够独立验证软件外部行为：

- 在什么状态下；
- 收到什么输入或触发；
- 软件应执行什么行为；
- 输出什么结果；
- 多长时间内完成；
- 异常输入时如何处理；
- 哪些参数允许标定；
- 通过什么接口交互。

例如：

> <mark style="background: #FFB86CA6;">当软件接受有效充气请求且所有充气允许条件均满足时，软件应在 20 ms 内输出压缩机运行请求。</mark>

这是一条合适的软件需求。

而下面这些通常偏向架构、详细设计或 AUTOSAR 配置：

- 由 `AirSupplyControlSwc` 中的 `Runnable_10ms` 实现；
- Runnable 映射到 `Task_10ms`；
- Task 优先级为 5；
- ADC 使用 Group 2、Channel 4；
- Dem Event ID 为 `0x1234`；
- NvM Block ID 为 15。

它们应放在：

- `SWE.2` 软件架构；
- 软件详细设计；
- ECU Configuration；
- ARXML；
- BSW 配置说明。

除非某个具体实现约束是客户明确指定的，否则不要全部塞进软件需求。

## 5. 控制需求混乱的几个实用规则

- 一条需求尽量只描述一个可验证行为。
- 公共输入处理需求只写一次，不在每个功能中重复。
- 软件需求按功能域组织，系统需求 ID 通过工具链接。
- 区分“上层分配需求”和“软件派生需求”。
- 标定项必须有默认值、单位、范围和使用条件。
- 不要把系统验证指标直接改写成“软件应保证”。
- 不要把 AUTOSAR 配置参数全部当成软件需求。
- 一个系统需求没有对应软件需求不一定是错误，它可能完全分配给硬件或机械。
- 一个系统需求对应多条软件需求也是正常的，重点是覆盖完整而非数量一致。

所以，避免混乱的关键不是减少必要的软件需求，而是把“需求内容的组织”和“上下游追溯关系”分开管理。软件需求文档面向软件功能，追溯矩阵负责证明每条系统需求都被正确覆盖。
