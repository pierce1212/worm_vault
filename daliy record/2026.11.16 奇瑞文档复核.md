| 客户条目            | 展示重点             | 建议依次打开的证据                           |
| --------------- | ---------------- | ----------------------------------- |
| 1.2.1 获得并理解客户需求 | 需求从哪里来，怎样理解和确认   | 原始输入 → 涉众需求 → 澄清/评审记录 → 需求基线        |
| 1.2.2 需求分解      | 客户要求怎样转化成系统、软件要求 | 系统需求 → 软件需求 → 分类与分配 → 上下游追溯         |
| 1.2.3 需求分析与确认   | 怎样判断正确、可行、可验证    | 需求分析字段 → 接口和环境影响 → 风险分析 → 评审及整改     |
| 1.2.4 验证准则      | 怎样判断一条需求是否满足     | 需求中的验证准则 → 对应测试用例及预期结果              |
| 1.2.5 需求变更      | 变更怎样受控并保持一致      | 变更申请 → 影响分析 → 审批 → 修改与回归验证 → 新基线及关闭 |
| 1.3.1 架构与详细设计   | 需求怎样落实到设计和实现     | 系统架构 → 软件架构 → 单元详设 → 追溯 → 实现版本      |
| 1.3.2 接口及动态行为   | 各部分怎样交互          | 接口定义 → 时序/状态机 → 单元交互 → 评审或验证        |
| 1.3.3 详细设计评估    | 怎样证明设计经过充分评价     | 评估准则 → 当前版本评审记录 → 问题整改与关闭           |


| 目录      | 主要用途                       | 你这套资料中的典型内容                      |
| ------- | -------------------------- | -------------------------------- |
| **版本库** | 管理开发过程中持续编写、修改和发布的工作产品     | 项目管理计划、软件架构设计、软件详细设计、测试计划及报告     |
| **存储库** | 保存开展活动时形成的记录，证明活动执行情况      | 评审检查单、评审问题及整改记录、变更申请、追溯矩阵、配置审计记录 |
| **基线库** | 保存经过评审、批准，作为后续开发或交付依据的确定版本 | 已批准的涉众需求、系统需求、软件需求基线             |
1. 在**版本库**中编写和修改架构设计，形成 V 0.1、V 0.2 等版本。
2. 开展评审，将检查结果、发现的问题及关闭情况保存在**存储库**。
3. 评审通过后，批准指定版本并建立**基线**。后续修改按变更流程处理。

“我们将开发工作产品、过程执行记录和已批准基线分类管理。版本库展示开发成果，存储库提供评审、变更和审计等执行证据，基线库明确当前受控的开发依据”



**建议以客户评价细则作为展示主线，用 ASPICE 解释方法，用现有文档和记录证明落实情况。**这样客户能直接找到评分依据，也能看出你的开发过程是系统化的。
