### 顶部工具栏的 ▶ GO

对应 TRACE 32 命令：

```
Go
```

作用：

- **从当前 PC 继续执行；**
- **不重新连接目标；**
- **正常情况下不主动复位；**
- **已设置的断点继续有效**。



程序停在 `CanNm_MainFunctionTx` 后，想继续运行，应该点击这个顶部三角形按钮。

### `SYStem.state` 窗口里的 Mode → Go

对应命令：

```
SYStem.Mode Go
```

它不是“继续运行”，而是切换调试系统工作模式。通常会执行类似：

```
建立/重新建立调试连接
→ 按当前 Reset 配置初始化目标
→ 让 CPU 运行
```

根据 TRACE 32 的启动脚本、`EnReset`、复位方式和芯片配置，它可能让目标重新复位或重新初始化，然后运行。因此不应该用它来从普通断点继续执行。

你当前 `SYStem.state` 中选中的是：

```
Up
```

这表示调试器已连接并控制 CPU。此时如果点击左边的 `Go` 单选项，就是执行 `SYStem.Mode Go`，不是普通的继续运行。

结论：

- 断点后继续执行：点击顶部工具栏的 ▶。
- 不要点击 `SYStem.state → Mode → Go`。
- `SYStem.state → Go` 主要用于调试系统初始启动/模式切换，可能触发复位。

如果你之前点击的是第二个 GO，那么 `bsw_1ms_counter` 清零，很可能是 TRACE 32 切换系统模式时主动重新初始化或复位目标，而不是业务代码从 `CanNm_MainFunctionTx` 继续运行后自行复位。


# CAN 修改后的唤醒休眠逻辑梳理


这两个提交是一前一后的关系：

`c066bb7b` 是一次完整的 CAN 被动唤醒/休眠架构调整；`66ad9b48` 是针对它遗留下来的“响应帧异常”做的小范围修正。

## `c066bb7b`：被动唤醒与休眠流程重构

提交：

```
c066bb7bc8dc0603b9f95e4621ce83b855b16428
passive wakeup process and shutdown improvment
```

这个提交修改了 EcuM、BswM、CanIf、CanNm、CanTrcv 和 ExeMgr，目标是把唤醒处理重新放回 AUTOSAR 标准链路。

## 2.1 CanNm 参数调整

ISOLAR 配置源：

```
BasicSoftware/ecu_config/bsw/gen/RTA_BIP_CanNm_EcucValues.arxml
```

修改了三个关键参数。

### Immediate NM 数量：20 → 0

```
<CanNmImmediateNmTransmissions>
    20 → 0
</CanNmImmediateNmTransmissions>
```

生成结果：

```
20 → 0  /* Number of Immediate Nm Pdus */
```

原来的 20 表示主动 Network Request 后，会按照 Immediate 周期快速发送 20 帧。

当前 Immediate 周期是：

```
CanNmImmediateNmCycleTime = 20 ms
```

因此旧配置倾向于产生：

```
t0
t0 + 20 ms
t0 + 40 ms
...
```

它并不是要求的 1 秒周期响应。

改为 0 以后，不再使用 Immediate 突发序列，而是使用：

```
CanNmMsgCycleOffset
CanNmMsgCycleTime
CanNmRepeatMessageTime
```

控制被动唤醒响应。

### Repeat Message 时间：1 秒 → 4 秒

```
<CanNmRepeatMessageTime>
    1.0 → 4.0
</CanNmRepeatMessageTime>
```

生成结果：

```
1000000 → 4000000
```

结合：

```
CanNmMsgCycleOffset = 0 s
CanNmMsgCycleTime   = 1 s
```

理论发送时序为：

```
t0       第1帧
t0 + 1s  第2帧
t0 + 2s  第3帧
t0 + 3s  第4帧
t0 + 4s  Repeat Message结束
```

因此这里的设计目标就是：被动唤醒后总计响应 4 帧。

### Node ID：0 → 11

```
<CanNmNodeId>
    0 → 11
</CanNmNodeId>
```

生成值：

```
0x0 → 0xB
```

这对应响应报文 `0x60B` 的第一个字节：

```
0B 00 02 00 00 00 00 00
^^
Node ID = 0x0B
```

这一项修正了 NM 响应报文中的本节点标识。

## 2.2 CanIf 将唤醒验证交给 EcuM

CanIf 配置新增：

```
CanIfDispatchUserValidateWakeupEventUL = ECUM
```

生成回调从：

```
NULL_PTR
```

改为：

```
&EcuM_ValidateWakeupEvent
```

位置在 `CanIf_Callback.User_ValidateWakeupEvent`。

修改前：

```
CanIf检测到有效唤醒报文
    ↓
没有上层验证回调
```

修改后：
![](assets/2026.08.21%20唤醒只响应一帧问题排查/file-20260825141408754.png)
```
CanIf检测到配置允许的唤醒报文
    ↓
EcuM_ValidateWakeupEvent()
    ↓
EcuM将CAN唤醒源从PENDING变为VALIDATED
```

**<mark style="background: #FF5582A6;">这一步非常关键，因为 CAN 唤醒验证不再由 ExeMgr 猜测或手工完成，而由 CanIf 收到真实报文后通知 EcuM。</mark>**

## 2.3 EcuM StartWakeupSources 真正启动 CanSM 唤醒

修改前：

```
void EcuM_StartWakeupSources(...)
{
}
```

修改后：

```
if(CAN wakeup source)
{
    EcuM_CanWakeupStartPending_b =
        (E_OK != CanSM_StartWakeupSource(CAN_CHANNEL));
}
```

作用是：
![](assets/2026.08.21%20唤醒只响应一帧问题排查/file-20260825142459940.png)
```
EcuM发现CAN唤醒
    ↓
调用CanSM_StartWakeupSource()
    ↓
CanSM把收发器、控制器、CanIf逐步带到可验证状态
```

增加的：

```
EcuM_CanWakeupStartPending_b
```

用于处理一个实际启动时序问题：<mark style="background: #FF5582A6;">EcuM 发现唤醒时，CanSM 可能还没初始化完，此时 `CanSM_StartWakeupSource()` 会返回失败。</mark>

所以代码不立即放弃，而是锁存：

```
EcuM_CanWakeupStartPending_b = TRUE
```

后续在 `EcuM_CheckValidation()` 中重试。

---

## 2.4 EcuM CheckValidation 改为使用 CanIf 验证

修改后 CAN 唤醒验证流程为：

```
if(CAN wakeup source)
{
    if(StartWakeupSource previously failed)
    {
        retry CanSM_StartWakeupSource();
    }

    CanIf_SetPduMode(..., CANIF_OFFLINE);
    CanIf_CheckValidation(wakeupSource);

    if(CAN wakeup validated)
    {
        CanIf_SetTrcvWakeupMode(..., CANTRCV_WUMODE_CLEAR);
    }
}
```

它解决了三个问题。

### 第一：CanSM 未就绪时允许重试

避免早期唤醒请求丢失。

### 第二：由 CanIf 检查真正的唤醒报文

```
CanIf_CheckValidation(wakeupSource);
```

CanIf 根据配置的 Rx PDU 和唤醒源，判断收到的报文是否是合法唤醒帧。

### 第三：验证成功后再清除收发器 WUF

```
CanIf_SetTrcvWakeupMode(..., CANTRCV_WUMODE_CLEAR);
```

旧逻辑可能在应用确认前就清除唤醒原因，造成：

- 后续读取不到唤醒原因；
- EcuM 认为唤醒无效；
- 唤醒事件丢失。

新逻辑改为：

```
检测到WUF
  → 启动CanSM
  → 收到有效CAN报文
  → CanIf验证
  → EcuM标记VALIDATED
  → 最后清WUF
```

---

## 2.5 EcuM CheckWakeup 取消直接请求 FullCom

修改前：

```
void EcuM_CheckWakeup(...)
{
    ComM_RequestComMode(0, COMM_FULL_COMMUNICATION);
    CanIf_CheckWakeup(wakeupSource);
}
```

修改后：

```
void EcuM_CheckWakeup(...)
{
    (void)CanIf_CheckWakeup(wakeupSource);
}
```

这是一次重要的职责修正。

`EcuM_CheckWakeup()` 的职责应该是：

```
检查是否存在唤醒事件
```

而不是：

```
无条件向ComM请求FullCom
```

旧逻辑一旦检测 CAN 唤醒，就主动保持 FullCom，会使 CanNm 的网络状态成为：

```
CANNM_NETWORK_REQUESTED
```

然后 CanNm 可能从：

```
REPEAT_MESSAGE
```

进入：

```
NORMAL_OPERATION
```

结果就是 1 秒周期一直发送。

删除这行以后，被动唤醒时可以保持：

```
CANNM_NETWORK_RELEASED
```

Repeat Message 到期后就能进入 Ready Sleep。

## 2.6 EcuM Enable/Disable/StopWakeupSources 补全

### EnableWakeupSources

```
CanIf_SetTrcvWakeupMode(..., CANTRCV_WUMODE_ENABLE);
```

允许 CanTrcv 向 EcuM 报告新的总线唤醒事件。

### DisableWakeupSources

```
CanIf_SetTrcvWakeupMode(..., CANTRCV_WUMODE_DISABLE);
```

在不允许唤醒的阶段关闭通知。

### StopWakeupSources

```
EcuM_CanWakeupStartPending_b = FALSE;
CanSM_StopWakeupSource(...);
CanIf_SetTrcvWakeupMode(..., CANTRCV_WUMODE_CLEAR);
```

当唤醒验证失败或停止验证时：

- 取消未完成的 StartWakeup；
- 通知 CanSM 停止唤醒流程；
- 清除收发器保存的 WUF。

这让 EcuM 唤醒源的生命周期完整闭环。

## 2.7 CanTrcv 清 WUF 行为修正

`CanTrcv_PrepareWakeUp.c` 中，旧逻辑执行 CLEAR 时：

```
CanTrcv_CurrentWakeupMode = CANTRCV_WUMODE_CLEAR;
```

新逻辑删除了这行，只清除：

```
CanTrcv_TrcvWakeupReason = CANTRCV_WU_NOT_SUPPORTED;
CanTrcv_CurrentWakeupFlag = FALSE;
ClearTrcvWufRqst = TRUE;
```

原因是：

```
CLEAR是动作，不应该成为长期模式
```

正确语义是：

- `ENABLE`：允许报告唤醒；
- `DISABLE`：禁止报告唤醒；
- `CLEAR`：清除已经保存的唤醒事件，但不改变 Enable/Disable 状态。

否则执行一次 CLEAR 后，当前模式会变成 CLEAR，后续可能无法继续正常检测唤醒。

## 2.8 CanTrcv MainFunction 避免重复处理清除中的 WUF

新增判断：

```
(FALSE == CanTrcvPnRqstStatus[...].ClearTrcvWufRqst)
```

完整语义：

```
配置允许Bus Wakeup
并且Channel正在使用
并且当前没有Clear WUF请求
    → 才处理新的Wakeup By Bus
```

作用是避免：

```
刚请求清除WUF
    ↓
MainFunction又读取到旧WUF
    ↓
重复上报同一个唤醒事件
```

## 2.9 删除 CanNm 向应用暴露的 PduRxInd_Flag

旧代码在 CanNm 核心文件中增加了：

```
bool PduRxInd_Flag = FALSE;
```

每次主函数读取 RxIndication 时：

```
PduRxInd_Flag = PduRxInd_b;
```

ExeMgr 依赖这个内部变量判断是否还在接收 NM 报文。

`c066bb7b` 删除了它，也删除了 ExeMgr 中的：

```
extern bool PduRxInd_Flag;
RxLostCnt;
CAN_WAKE_RX_LOST_DELAY_CNT;
Nm_Test[0].IsNmReceived;
```

原因是这是错误的分层：

```
CanNm内部临时状态
    ↓ 通过全局变量泄漏
应用ExeMgr
    ↓ 手工判断网络是否丢失
```

而且 `RxIndication_b` 通常是一次性状态，每次 CanNm MainFunction 都会清零，不适合被应用层当作稳定网络状态。

新方案改为使用：

```
EcuM pending/validated wakeup events
ComM current mode
CanNm标准状态机
CanTrcv wakeup reason
```

## 2.10 BswM 不再主动请求 FullCom

BswM 删除了以下动作：

```
BswM_AI_ComMReqFullComm_Can_Network_ETAS
BswM_AI_ComMReqFullComm_Can_Network2_ETAS
```

它们原来位于：

- `BswM_AL_BswMStartCommForVBat`
- `BswM_AL_BswMSwitchAppRun`

修改前可能出现：

```
ExeMgr请求FullCom
EcuM CheckWakeup请求FullCom
BswM切APP_RUN又请求FullCom
BswM电压动作再次请求FullCom
```

多个请求者使得谁负责释放网络不明确。

修改后，BswM 主要负责：

- Allow/Disable communication；
- 启停 PDU Group；
- 状态仲裁；
- 进入 POST_RUN/OFF。

<mark style="background: #FFF3A3A6;">本地 FullCom 需求改由 ExeMgr 统一表达。</mark>

## 2.11 BswM 关机条件增加 ComM NoCom

关机逻辑表达式新增：

```
COMM_NO_COMMUNICATION ==
    BswM_Cfg_ComMIndicationModeInfo[CAN_CHANNEL].dataMode
```

因此进入关机阶段必须同时满足：

```
IGN wakeup source = NONE
CAN wakeup source = NONE
Application mode  = POST_RUN
ComM channel      = NO_COMMUNICATION
```

这是正确的安全关机条件。

如果不等 ComM 进入 NoCom 就关机，可能发生：

- CanSM 还在关闭控制器；
- CanNm 仍处于 Prepare Bus Sleep；
- PDU 仍在发送；
- NvM/关机流程提前切断通信；
- 下一次唤醒时控制器或收发器状态不一致。

## 2.13 ExeMgr 主状态机重构

这是 `c066bb7b` 最大的应用层变化。

### KL 15 关机延时修正

```
KL15_OFF_DELAY_CNT:
1 → 300
```

主函数周期是 10 ms，所以：

```
300 × 10 ms = 3 s
```

旧值 1 实际只有 10 ms，与注释中的 3 秒不一致。

新逻辑还增加饱和判断：

```
if(delayCount < KL15_OFF_DELAY_CNT)
{
    delayCount++;
}
```

避免无符号计数器持续递增后溢出。

### KL 15 ON 路径

现在明确执行：

```
复位关机延时
禁止关机
清除关机请求锁存
标记CAN曾进入FullCom
请求COMM_FULL_COMMUNICATION
设置IGN wakeup event
验证IGN wakeup event
请求APP_RUN
```

这条路径表达的是本地真实通信需求：

```
点火开启 → ECU主动保持通信
```

### KL 15 OFF 路径

执行：

```
请求COMM_NO_COMMUNICATION
累计3秒防抖
清理旧IGN唤醒事件
记录CAN唤醒事件
等待ComM真实进入NoCom
确认CAN唤醒事件已消费
满足全部条件后请求POST_RUN
```

关机判断从旧的：

```
RE_ExeMgr_ValidateWakeup() == E_NOT_OK
&& isIgnAllowPowerDown
```

改为：

```
isIgnAllowPowerDown
&& ComM_Mode == COMM_NO_COMMUNICATION
&& canWakeupActive == FALSE
```

这比旧逻辑可靠，因为它检查的是系统真实状态，不是一次函数返回值。

### CAN 唤醒验证移交 CanIf

旧代码：

```
RE_ExeMgr_ValidateWakeup()
{
    重新触发GetWakeupSource;
    判断IRV;
    手动CLEAR CanTrcv WUF;
    返回E_OK/E_NOT_OK;
}
```

新代码：

```
RE_ExeMgr_ValidateWakeup()
{
    return IGN_ON ? E_OK : E_NOT_OK;
}
```

并注明：

```
/* CAN wakeup validation is handled by CanIf_CheckValidation(). */
```

也就是说，该函数只负责项目特定的 IGN 验证；CAN 验证完全交给 CanIf/EcuM。

### 不再周期性执行 EvaluateWakeup

旧主函数每个周期调用：

```
RE_ExeMgr_EvaluateWakeup();
```

新代码删除。

原因是 `EvaluateWakeup` 是启动阶段动作，不应每 10 ms 反复执行，否则可能反复：

- SetWakeupEvent；
- ValidateWakeupEvent；
- ClearWakeupEvent；
- 清 WUF。

## 2.14 删除 CAN Wakeup 与 PNC 绑定

EcuM 配置删除：

```
ECUM_WKSOURCE_INTERNAL_CAN → ComMPnc_0
```

原来 CAN 唤醒源自动关联一个 PNC。

删除后，CAN 唤醒不再通过 PNC 请求链自动保持通信，而是按照普通 CanNm/ComM Channel 处理。

这能减少以下情况：

```
CAN唤醒事件已经结束
但PNC仍处于REQUESTED
导致ComM无法回到NoCom
```

## 三、`c066bb7b` 建立的目标状态流程

## CAN 被动唤醒

```
CanTrcv检测Bus Wakeup/WUF
        ↓
EcuM_CheckWakeup()
        ↓
CanIf_CheckWakeup()
        ↓
EcuM_StartWakeupSources()
        ↓
CanSM_StartWakeupSource()
        ↓
CanIf/Can控制器进入可验证状态
        ↓
收到配置的NM唤醒报文
        ↓
CanIf_CheckValidation()
        ↓
EcuM_ValidateWakeupEvent()
        ↓
清除CanTrcv WUF
        ↓
CanNm进入REPEAT_MESSAGE
```

因为这是被动唤醒，没有本地 Network Request，理论上：

```
NetworkReqState = RELEASED
```

CanNm 配置决定响应：

```
MsgCycleOffset     = 0
MsgCycleTime       = 1 s
RepeatMessageTime  = 4 s
```

因此总计约 4 帧。

## 休眠

```
REPEAT_MESSAGE 4秒结束
        ↓ Network Released
READY_SLEEP
        ↓ NM Timeout
PREPARE_BUS_SLEEP
        ↓ Wait Bus Sleep
BUS_SLEEP
        ↓
ComM进入NO_COMMUNICATION
        ↓
BswM关机表达式满足
        ↓
APP_POST_RUN
        ↓
EcuM OFF
```

---
 ExeMgr 会真正调用：

```
ComM_RequestComMode(CAN_USER, COMM_NO_COMMUNICATION);
ComM_RequestComMode(XCP_USER, COMM_NO_COMMUNICATION);
```

这会在被动唤醒过程中额外插入一次本地 NoCom 请求。

理论上 ComM 用户初始需求本来就是 NoCom，不需要再主动请求；这次请求可能干扰 CanNm 刚进入的 Repeat Message 流程，使其只发送第一帧就停止。



# 八、复盘结论

这两个提交共同完成了两个层面的修复：

1. `c066bb7b` 解决“CAN 唤醒和关机链路不规范”的体系问题，把职责重新分配给 EcuM、CanIf、CanSM、CanNm 和 BswM。
    
2. `66ad9b48` 解决重构后的两个应用层干扰：
    
    - 初始 `0xFF` 触发了一次不必要的 NoCom 请求；
    - 普通 CAN 与 XCP 两个独立 Channel 被错误绑在一起。

最终设计原则是：

```
应用层只表达本地通信需求；
CAN被动唤醒由EcuM/CanIf/CanSM处理；
NM响应数量和周期由ISOLAR CanNm配置决定；
休眠必须等待CanNm、ComM和BswM状态完整收敛。
```
